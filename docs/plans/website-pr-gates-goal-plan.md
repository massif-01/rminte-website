## 3 GitHub 门禁及 Owner 例外

采用一个作用于 `refs/heads/main` 的仓库分支规则集，配合 `.github/CODEOWNERS`。不引入自建审批平台或额外审批机器人。

普通贡献者的规则：

1. 改动通过 PR 进入 `main`，禁止直接推送、强推及删除该分支。
2. 要求一个固定名称的必需检查 `pr-gate`，来源绑定实际运行该检查的 GitHub Actions App。
3. 合并前与最新目标分支保持兼容；使用 GitHub 的分支最新要求及 PR 合并结果测试。
4. 要求一次批准及 Code Owner 批准。`CODEOWNERS` 的默认负责人是 `massif-01`，覆盖整个仓库，也覆盖 `.github/`、测试、验收脚本和规范文件。
5. 推送改变 PR 差异的新提交后，旧批准失效；审查讨论处理完成后才能走普通合并流程。
6. 不要求部署环境人工批准，不要求额外 AI 审查、第二位审阅人、签名提交或合并队列。

为 `massif-01` 配置 GitHub 原生的 PR 绕过权限，优先使用当前规则 API 支持的 `User` actor 和实际用户 ID，绕过模式为 `pull_request`。只对指定账号开放，不把 `write`、`maintain` 或全体仓库管理员加入绕过名单。

这个权限按合并操作者生效，不按 PR 作者生效：Owner 可以自行合并自己的 PR，也保留对其他 PR 的最终处置权。自动检查仍生成结果；Owner 自己决定如何处理。普通贡献者不获得这项权限。这样不用把 Owner 自己的 PR 交给另一位审阅人批准。

配置先保持未激活。组织上游已实际运行 `pr-gate`、工作流已进入 `main` 后再激活，避免先要求一个尚不存在的检查。配置后通过 API 读回目标分支、规则、检查来源及绕过账号，检查 `.github/CODEOWNERS` 是否有解析错误。

## 5 CI 如何执行

### 5.1 依据真实差异识别范围

范围由 Git 差异决定，不依赖作者自己选择标签来减少检查。PR 自身改动从共同祖先比较到 PR Head；保留新增、删除和重命名信息，重命名同时考虑原路径和目标路径。Git 失败直接报错，不当成没有改动。

用真实临时 Git 仓库验证分支分叉：`main` 独立前进后，纯文档 PR 仍只识别自身文档改动，不能把 `main` 独有的生产修改算入该 PR。

PR 改动范围用于选择验收项目；实际测试代码采用 GitHub 的 PR 合并结果，报告同时记录 Base SHA、Head SHA 和被测试的提交 SHA，避免只测一条孤立分支。

| 改动类型 | 必需检查及证据 |
| --- | --- |
| 非生产文档、贡献约定 | 内容、链接及差异检查；不要求网页截图或全站浏览器测试 |
| 单页 HTML、CSS、JS 或媒体 | 相关语法、资源、浏览器操作和目标区域截图；中文、英文，桌面及手机，并覆盖受影响断点 |
| 共享字体、主题或布局 | 按依赖扩大到受影响页面；至少遵循现有 AGENTS 的首页、图册、下载、指南入口及四篇指南矩阵，中文、英文，1440、768、390、320px；模型、案例、后台和工具按实际受影响范围加入 |
| 首页布局、影像或动效 | 正常视频播放，滚动分解起止及中间状态，宝石明暗、工艺步骤、向上回退和减少动效；提供相应状态证据 |
| 多语言文案和数据 | 语义及键值对应、中文字体覆盖、生成文件一致性；检查实际涉及语言的页面显示 |
| SEO、路由、Pages Worker | 相关 SEO 测试及 HTTP 行为；使用能模拟 Pages 路由和 Worker 的运行环境 |
| 案例授权或 OTA 服务 | 对应单元及本地集成测试；UI 变动再加入页面证据；不访问生产写入接口 |
| 工作流、测试或验收脚本 | 运行被影响的检查及门禁自身回归，清楚显示验收标准是否改变，由 Owner 决定合并 |

无法证明影响局部的生产文件按相应较大范围检查，不能静默归入文档。更细的页面映射以现有资源引用为依据，不建立复杂的通用依赖分析系统。

### 5.2 检查内容

静态检查验证改动 JavaScript 和 JSON 的语法、CSS 解析、站内资源路径及部署目录中的实际文件。内联脚本和运行时生成内容通过对应解析或浏览器路径检查。锚点和本地链接检查考虑真实页面路由，不用普通文件服务器的假 404 判定 Pages 行为。

派生资源复用已有 `--check`。指南和译文在隔离检出或临时副本中生成，核对预期产物与提交内容一致，不自动修改提交，不每次联网重新生成全部字体。

浏览器测试验证用户能完成操作，而不只验证 DOM 存在。按范围覆盖菜单开关、Escape、语言切换、焦点、图册切换和滑动、指南搜索和复制、下载，以及相关页面的既有行为。下载涉及本地发布资源时至少实际获取一个文件；生产 OTA 接口采用明确标注的本地测试响应验证页面契约，不能把它当成真实设备或线上服务验收。

布局检查同时看截图、计算样式和可见内容边界，避免祖先 `overflow:hidden` 裁掉内容却没有横向滚动条。只检查有明确布局约定的可见正文、控件和媒体，不把有意裁切的动效层、折叠区或图册轨道一律判错。

共享行为遵循 DESIGN 已确认的状态；不把尚未实施的设计讨论写成必过断言。既有错误和外部网络失败分别定位，不能用无条件忽略所有控制台错误制造通过。

### 5.3 工作流及统一入口

工作流至少处理 PR 的打开、重开、提交更新、正文编辑和转为可审查状态。必需工作流不通过 `paths` 把整次运行跳过；昂贵的项目在内部按范围选择。保留平台原有 fork 运行策略，不另加人工工作流审批制度。

`pr-gate` 始终汇总本次应执行项目：必需项失败、取消、缺证据或意外跳过，汇总失败；不适用项明确记录原因。不能把任意 `skipped` 当成功，也不能用 `continue-on-error` 隐藏必需失败。由失败或取消状态生成的诊断材料不能变成合格证据。

普通贡献者 PR 的必填说明检查只验证字段和必要证据是否存在，不用关键词或 AI 判断代替需求、审美及规格审核。Owner 本人 PR 不因缺少模板字段或人工审查材料而失败；自动技术检查正常执行。

提供两个清楚的本地入口，例如 `npm run verify` 和 `npm run evidence`，和 CI 调用同一套脚本。失败信息给出具体文件、页面、缺字或操作步骤，以及可复验命令。同事不必理解整套工作流 YAML 才能修复失败。

PR 执行环境只需要读取仓库。开发依赖使用锁文件，Actions 固定到经核实的提交。测试账号、密钥和数据库临时生成，不提供生产 Cloudflare、D1、R2 或 OTA 发布凭据；不在能访问生产凭据的事件中执行未合并的 PR 代码。

## 6 截图及 PR 证据

| 修改内容 | 证据要求 |
| --- | --- |
| 视觉修改 | 相同页面、区域、语言、视口和状态的前后截图；覆盖改动位置及相关信息组 |
| 交互修改 | 必要截图加实际操作测试；失败保留 trace，重要状态变化保留过程证据 |
| 动效修改 | 起点、中间、终点及必要回退状态；正常动效测试保留短录屏或可复验的过程记录，不能用静止截图证明动效正常 |
| 文档或无 UI 的服务逻辑 | 对应内容、接口或测试证据，不强制无关网页截图 |

CI 自动生成 HTML 测试报告、截图、必要的 trace 或录屏，以及一份机器可读清单。清单记录 PR、Base SHA、Head SHA、测试提交、页面、语言、视口、状态、检查结果和不适用原因。证据上传为 Actions artifact，失败也保留已有诊断材料，默认保留 30 天，不将每次截图提交进源码仓库。

前后截图在同一运行环境中生成。等待字体和图片就绪，统一动态媒体的截图取样条件；正常播放和滚动行为在独立测试中验证，不为了截图稳定修改生产动画。数据为临时测试数据时，在报告中说明。

新的 Head 触发新的证据生成，旧 Head 的截图或旧运行结果不能充当当前验证。当前截图缺失、清单版本不匹配或必需报告未生成时，普通贡献者 PR 不通过。

首版生成可比较的截图并检查确定性的功能和布局错误，不设置全站像素差异阈值，也不引入 AI 审美评分。Owner 判断视觉变化是否符合 DESIGN。稳定区域后续是否升级为截图基线门禁，是另一个有明确依据的调整，不作为本目标的前置工作。

普通贡献者 PR 模板只包含影响审核的信息：

1. 要解决的问题及修改原因。
2. 影响的页面、语言、交互或服务。
3. 涉及内容删除、规格、承诺、新依赖或设计方向时的依据。
4. 实际验证结果、CI 证据入口和仍未验证的项目。
5. 改动测试、截图基线、检查阈值或豁免规则时的具体原因。

不强制每个小修改另开 Issue，不按 AI 生成占比、代码行数或任意覆盖率数字决定通过。作者负责解释关键改动，验证结果必须可复验。

## 7 AGENTS 中需要写明的约定

以下内容归入现有贡献和交付章节，避免重复追加另一套验收矩阵：

- 同事的一个 PR 解决一个明确问题，不混入无关重构、产品文案或服务发布。
- 页面修改按现有范围矩阵验收，并提供当前提交的自动证据；纯文档和无 UI 逻辑提供各自所需证据。
- 本地验证、CI、测试数据、预览、正式上线和真实设备结果分开陈述。
- 修改测试、基线、阈值、CI 或检查豁免必须说明原因，不得为了过关删除必要验证。
- 普通贡献者需要 Owner 批准；Owner 自己的 PR 自行决定合并，不增加额外人审或 AI 审查。
- 正式仓库为组织上游；Owner 合并到 `main` 即同意自动上线，代理不再索取部署或上线确认。
- 同事不得绕过规则、直接改生产资源或使用未获授权的生产凭据。Owner 保留管理与原生绕过权限。

## 8 执行顺序

| 阶段 | 工作 | 阶段结果 |
| --- | --- | --- |
| 1 确认起点 | 从最新组织上游建立隔离检出；读取 AGENTS、DESIGN、既有脚本和当前 Pages 配置；核对组织迁移后的 GitHub App 连接 | 确定源提交、依赖、构建及自动部署链路；保留原工作区 |
| 2 实现验证入口 | 完成范围识别、静态和派生检查、必要的回归及本地运行入口 | 干净基线能运行，失败有具体原因；范围分类经真实 Git 分叉验证 |
| 3 实现浏览器及证据 | 完成受影响页面矩阵、关键操作、前后截图和报告；接入服务本地测试设施 | 当前提交有完整证据，正常和减少动效状态分别验证 |
| 4 提交组织上游 | 完成工作流、CODEOWNERS、模板和贡献文档；仅提交本目标文件，向 `RMinte/rminte-website:main` 提配置 PR | 上游 PR、Head SHA、文件清单及 Actions 真实运行结果可核对；不能仅提交到个人 fork 后声称落地 |
| 5 合并并激活 | Owner 自行合并配置 PR；随后按既有授权激活规则集，读回配置；核实 `main` 自动部署，无第二次发布审批 | 工作流在上游默认分支生效，Owner 例外及同事约束实际配置正确 |
| 6 完成验收 | 核对最新主线检查、规则、自动部署来源和正式地址；提交简洁的证据与使用说明 | 门禁已经生效，合并自动上线链路已核实 |

目标执行代理不代替 Owner 合并配置 PR。若代码和 CI 已准备好但 Owner 尚未合并，报告“实现已交付，门禁尚未在主线生效”；不把这一状态标成整个目标完成。Owner 合并后继续完成激活和生效核查，不再增加新的审批步骤。

若组织迁移导致 Pages 仍连接个人仓库，只修正本网站项目对应的连接或触发链路，保持域名、输出目录、绑定资源及自动上线方式。若平台限制要求更换项目或迁移生产数据，这属于新增关键决策，先说明实际证据和最小可行选项。

## 9 目标完成的验收标准

| 验收项目 | 合格证据 |
| --- | --- |
| 组织上游落地 | 工作流及约定已进入 `RMinte/rminte-website:main`；文件内容与确定提交对应 |

规则配置读回、Owner 实际合并、普通贡献者实际被拒绝，是不同证据。以当前具备的身份验证原生设置和 PR 状态；没有以普通贡献者身份执行的拒绝操作，不声称已经实测。无需为了这项检查新增账号、索取同事凭据或调整组织成员。
