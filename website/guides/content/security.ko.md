# TianShanOS 보안 페이지 가이드

대상 버전: TianshanOS 0.6.4. 확인일: 2026년 11월 3일.

이 가이드를 사용하여 장치 비밀번호를 변경하고, SSH 서버에 연결하고, 서버 ID를 확인하고, 인증서 및 구성 패키지를 관리하세요. 최초 설정의 경우 1, 2, 3장부터 시작하세요. 인증서 발급 및 복구에 대해서는 장치 또는 서버 관리자와 협력하세요.

> 신뢰할 수 있는 관리 네트워크를 사용하세요. 전체 웹 인터페이스는 HTTP를 사용합니다. 인증서를 설치해도 HTTPS로 전환되지는 않습니다. 일부 인증서 작업은 로그인하지 않고도 계속 호출할 수 있으므로 로그아웃은 네트워크 격리를 대체하지 않습니다. 공용 네트워크에 장치 관리 액세스를 노출하지 마십시오.

## 1. 시작하기 전에

### 1.1 필요한 작업 찾기

1. 브라우저에 대상 장치의 IP 주소를 입력하고 장치 계정으로 로그인하세요.
2. 탐색 모음에서 보안을 선택합니다. 비밀번호를 입력하거나 열쇠를 취급하기 전에 주소를 확인하세요.
3. 아래 표를 사용하여 올바른 섹션을 찾으세요. root에는 계정 보안도 표시됩니다.

| 작업 | 어디로 가야합니까? |
|---|---|
| 장치의 root 또는 admin 비밀번호 변경 | 계정 보안; 2 장 |
| SSH 키를 사용하여 서버에 연결 | 키 관리 및 배포된 호스트; 3 장 |
| 키 복사, 호스트 편집 또는 제거, 지문 확인 | 키 관리, 배포된 호스트 및 알려진 호스트 지문 제4장 |
| 장치 인증서 요청 및 설치 | HTTPS 인증서; 5 장 |
| 일반 암호화된 구성 패키지 검사 또는 생성 | 구성 팩; 먼저 6장의 제한 사항을 읽어보세요. |

### 1.2 계정 및 장치 ID

- **admin**은 보안을 열고 페이지에서 제공하는 SSH 키, 호스트 및 인증서 기능을 관리할 수 있습니다. 계정 보안이 표시되지 않습니다.
- **root**는 root와 admin의 비밀번호 설정, admin 접근 복구, root가 필요한 자동화 설정과 웹 터미널도 관리할 수 있습니다. 로그인한 admin도 홈 화면에서 제공하는 서비스 제어를 사용할 수 있습니다.
- **Developer 장치**는 인증서에 개발용 식별 정보가 기록된 장치입니다. 로그인 계정이 아닙니다. 암호화된 Config Pack과 SSH 호스트 설정을 내보내려면 이 식별 정보가 필요합니다. root로 로그인해도 바뀌지 않습니다.

로그인이 필요한 작업에서는 장치가 계정을 확인합니다. 일부 조회와 인증서 작업은 아직 로그인 없이 호출할 수 있습니다. 버튼이 보인다고 계정과 장치의 조건을 모두 충족한 것은 아닙니다. 권한이 거부되면 세션과 필요한 조건을 확인한 뒤 다시 시도하세요.

### 1.3 작업 준비

1. 컴퓨터와 대상 장치가 신뢰할 수 있는 관리 네트워크에 있는지 확인하십시오.
2. 서버 관리자에게 SSH 주소, 포트, 계정 및 전체 호스트 지문을 확인하세요.
3. 페이지를 통해 공개 키를 배포하거나 취소하려면 원격 계정의 비밀번호와 비밀번호 인증이 필요합니다. 서버 관리자는 나중에 비밀번호 인증을 활성화할지 여부를 결정합니다.
4. 액세스 취소, 키 삭제, 인증서 교체 전에 서버 콘솔, 다른 관리자 키, 기기의 HTTP 인터페이스 등 다른 관리 연결이 작동하는지 확인하세요.

## 2. 장치 비밀번호 변경

이러한 컨트롤은 TianshanOS 로그인 비밀번호를 변경합니다. 원격 서버의 SSH 비밀번호는 변경되지 않습니다.

### 2.1 처음 로그인 후 프롬프트

계정에 여전히 비밀번호가 변경되지 않은 것으로 표시된 경우 로그인 후 비밀번호 변경 프롬프트가 나타납니다. 길고 고유한 비밀번호를 설정하세요. 나중에 변경하도록 선택하면 메시지가 닫힙니다.

이 메시지는 언제든지 다시 열 수 있는 계정 설정 화면이 아닙니다. 관리자가 이미 비밀번호를 변경했고 또 다른 변경이 필요한 경우 root에게 보안에서 비밀번호를 설정하도록 요청하세요.

### 2.2 비밀번호를 root로 설정하세요.

1. root로 로그인하고 보안을 엽니다.
2. 계정 보안에서 root 또는 관리자 비밀번호 제어를 찾으세요. 새 비밀번호와 확인을 입력하세요.
3. root 비밀번호 설정 또는 관리자 비밀번호 설정을 선택합니다. 최소 12자 이상의 고유한 비밀번호를 사용하세요. 영문자, 숫자, 기호는 길이 계산 시 차이를 방지하는 데 도움이 됩니다.

화면에는 4~64자로 안내하지만 장치는 UTF-8 바이트 수를 검사합니다. 영문, 숫자, 일반 ASCII 기호는 1자에 1바이트이고 한자는 보통 여러 바이트입니다. 4는 허용하는 최소 길이이며 권장 비밀번호 길이가 아닙니다.

**결과 확인:** 원래 세션에서 로그아웃하기 전에 개인 탐색 창에서 새 비밀번호로 로그인하세요. 새 비밀번호를 설정해도 기존 세션이 자동으로 종료되지는 않습니다.

**로그인에 실패한 경우:** 계정과 기기 주소를 확인하세요. 5번 연속 실패하면 약 5분간의 잠금이 트리거됩니다. 반복적인 추측을 피하세요.

### 2.3 admin 비밀번호 재설정

루트는 admin를 기본값으로 재설정을 선택하여 `rm01`에 대한 비밀번호를 복원하고 로그인 잠금을 지울 수 있습니다. 새 세션에서 admin로 로그인한 후 즉시 고유 비밀번호를 설정하세요.

> 일시적으로 액세스를 복구하는 경우에만 기본 비밀번호를 사용하세요. 즉시 변경하고 더 이상 필요하지 않은 세션에서 로그아웃하세요.

### 2.4 root 비밀번호를 잊어버린 경우

장치에 맞는 복구 방법은 장치 관리자에게 문의하세요. 현재 복구 펌웨어는 새 설정 저장 방식만 지원하며 root와 admin 비밀번호를 모두 초기화합니다. 오래된 복구 펌웨어를 직접 설치하지 마세요. 접근을 복구한 뒤 각 계정에 고유한 비밀번호를 설정하세요.

## 3. SSH 키를 사용하여 서버에 연결

초기 설정에서는 RSA 키를 생성하고, 공개 키를 배포하고, 결과를 검토하고, 연결을 테스트합니다. 이 프로세스의 일부로 서버 지문을 확인하십시오. 키를 폐기하려면 모든 서버에서 액세스를 취소하고 이전 키가 더 이상 작동하지 않는지 확인한 다음 로컬 키를 삭제하세요.

### 3.1 키 생성

1. 키 관리에서 새 키 생성을 선택합니다.
2. 사용하지 않는 키 ID를 입력하세요. 예: `backup01`. 쉼표 없이 영문과 숫자로 10자 이내로 정하세요. 실제 상한은 UTF-8 10바이트이며, 한자 10자를 뜻하지 않습니다.
3. RSA 2048 또는 RSA 4096을 선택합니다. RSA 2048이 기본값입니다. ECDSA 옵션도 표시되지만 현재 SSH 워크플로는 이를 지원하지 않습니다. SSH용 RSA를 선택합니다.
4. 유용한 경우 설명이나 별칭을 추가하세요. 개인 키를 백업하거나 마이그레이션해야 하는 경우에만 내보내기 가능을 활성화하십시오. 생성 후 이 옵션을 변경할 수 있는 페이지 컨트롤이 없습니다.
5. 필요한 경우 숨김을 설정한 다음 생성을 선택합니다. 숨김은 표시에 영향을 미칩니다. 실제 키 ID나 키에 대한 액세스를 차단하지는 않습니다.

**결과 확인:** 창이 닫히고 목록이 새로고침된 후 원하는 ID와 RSA 유형을 찾습니다. 공개 키를 열고 전체 텍스트가 `ssh-rsa` 로 시작하는지 확인하세요.

**생성을 기다리는 동안:** 다시 제출하지 마세요. 창을 닫아도 장치의 생성 작업은 취소되지 않습니다.

| 메시지 또는 상황 | 수행할 작업 |
|---|---|
| 이미 사용중인 아이디입니다 | 다른 ID를 선택하세요. 새 키를 생성하면 기존 키를 덮어쓸 수 없습니다. |
| 키 개수 제한에 도달했습니다. | 장치에는 최대 8개의 SSH 키가 있습니다. 먼저 해지 프로세스를 통해 사용되지 않은 키를 폐기합니다. |
| 스토리지 또는 메모리가 부족합니다. | 장치 리소스 문제를 해결합니다. 실패를 성공적인 창조로 여기지 말라 |
| 키가 생성되었지만 목록을 새로 고칠 수 없습니다. | 수동으로 새로 고치고 키를 확인하세요. 다시 생성하지 마세요 |
| 세대는 확인되지 않았습니다. | 기다렸다가 기록을 확인하세요. 동일한 ID를 다시 제출하지 마세요. |
| 정리가 완료되지 않았습니다. | 키 생성을 일시중지하고 관리자에게 저장용량 확인을 요청하세요. |

동일한 ID를 가진 기록은 이 시도가 완료되었음을 증명하지 않습니다. 결과가 불확실할 경우 기록과 핵심자료를 확인하세요.

### 3.2 공개 키 배포

배포에서는 원격 계정의 권한 부여 파일인 `~/.ssh/authorized_keys` 에 공개 키를 추가하므로 일치하는 개인 키로 로그인할 수 있습니다. 서버 비밀번호는 변경되지 않습니다.

1. 의도한 키 행에서 배포를 선택합니다.
2. 서버 주소, 사용자 이름, SSH 포트 및 SSH 로그인 비밀번호를 입력합니다.
3. 주소와 계정을 검토한 다음 배포 시작을 선택합니다.
4. 결과를 읽고 배포된 호스트에서 해당 레코드를 확인합니다.

> 배포에서는 비밀번호를 사용하기 전에 호스트 지문을 확인합니다. 알려진 호스트에 대해 변경된 지문이 거부됩니다. 그러나 알 수 없는 호스트에 대한 초기 배포에서는 먼저 확인을 요청하지 않고 지문을 저장하고 신뢰합니다. 통제된 네트워크를 사용하고 신뢰할 수 있는 채널을 통해 전체 지문을 확인하세요.

### 3.3 배포 결과 이해

| 결과가 말해 주는 것 | 다음에 수행할 작업 |
|---|---|
| 키가 배포되었고, 호스트가 등록되었으며, 공개 키 로그인이 확인되었습니다. | 호스트 세부 정보를 확인한 후 실제 작업을 테스트하세요. |
| 키가 배포되고 호스트가 등록되었지만 로그인이 확인되지 않았습니다. | 테스트를 선택합니다. 실패하면 다른 연결을 통해 인증 및 계정 설정을 확인하세요. |
| 키가 배포되었지만 등록이 실패했거나 확인되지 않았습니다. | 다시 배포하기 전에 로컬 목록과 원격 인증을 확인하세요. |
| 배포가 완료되었지만 목록을 새로 고칠 수 없습니다. | 수동으로 새로 고칩니다. 새로 고침이 실패했다고 해서 원격 키가 설치되지 않았다는 의미는 아닙니다. |

배포할 때마다 키가 추가되므로 이를 반복하면 중복된 줄이 생성될 수 있습니다. 원격 결과를 확인해야 할 경우 다른 관리 연결을 사용하여 인증 파일을 검사하세요.

### 3.4 연결 테스트

1. 배포된 호스트에서 주소, 포트, 사용자 이름, 키 ID를 확인한 후 테스트를 선택합니다.
2. 초기 지문 확인이 나타나면 신뢰 및 연결을 선택하기 전에 섹션 4.3에 설명된 대로 전체 지문을 비교하십시오.
3. 지문이 변경된 경우 대화 상자에는 저장된 값과 현재 값이 모두 표시됩니다. 취소하고 먼저 조사해 보세요. 승인된 변경 사항을 확인한 후에만 호스트 키 업데이트를 선택하세요.

테스트에서는 고정 에코 명령 `echo "TianshanOS SSH Test OK"` 를 시도합니다. 성공 메시지는 명령의 종료 상태나 출력을 확인하지 않습니다. 기본적인 연결 확인 용도로만 사용하세요. sudo 또는 응용 프로그램 명령이 작동하는지 확인하지는 않습니다.

**실패할 경우:** 네트워크, SSH 서비스, 계정, 원격 인증을 확인하세요. 서버 ID가 확실하지 않거나 지문이 변경된 경우 재시도를 중지하세요.

### 3.5 원격 액세스를 취소한 후 로컬 기록 정리

> 취소하면 향후 로그인에 영향을 미칩니다. 다른 관리 연결이 작동하는지 확인하고 여전히 중지하거나 확인해야 하는 작업을 처리합니다. 공개 키를 취소하거나, 호스트를 제거하거나, 키를 삭제해도 원격 프로그램이 자동으로 중지되지는 않습니다.

1. 호스트 행에서 취소를 선택하고 서버 비밀번호를 입력한 후 원격 공개 키 취소를 선택합니다. 키 행에서 시작하여 대상 세부정보를 입력할 수도 있습니다.
2. 원격 결과를 읽습니다. 취소가 성공하면 로컬 호스트 삭제 확인이 열립니다. 로컬 삭제에는 여전히 별도의 결정이 필요합니다. 기록이 자동으로 제거되지 않았습니다.
3. 신뢰할 수 있는 연결을 통해 공개 키와 중복 항목이 인증 파일에서 사라졌는지 확인하세요. 이전 키가 더 이상 작동하지 않는지 확인하세요. 이전 액세스가 나중에 복원되지 않도록 서버의 백업 정책에 따라 결과 `authorized_keys.bak` 를 처리합니다.
4. 로컬 호스트 구성을 제거하려면 확인하기 전에 섹션 4.2에 설명된 대로 참조 및 영향을 검토하세요.
5. 모든 대상 서버 및 관련 작업이 처리되면 섹션 4.1에 설명된 대로 이전 장치 키와 불필요한 개인 키 복사본을 삭제합니다.

**일치하는 공개 키가 없는 경우:** 대상 계정과 서버의 공개 키 등록을 확인하세요. 「로컬 호스트 설정 검토 및 삭제」는 장치 안의 기록만 처리하며, 서버 확인을 대신하지 않습니다.

**해지에 실패하거나 확인되지 않은 경우:** 신뢰할 수 있는 연결을 통해 원격 승인을 검사합니다. 결과가 명확해질 때까지 로컬 키를 유지하세요. 원격 해지 및 로컬 삭제를 별도로 평가합니다. 하나의 실패가 다른 하나가 결코 일어나지 않았다는 것을 증명하지는 않습니다.

## 4. 키, 호스트, 지문 관리

### 4.1 키 복사, 내보내기 및 삭제

SSH 키 행에 대해서는 아래 지침을 따르세요. `https` 라는 행에는 장치 인증서 키가 포함되어 있습니다. 해당 행을 삭제하면 모든 인증서 자격 증명이 지워집니다. 먼저 섹션 5.6을 읽어보세요.

**공개 키 복사:** 공개 키를 선택하고 전체 한 줄 값을 서버 관리자에게 보냅니다. 공개 키는 공유될 수 있습니다. 관리자가 계정의 인증 목록에 키를 추가하면 액세스 권한이 부여됩니다.

**개인 키 내보내기:** 키를 만들 때 「내보내기 가능」을 켠 경우에만 사용할 수 있습니다. 신뢰하는 컴퓨터와 격리된 관리 네트워크에서 「개인 키」를 선택하고 승인된 비밀 정보 저장소에 보관하세요. 클립보드와 다운로드 폴더의 임시 사본은 지우세요. 채팅, 문의 티켓, 로그에 붙여 넣지 마세요.

**복사가 아무 작업도 수행되지 않는 경우:** 브라우저는 HTTP 페이지에서 클립보드 액세스를 제한할 수 있습니다. 텍스트를 수동으로 선택하고 복사한 다음 완성도를 확인하세요. 복사를 활성화하기 위해 브라우저 보안 설정을 약화시키지 마십시오.

**키를 삭제하기 전:** 서버 승인을 취소하고 확인에 나열된 호스트 및 실행 기록을 검토하세요. 삭제 후 이 장치는 해당 키를 사용하여 관련 작업을 연결, 확인 또는 중지할 수 없지만 해당 작업은 원격으로 계속 실행될 수 있습니다. 먼저 다른 연결을 통해 처리하세요. 불완전한 영향 목록이 참조가 없다는 의미는 아닙니다.

삭제 확인 후 새로고침하여 결과를 확인하세요. 스토리지 삭제가 완료되지 않은 경우, 현재 상태를 확인하여 관리자에게 해결을 요청하세요. 누락된 목록 항목만으로는 완료를 증명할 수 없습니다.

### 4.2 호스트 제거 및 해당 참조 처리

| 액션 | 무엇이 바뀌는가 |
|---|---|
| 공개 키 취소 | 일치하는 원격 인증을 제거합니다. 원격 비밀번호가 필요합니다 |
| 호스트 제거 | 장치 구성을 삭제하고 선택에 따라 관련 명령 및 규칙을 처리합니다. |
| 키 삭제 | 장치에서 키 자료를 삭제합니다. |
| 알려진 호스트 지문 제거 | 장치에 저장된 서버 ID 레코드를 삭제합니다. |

마지막 세 가지 작업은 원격 공개 키를 취소하지도 않고 원격 프로그램을 중지하지도 않습니다. 배포된 호스트는 로컬 목록일 뿐입니다. 빈 목록은 원격 액세스가 제거되었음을 증명하지 않습니다.

1. 호스트 행에서 제거를 선택하고 참조 확인을 기다립니다.
2. 영향을 받는 명령, 템플릿 또는 규칙을 검토합니다. 교체 호스트를 선택하거나 참조 링크를 해제하고 영향을 받는 구성을 비활성화합니다. 교체에는 필수 계정, 키 및 작업 환경이 있어야 합니다.
3. 삭제를 선택하고 결과를 읽어 관련 명령 및 규칙을 확인합니다. 연결 해제된 명령을 다시 활성화하려면 호스트를 선택해야 합니다.

강제 삭제는 영향을 이해한 뒤 설정을 제거하기로 결정할 때 사용하는 기능입니다. 원격 서비스가 중지됐거나 상태가 확인됐다는 조건을 요구하지 않습니다. 영향을 확인할 수 없다면 「자동화를 일시 중지하고 삭제를 계속하는 데 동의」를 선택해야 할 수 있습니다. 이후 root가 설정을 확인하고 활성화할 때까지 자동화는 일시 중지 상태로 남습니다.

> 단지 오류를 지우기 위해 강제로 삭제하지 마십시오. 먼저 원격 작업을 관리할 사람과 영향을 받을 자동 규칙을 설정합니다.

구성이 변경된 경우 삭제 영향 검토를 선택하고 새 결과에서 결정합니다. 저장 실패 또는 확인되지 않은 결과가 발생한 경우 구성을 새로 고치고 검사한 후 다시 삭제하세요.

### 4.3 SSH 서버 지문 확인

지문은 서버를 식별하는 데 도움이 됩니다. 이 페이지에는 SHA-256 다이제스트가 64개의 16진수 문자로 표시됩니다. OpenSSH 도구는 일반적으로 `SHA256:base64` 를 표시합니다. 관리자에게 동일한 형식을 요청하세요. 이러한 문자열은 직접 비교할 수 없습니다.

**전체 값 비교:** 알려진 호스트 지문 아래에서 보기를 선택하고 이를 서버 콘솔, 자산 기록 또는 다른 신뢰할 수 있는 채널의 값과 비교합니다. 표에는 처음 32자만 표시되어 전체 확인에는 충분하지 않습니다.

**테스트에서 확인을 요청하는 경우:** 초기 대화 상자에 현재 지문이 표시됩니다. 변경 경고에는 저장된 값과 현재 값이 모두 표시되며 기본적으로 취소가 허용됩니다. 서버, 주소, 포트, 유지관리 기록 등을 확인하신 후 결정하세요. 확인은 표시된 지문에만 적용됩니다. 다른 변경에는 또 다른 확인이 필요합니다.

**다르거나 출처가 불분명한 경우** 취소하고 조사해 보세요. 의심스러운 연결을 통해 비밀번호가 사용된 경우 신뢰할 수 있는 연결을 통해 비밀번호를 변경하고 로그인 로그 및 승인을 검토하세요. 키를 취소하기 위해 의심스러운 연결을 통해 비밀번호를 보내지 마십시오.

**승인된 시스템 재설치나 호스트 키 변경 후:** 새 지문과 변경 이력을 확인한 뒤 테스트 창에서 「호스트 키 업데이트」를 선택하세요. 검사를 건너뛰려고 이전 항목을 지우지 마세요. 항목을 지워도 다음 연결이 안전해지는 것은 아닙니다.

지문은 장치 내부에 저장되며 더 이상 SD 카드 지문 파일과 동기화되지 않습니다. 구성 백업 및 SSH 호스트 가져오기에는 이러한 기록이 포함되지 않습니다. 복구 또는 마이그레이션 후에 서버 ID를 다시 확인하세요.

### 4.4 호스트 편집

1. 배포된 호스트에서 편집을 선택합니다.
2. SSH 호스트 편집에서 주소, 포트 또는 로그인 계정을 변경합니다. 키 인증의 경우 로그인 키 ID를 변경할 수도 있습니다. 포트는 1-65535여야 합니다.
3. 저장을 선택하고 세부 정보를 새로 고치고 검토한 후 연결을 테스트합니다. 대상 서버 변경 시 전체 지문을 확인하세요.

변경 사항은 향후 연결에 적용됩니다. 이미 시작된 작업에 대한 실행 기록은 여전히 원래 호스트 세부 정보를 사용합니다. 주소를 변경해도 이전 작업이 이동되거나 중지되지 않습니다.

### 4.5 SSH 호스트 구성 가져오기 및 내보내기

호스트 가져오기는 6장의 일반 구성 팩 제어와 별개인 전용 워크플로입니다. 패키지에는 주소, 포트, 계정, 인증 방법 및 키 ID가 포함되어 있습니다. 여기에는 SSH 비밀번호, 개인 키 또는 저장된 호스트 지문이 포함되어 있지 않으며 서버 액세스 권한을 부여하지 않습니다.

**내보내기:** Developer 장치에서 호스트 행의 「내보내기」를 선택하세요. 다른 장치용이라면 그 장치의 인증서를 붙여 넣고 확인한 뒤 패키지를 만들고 「다운로드」를 선택하세요. 파일이 저장됐는지 확인하세요. 일반 장치는 root로 로그인해도 내보내기 권한을 얻지 못합니다.

**가져오기 전:** 소스를 확인하고, 패키지가 이 기기용으로 제작되었는지 확인하고, 올바른 키가 이미 있는지 확인하세요. 일치하는 ID만으로는 충분하지 않습니다. 해당 키 자료는 원격 인증과 일치해야 합니다. 현재 구성 위치는 쓰기 가능해야 하지만 SD 카드가 항상 필요한 것은 아닙니다.

1. 호스트 가져오기를 선택하고 `.tscfg` 파일을 선택한 후 확인이 완료될 때까지 기다립니다.
2. 미리보기에서 호스트, 주소, 계정 및 변경 사항을 검토하세요. 기존 구성을 동일한 ID로 바꾸려는 경우에만 덮어쓰기를 활성화하십시오.
3. 가져오기 확인을 선택합니다. 장치는 오래된 미리 보기에 의존하지 않고 패키지, 자격 증명 및 현재 구성을 다시 확인합니다.
4. 성공적으로 저장한 후 호스트 목록을 새로 고쳐서 확인한 다음 연결을 테스트하세요. 저장된 구성은 다시 시작하지 않고도 즉시 적용됩니다. 기존 활성화 또는 일시 중지된 자동화 설정은 유지됩니다.

이 워크플로는 미리 보기 중에 수신자 장치, 서명, 신뢰할 수 있는 발급자 및 서명자의 자격을 확인한 다음 콘텐츠의 암호를 해독하고 확인합니다. 또한 신뢰할 수 있는 채널을 통해 출처를 확인하세요. 이름이나 공식 라벨만으로는 충분하지 않습니다.

**검사에 실패한 경우:** 메시지에 따라 기기 시간, 기기 인증서, 클라이언트 CA 체인, 신뢰할 수 있는 발급자 설정을 확인하세요. HTTPS에 허용된 인증서가 반드시 구성 팩에 서명할 수 있는 것은 아닙니다. 이 문제를 해결하려면 장치 관리자에게 문의하세요. 단지 익숙하지 않은 패키지를 가져오기 위해 익숙하지 않은 CA를 설치하지 마십시오.

**미리보기가 만료되는 경우:** 패키지 다시 확인을 선택하고 변경 사항을 검토하세요. 대화 상자를 다시 열어야 하는 경우 먼저 필요한 입력을 유지하고 섹션 7.2를 따르십시오.

### 4.6 백업과 복원이 가져올 수 있는 것

SSH 호스트는 자동화 규칙, 템플릿, 명령 및 관련 구성과 함께 저장됩니다. 정상 작동에서는 SD 구성을 사용합니다. 내부 비상 모드에서는 편집 내용이 장치 내부에 저장됩니다. 호스트 가져오기, 편집 및 제거는 모두 현재 사용 중인 구성에 기록됩니다.

root는 자동화 페이지의 구성 및 백업에서 현재 위치를 볼 수 있습니다. 긴급 백업 저장은 전체 내부 복사본을 수동으로 업데이트합니다. 편집할 때마다 동기화되지 않습니다. 긴급 백업 복원은 다시 시작하지 않고 현재 구성을 교체하기 전의 차이점을 보여줍니다.

이전 복사본은 이전 호스트, 명령 및 규칙을 다시 가져올 수 있으며 자동화 활성화 여부를 변경할 수 있습니다. 복원하기 전에 차이점을 검토하세요. 복원은 원격 서비스를 중지 또는 다시 시작하거나 개인 키 또는 알려진 호스트 지문을 복구하지 않습니다.

현재 구성을 삭제해도 다른 수동 복사본은 정리되지 않습니다. 호스트를 폐기한 후 응급 복사본을 업데이트하도록 준비합니다. SD 카드를 다시 삽입해도 구성이 자동으로 전환되지 않습니다. root는 구성 및 백업에서 사용할 항목을 선택해야 합니다. 파일 관리자를 통해 내부적으로 관리되는 자동화 파일을 삭제하거나 덮어쓰지 마십시오.

## 5. HTTPS 인증서 및 mTLS 구성

이 가이드에서 검토한 빌드 구성은 HTTPS 서비스를 활성화하지 않습니다. 인증서 제어는 자격 증명을 준비할 수 있지만 포트 443이 열려 있는지 설정하지는 않습니다. HTTPS가 필요한 경우 먼저 장치 관리자에게 설치된 펌웨어에서 이를 활성화하는지 확인하도록 요청하세요.

활성화되면 현재 HTTPS 서비스는 전체 웹 인터페이스가 아닌 상태, ID 및 권한 테스트 엔드포인트를 제공합니다. 아래 연결 테스트는 HTTPS가 활성화된 배포에 적용됩니다.

### 5.1 어떤 인증서가 무엇을 하는지 알아보세요.

- **장치 인증서 및 개인 키**를 사용하면 장치가 클라이언트에게 자신의 신원을 증명할 수 있습니다.
- 컴퓨터나 서비스에 보관된 **클라이언트 인증서 및 개인 키**를 통해 해당 클라이언트는 기기에 자신의 신원을 증명할 수 있습니다.
- **기기의 클라이언트 확인 CA**는 클라이언트 인증서의 유효성을 검사합니다. 브라우저가 장치 인증서를 자동으로 신뢰하도록 만들지는 않습니다.

이 양방향 인증을 mTLS라고 합니다. 클라이언트는 여전히 장치 인증서 발급자를 신뢰하고 액세스 이름, 허용된 용도 및 유효성을 확인해야 합니다. CA는 인증 기관 또는 해당 인증서입니다.

### 5.2 상태 읽기 및 장치 시간 설정

「저장됨」, 「유효기간 내」, 「HTTPS: 실행 중」은 각각 저장 상태, 유효기간, 서비스 동작을 뜻합니다. 하나만으로 다른 조건도 충족했다고 판단할 수 없습니다.

| 상태 또는 상황 | 수행할 작업 |
|---|---|
| 장치 인증서, 개인 키 또는 클라이언트 확인 CA가 누락되었습니다. | 누락된 자료를 설치합니다. |
| 장치 시간을 기다리는 중 | 컴퓨터 시계를 확인한 다음 이 컴퓨터에서 장치 시간 설정(브라우저 소스)을 선택합니다. |
| 아직 유효하지 않거나 만료됨 | 장치 시간과 인증서 날짜를 확인하세요. 필요한 경우 갱신 준비 |
| 시간 유효성은 정확하지만 HTTPS가 중지되었습니다. | 먼저 펌웨어가 HTTPS를 활성화하는지 확인한 다음 표시된 자격 증명, 일치 또는 시작 문제를 해결합니다. |
| 실행 중인 서비스는 여전히 이전 자료를 사용합니다. | 다른 작업을 저장하고 지시에 따라 다시 시작한 후 실제로 사용 중인 인증서를 확인하세요. |
| 저장 또는 읽기가 확인되지 않았습니다. | 다시 설치하거나 삭제하기 전에 새로고침하고 확인하세요. |

펌웨어에서 HTTPS가 활성화되면 자격 증명과 시간이 준비되면 중지된 서비스가 시작을 시도합니다. 시간을 설정한 후 기기 시계, 동기화 상태, HTTPS 상태를 확인하세요. 설치 성공만으로는 준비 상태가 입증되지 않습니다.

### 5.3 장치 키 및 인증서 요청 생성

> 키가 이미 존재하는 경우 먼저 섹션 5.6을 읽으십시오. 재생성하면 이를 덮어쓰게 되어 이전 인증서 및 패키지를 계속 사용하지 못하게 될 수 있습니다.

1. 키 쌍 생성을 선택합니다. 이렇게 하면 SSH 키와 관련되지 않은 별도의 ECDSA P-256 개인 키가 생성됩니다. 이 인터페이스를 통해 내보낼 수 없습니다.
2. CSR 생성을 선택합니다. 장치 ID(CN), 조직, 부서를 입력하거나 모든 필드를 비워 둡니다. 부서는 인증서의 조직 단위(OU)에 해당합니다.
3. 인증서 서명 요청 생성을 선택하고 전체 CSR을 CA 관리자에게 보냅니다.

영문자와 숫자로 구성된 짧고 안정적인 디바이스 ID를 사용하세요. 양식 필드는 최대 63 UTF-8 바이트를 허용합니다. 한자는 여러 바이트를 사용합니다. 길이 오류가 나타나면 필드를 줄이세요.

**발행 전 액세스 이름 확인:** 사용자 정의 필드가 있는 경우 이 양식은 SAN(주체 대체 이름) 목록을 생성하지 않습니다. 모든 필드가 비어 있으면 장치 ID는 `TIANSHAN-DEVICE-001` 로 고정됩니다. 가능한 경우 현재 IP만 추가됩니다. DNS 이름이 추가되지 않습니다. CA 관리자에게 실제 접속 IP나 DNS 이름을 포함시키고 통제된 발급 과정을 통해 인증 목적을 확인하도록 하세요. 이 양식에서는 SAN을 편집할 수 없습니다.

CSR은 단지 요청일 뿐입니다. 개인 키가 포함되어 있지 않으며 인증서를 설치하지 않습니다. 발급 전 공개키, 주체, 접속명을 확인하세요.

### 5.4 장치 인증서 설치

1. 현재 장치 개인 키와 일치하는 PEM 인증서를 얻습니다. PEM은 BEGIN/END 경계 표시가 있는 텍스트입니다.
2. 인증서 설치를 선택하고 전체 텍스트를 붙여넣은 다음 설치를 선택합니다.
3. 저장된 결과, 주체, 발급자, 유효성을 확인한 후 실제 HTTPS 상태를 확인합니다.

설치 시 형식과 키 일치를 확인합니다. 클라이언트는 여전히 신뢰, 액세스 주소 및 허용된 용도를 별도로 확인해야 합니다.

인증서 텍스트를 보려면 키 관리의 `https` 행에서 인증서를 선택합니다. 전체 PEM을 검토하거나 복사합니다. 구성 팩 발신자와 공개 인증서를 공유할 수 있습니다. 개인 키를 비밀로 유지하십시오.

**키가 일치하지 않는 경우:** 현재 CSR에 대해 발급된 인증서를 찾습니다. 단지 오류를 지우기 위해 개인 키를 다시 생성하지 마십시오. 결과가 확인되지 않은 경우 새로고침하여 저장된 내용을 확인한 후 재시도 여부를 결정하세요.

### 5.5 클라이언트 CA 체인을 설치하고 테스트합니다.

1. CA 설치를 선택하고 클라이언트 유효성을 검사하는 데 필요한 하나 이상의 PEM CA 인증서를 붙여넣은 다음 설치를 선택합니다. 관리자가 승인한 CA만 설치하십시오.
2. 상태를 확인하세요. HTTPS가 활성화되면 자격 증명과 시간이 준비되면 중지된 서비스가 시작을 시도합니다. 실행 중인 서비스에 새 자료를 적용해야 하는 경우 지침에 따라 다시 시작하세요.
3. 목적과 역할이 올바른 신뢰할 수 있는 클라이언트 인증서를 사용하여 관리자가 적절한 테스트 엔드포인트에 액세스하도록 하세요.
4. 신뢰할 수 없는 인증서 또는 인증서 없음을 사용하여 반복하고 거부를 확인합니다.

**결과 확인:** 의도한 인증서로 HTTPS가 실행 중인지 확인하세요. 「사용 중인 인증서 SHA-256」이 표시되면 비교하세요. 신뢰하는 클라이언트라도 역할에 허용된 주소에만 접근해야 합니다. 실제 장치에서 허용할 연결과 거부할 연결을 각각 확인하세요.

### 5.6 자격 증명 갱신, 교체 또는 삭제

**인증서 갱신:** 유출되지 않은 키를 재사용해 새 인증서를 요청하고, 설치한 뒤 안내에 따라 적용하고 테스트하세요. Config Pack은 받는 장치의 인증서 지문과 연결됩니다. 개인 키가 같아도 인증서를 바꾼 뒤 이전 패키지를 다시 읽으면 거부될 수 있습니다. 먼저 새 패키지를 준비하세요.

**개인 키 교체:** 이전 CSR과 인증서는 새 키와 맞지 않게 됩니다. 이전 키에 의존하는 패키지는 복구하지 못할 수 있습니다. 키가 노출됐다면 CA 관리자에게 인증서 폐기도 요청하세요. 새 키를 만드는 것만으로는 폐기되지 않습니다.

**모든 자격 증명 삭제:** 먼저 HTTP 관리 액세스가 작동하는지 확인하고 여전히 필요한 패키지를 준비하세요. 자격 증명 삭제는 장치 키, 장치 인증서 및 클라이언트 CA 체인을 함께 제거합니다. 공개 인증서 백업은 개인 키를 복구할 수 없습니다.

삭제 후 새로고침하여 자료가 누락되었는지 확인하세요. 실행 중인 HTTPS 서비스에는 여전히 이전 자격 증명이 남아 있을 수 있습니다. 저장된 데이터를 삭제하는 것은 즉시 취소되는 것이 아닙니다. 지시에 따라 다시 시작한 다음 이전 자격 증명이 더 이상 사용되지 않는지 확인합니다. 서비스를 복원하려면 키, 기기 인증서, CA 체인을 다시 준비한 후 테스트하세요.

## 6. 일반적인 구성 팩 제한 사항 이해

구성 팩은 암호화되고 서명된 `.tscfg` 파일입니다. 구성 팩 섹션의 일반 제어는 섹션 4.5의 호스트 가져오기와 다릅니다. 전용 호스트, 명령, 소스, 템플릿 또는 규칙 가져오기를 판단하기 위해 일반 제어 동작을 사용하지 마십시오.

### 6.1 컨트롤의 기능

| 액션 | 현재 결과 |
|---|---|
| 수출 장치 인증서 | 발신자가 이 장치에 대한 패키지를 만들 수 있도록 공용 인증서를 공유합니다. 개인 키를 내보내지 않습니다. |
| 확인만 가능 | 포함된 인증서와 비교하여 구조와 서명을 확인합니다. 서명자 신뢰 또는 수신자 일치를 설정하지 않습니다. |
| 일반 대화상자에서 선택 또는 붙여넣기 후 가져오기 | 이 진입점은 현재 가져오기를 완료할 수 없습니다. |
| 패키지 목록에서 가져오기 | 구성을 복사, 암호 해독 또는 적용하지 않고 기존 장치 파일을 확인합니다. |
| 적용 | 설정을 작성하지 않고 구성 카테고리를 해독하고 나열합니다. 여전히 성공을 보고할 수 있습니다. |
| Developer 장치에서 Config Pack 내보내기 | 패키지를 생성하여 SD 카드에 저장한 다음 성공 후 다운로드를 제공합니다. |

> 일반 Config Pack의 「적용」을 여러 장치의 일괄 설정, 재해 복구, 설정 반영 확인에 사용하지 마세요. 성공으로 표시돼도 해당 기능 페이지에서 설정하고 결과를 확인하세요.

### 6.2 소스와 수신자를 확인하세요.

일반 확인만은 신뢰할 수 있는 기관에서 발급한 것인지 확인하지 않고 패키지에 포함된 서명자 인증서를 사용합니다. 서명은 암호화된 콘텐츠를 보호합니다. 표시된 모든 필드를 신뢰할 수 있게 만드는 것은 아닙니다. 공식 라벨, 패키지 이름 또는 대상 이름은 소스 확인을 대체할 수 없습니다.

자산 기록 또는 독립적이고 신뢰할 수 있는 채널을 사용하여 서명자 인증서 지문, 수신 장치 인증서 및 목적을 확인합니다. 동일한 메시지에 수신된 인증서와 지문은 독립적인 검사가 아닙니다. 출처, 대상, 목적이 불분명할 경우 중지하세요.

### 6.3 장치 인증서 공유 및 패키지 검사

**이 장치의 인증서 제공:** 장치 인증서 내보내기를 선택하고 전체 PEM과 표시된 지문을 복사합니다. 공개 인증서를 보낸 사람에게 보낸 다음 신뢰할 수 있는 다른 채널을 통해 지문을 확인하세요.

**수신된 패키지 검사:** 구성 팩 가져오기를 열고 파일을 선택하거나 붙여넣은 다음 확인만을 선택합니다. 서명 정보를 검토하고 출처를 확인하세요. 이는 설정을 적용하거나 이 장치가 수신자임을 증명하지 않습니다.

검증을 통과한 후에도 일반 가져오기 및 적용을 사용하여 장치를 구성할 수 없습니다. SSH 호스트 패키지의 경우 호스트 가져오기를 사용하고 기타 설정은 관련 페이지에서 지원되는 컨트롤을 사용하세요.

### 6.4 개발자 장치에서 일반 구성 팩 내보내기

1. SD 카드에 유효한 JSON 구성 파일을 준비하고 검증된 대상 장치 인증서를 획득하세요.
2. 구성 팩 내보내기를 선택하고 파일을 선택합니다. 필요한 모든 파일이 로드되었는지 확인하세요. 필수 콘텐츠를 그대로 두지 말고 읽기 오류를 해결하세요.
3. 이름과 설명을 입력하고 수신자 인증서를 붙여넣은 후 패키지를 생성합니다.
4. 성공 메시지와 장치 저장 경로를 확인한 후 다운로드를 선택하세요. 브라우저가 `.tscfg` 파일을 저장했는지 확인합니다.

저장 위치는 `/sdcard/output_config/`입니다. 장치 저장에 실패하면 오류가 표시되고 새 패키지는 다운로드할 수 없습니다. 이전 결과를 이번 작업의 성공으로 착각하지 마세요. SD 카드와 저장 결과를 확인한 뒤 다시 만들지 결정하세요.

내보내기는 원본 설정을 바꾸지 않습니다. 대상 장치가 잘못됐거나 받는 장치의 인증서를 교체했다면 패키지를 다시 만드세요. 내보내기 성공이 대상 장치의 일반 「적용」 기능 사용을 보장하지는 않습니다.

## 7. 문제 해결 및 사고 대응

### 7.1 일반적인 문제

| 증상 | 수행할 작업 |
|---|---|
| 계정 보안이 누락되었습니다 | root에만 표시됩니다. |
| 인증 또는 권한이 거부되었습니다. | 계정과 필요한 장치 ID를 확인하세요. 반복적인 클릭은 요구사항을 우회할 수 없습니다. |
| 생성 또는 배포가 확인되지 않았습니다. | 다시 제출하기 전에 로컬 기록과 원격 결과를 확인하세요. |
| 목록을 읽을 수 없습니다. | 연결을 복원하고 새로 고칩니다. 읽기 실패는 목록이 비어 있음을 의미하지 않습니다. |
| 호스트 지문이 변경됩니다. | 취소하고 신뢰할 수 있는 채널을 통해 확인하세요. 섹션 4.3 참조 |
| 로컬 호스트는 취소 후에도 유지됩니다. | 원격 해지와 로컬 삭제를 별도로 확인하세요. 섹션 3.5 참조 |
| 액세스가 계속 작동합니다. | 원격 공개 키를 별도로 취소합니다. 로컬 제거는 액세스 권한을 취소하지 않습니다. |
| 삭제 확인 또는 패키지 미리보기가 만료되었습니다. | 이전 미리보기가 아닌 새로운 결과를 다시 확인하고 결정하세요. |
| 인증서가 저장되었지만 HTTPS가 중지되었습니다. | 먼저 펌웨어가 HTTPS를 활성화하는지 확인한 다음 시간, 자격 증명 및 시작 메시지를 확인하세요. |
| 클라이언트가 인증서를 거부합니다. | 클라이언트 신뢰도, 액세스 이름, 허용된 용도, 유효성을 확인하세요. |
| 일반 적용이 성공했지만 설정이 변경되지 않음 | 이 진입점은 아직 설정을 쓰지 않습니다. 관련 기능 페이지를 사용하세요 |

### 7.2 구성 변경 또는 불확실한 결과

**편집기에서 구성이 변경되었다고 말합니다.** 입력 내용이 여전히 창에 있을 수 있지만 초안으로 저장되지는 않았습니다. 필요한 모든 것을 안전한 장소에 복사하고 편집기를 닫았다가 다시 열고 현재 구성을 읽은 다음 다시 편집하십시오. 일반 노트에 비밀번호나 개인 키를 넣지 마세요.

**패키지 미리보기 기한이 지난 경우:** 「패키지 다시 확인」을 선택해 변경 내용을 확인하세요. 인증 정보나 설정이 바뀌면 이전 미리보기는 사용할 수 없습니다.

**삭제 확인 기한이 지난 경우:** 「삭제 영향 검토」를 선택해 현재 어떤 설정에서 사용 중인지 확인하세요. 다른 창의 작업 때문에 결과가 바뀌었을 수 있습니다.

**시간 초과, 연결 끊김 또는 불완전한 응답이 발생하는 경우:** 현재 구성, 키, 인증서 또는 원격 인증을 먼저 검사하세요. 확인이 누락되었다고 해서 작업이 전혀 발생하지 않았다는 의미는 아닙니다. 재시도 여부를 결정하기 전에 확인하세요.

### 7.3 의심되는 키 또는 비밀번호 노출

1. 장치 및 영향을 받는 자료에 대한 접근을 제한하십시오. 조사에 필요한 기록을 보관하십시오.
2. 노출된 SSH 개인 키의 경우 신뢰할 수 있는 연결을 통해 영향을 받는 모든 서버에서 공개 키를 취소합니다. 백업을 확인하고 이전 키가 더 이상 작동하지 않는지 확인하세요.
3. 새 ID로 새 RSA 키를 생성하고 배포합니다. 이를 확인한 다음 이전 키와 내보낸 복사본을 삭제하세요.
4. 노출된 SSH 비밀번호의 경우 신뢰할 수 있는 관리 연결을 통해 비밀번호를 변경하고 로그인 기록을 검토하세요.
5. 노출된 장치 인증서 키의 경우 섹션 5.6에 설명된 대로 자격 증명을 교체합니다. 해지 및 이전 패키지에 대해서는 CA 관리자와 협력하세요.

로컬 호스트 목록에는 액세스 권한을 부여한 모든 서버가 포함되지 않을 수도 있습니다. 서버 및 자산 기록도 확인하세요. 로그를 공유하기 전에 로그에 비밀번호, 키 또는 기타 민감한 정보가 있는지 검토하세요.

### 7.4 현재 작동 한계

1장의 HTTP 및 액세스 제한 사항, 3장의 초기 배포 신뢰, 6장의 일반 구성 팩 제한 사항을 설명합니다. Hidden은 액세스 제어 메커니즘이 아닙니다.

확인한 빌드 설정에서는 NVS 암호화, Flash 암호화, Secure Boot가 켜져 있지 않습니다. 저장된 키가 암호화나 보안 부팅으로 보호된다고 판단할 근거가 되지 않습니다. 실제 펌웨어와 하드웨어의 보안 설정은 따로 확인해야 합니다. 이 제한을 받아들이기 어렵다면 보안 담당자에게 격리나 수정을 요청하세요.

## 8. 범위 및 용어집

### 8.1 이 판의 기초

이 가이드에서는 TianshanOS 0.6.4를 다룹니다. 해당 지침은 2026년 11월 3일에 검토된 업스트림 코드와 중국어 및 영어 인터페이스를 따릅니다. 검토된 구현을 사용하여 기능을 판단합니다. 버전 번호만으로는 충분하지 않습니다.

이후 버전에서도 이 안내를 참고할 수 있는 부분이 있습니다. 화면, 단계, 결과가 다르면 실제 화면과 업데이트 설명을 확인하세요. 문서 확인만으로 실제 장치의 SSH 접근, 서버의 공개 키 등록, HTTPS 연결, 재시작, 복구 검증을 대신할 수 없습니다.

### 8.2 이 가이드에 사용된 용어

- **공개 키/개인 키:** 액세스 권한을 부여하는 당사자와 공개 키를 공유합니다. 개인 키를 비밀로 유지하십시오. 로그인에서는 일치하는 쌍을 사용합니다.
- **지문:** 서버 또는 인증서 ID를 비교하는 데 사용되는 다이제스트입니다. 비교하기 전에 다양한 디스플레이 형식을 변환하세요.
- **CSR / CA:** 인증서 서명 요청 및 인증 기관 또는 해당 인증서.
- **CN / OU:** 인증서의 이름 및 조직 단위입니다. 양식의 부서는 OU에 해당합니다.
- **SAN:** 인증서에 포함된 DNS 이름 또는 IP 주소입니다.
- **PEM:** BEGIN/END 마커가 있는 인증서, 요청 또는 키 텍스트입니다.
- **mTLS:** 양 당사자가 인증서를 제시하는 인증입니다.
- **NVS:** 장치 설정 및 키를 위한 내부 저장 영역입니다. 그 이름은 암호화를 의미하지 않습니다.
