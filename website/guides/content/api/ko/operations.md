# 연동 시스템 운영

## 로그인 상태 관리

클라이언트 프로세스마다 세션 하나를 유지하고 요청에 재사용하세요. expires_in을 기준으로 갱신 시점을 정하고, 매번 조회할 때가 아니라 인증 실패가 확인되었을 때 다시 로그인하세요. 스크립트와 브라우저가 공유하는 세션 슬롯은 8개입니다. 슬롯이 가득 차면 새 로그인이 같은 계정의 이전 세션을 무효화할 수 있습니다.

이 빌드의 일반 세션은 86400초 후에 만료됩니다. 재시작, 로그아웃, 비밀번호 변경, 세션 취소 후에는 다시 인증해야 합니다. 토큰은 인증 정보로 취급하고 내용을 해석하거나 직접 만들어 사용하지 마세요.

## 폴링과 구독 선택

가끔 상태를 조회할 때는 HTTP를, 대시보드를 계속 갱신할 때는 WebSocket을 사용하세요. 필요한 토픽만 구독하고 화면을 떠날 때 구독을 취소하세요. 화면 갱신 간격은 하드웨어 샘플링 주기나 팬 제어 주기를 바꾸지 않습니다.

연결을 끊은 후 구독을 다시 연결하고 인증하고 복원합니다. 전원 명령, SSH 실행 또는 업데이트를 자동으로 반복하지 마십시오. 연결 해제 중에 누락된 원격 측정 및 로그는 재생이 보장되지 않습니다.

## 개별 작업 추적

스트리밍 SSH는 session_id+boot_id+result_key를 사용합니다. 실행 session_id가 로그인 session_id와 다릅니다. OTA는 비공개 작업 접수 정보 없이 기기 전체 진행 상황을 사용합니다.

SSH 결과 조회에는 전체 작업 접수 정보와 작업을 시작한 로그인 세션이 필요합니다. 취소 시에는 같은 로그인 세션의 실행용 session_id만 사용할 수 있습니다. 접수 정보는 공유하지 마세요. 재시작, 작업 교체, 보관 기간 제한으로 결과를 조회할 수 없으면 원격 상태를 확인하세요. OTA 상태는 개별 전용 작업이 아닌 장치 전체의 공유 상태이므로 시작, 취소, 진행 상황 확인을 하나의 유지보수 프로세스에서 조율하세요.

## 시간 초과 및 재시도

연결과 실행의 제한 시간을 각각 설정하세요. 스캔, 네트워크 진단, 원격 명령, 업데이트는 일반 조회보다 오래 걸릴 수 있습니다. HTTP 요청이 시간 초과되어도 서버 측 작업은 취소되지 않습니다.

조회 재시도 시 동시 요청 수를 제한하고 대기 시간을 점차 늘리세요. 쓰기 결과가 불확실하면 먼저 상태를 확인하세요. 작업이 시작되지 않았고 여전히 필요하다는 점을 확인한 경우에만 다시 실행하세요. toggle보다는 원하는 상태를 명시하는 방식을 사용하세요.

## 구성 변경

쓰기 전에 active_version을 읽고 충돌 후에는 새로 조회하세요. 규칙에는 expected_revision도 필요할 수 있습니다. 필터링된 목록 응답으로 완전한 객체를 덮어쓰지 마세요.

연동에서 사용하는 애플리케이션 버전, 빌드 날짜·시간, 기능을 기록하세요. 버전 문자열이 같아도 수정 내용이 다른 빌드일 수 있습니다. 업그레이드 후에는 메서드, 역할, 필드 및 지원 중단 항목의 변경 사항을 확인하세요.

## 운영 기록

시간, 대상, 작업 종류, 처리 코드, 간단한 사유와 비밀이 아닌 작업 식별자를 기록하세요. 결과 조회용 인증 정보를 보관해야 한다면 접근이 통제된 저장소를 사용하세요. 일반 로그에는 Authorization, 로그인 본문, 개인 키 또는 패키지의 비밀 정보를 기록하지 마세요.
