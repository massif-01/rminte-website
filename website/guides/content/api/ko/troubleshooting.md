# 문제 해결

메서드, 경로, HTTP 상태, 처리 코드, 사유와 작업 접수 정보를 기록하세요. 지원 요청에는 비밀번호, 토큰, 개인 키 또는 전체 Authorization 헤더를 넣지 마세요.

## 연결할 수 없습니다

http://10.10.99.97. 와 같은 현재 HTTP 장치 주소를 사용합니다. 기본 포트는 80이며 명시적으로 작성할 필요가 없습니다. 주소, 네트워크 연결성, WebUI 서비스 상태를 확인하세요.

443에서 작동하는 mTLS 진단 페이지는 장치 관리 API가 실행 중임을 증명하지 않습니다. 공개 system.info 요청이 작동하면 로그인 및 대상 기능을 조사하십시오.

## 인증 또는 권한 실패

HTTP401은 일반적으로 세션이 없거나 유효하지 않거나 만료되었음을 의미하며, 403은 일반적으로 권한이 부족함을 의미합니다. 일부 핸들러는 인증 오류를 HTTP200 내의 API 처리 오류로 보고합니다.

다시 로그인하여 data.level을 검사합니다. 관리자는 ADMIN 구성 및 유지 관리 API를 사용할 수 있습니다. 원시 SSH 실행, 자동화 정의 쓰기 및 선택된 계정 관리에는 여전히 ROOT가 필요합니다. 초기 기본 비밀번호는 rm01입니다. 비밀번호가 변경된 경우 현재 비밀번호를 사용하세요. 비밀번호를 변경하면 영향을 받은 세션이 취소됩니다. 반복적인 동시 재시도를 시작하는 대신 로그인 잠금을 기다리세요.

## 온도 또는 원격 측정 누락

temp.sources의 유효성, 갱신 시각, 경과 시간, 소스를 확인하세요. 변수 기반 온도 입력은 일부 데이터만 오래되었을 수 있으므로 유효한 가중치와 항목 수도 확인하세요. monitor.data는 컴퓨팅 호스트의 모니터링 서비스에 의존합니다. 모니터 연결과 주소 설정을 확인하세요. 하드웨어의 전원이 켜졌다고 해서 원격 측정 데이터가 도착했다고 판단하지 마세요.

## 승인되었지만 완료되지 않음

작업 접수 정보 또는 실행 기록을 보관하고 조회하세요. SSH는 최종 상태, 종료 코드, 출력의 완전성을 확인해야 합니다. 관리형 서비스는 검증된 상태를, OTA는 장치 전체 진행 정보와 파티션 상태 및 재시작 후 실행 버전을 확인해야 합니다. started, cancel_requested 또는 과거 기록만으로는 충분하지 않습니다.

## 구성이 변경되었습니다.

configuration_changed 또는 버전 충돌이 발생하면 현재 상태와 해당 객체를 다시 읽으세요. 새 버전을 제출하기 전에 저장하지 않은 입력을 비교하고 병합하세요. 버전 토큰만 바꾼 채 이전 삭제·가져오기·덮어쓰기 요청을 그대로 반복하지 마세요.

## 저장 실패 또는 결과 알 수 없음

applied, persisted, saved, uncertain, result_unknown과 reason을 확인하세요. 저장에 실패해도 실행 중인 상태는 이미 변경되었을 수 있습니다. 현재 상태를 다시 읽고, 필요에 따라 저장된 시작 설정이나 백업도 확인하세요. 네트워크 오류가 발생했다고 해서 요청의 영향이 없었다고 판단해서는 안 됩니다.

## SSH 지문이 변경되었습니다.

자동 재시도를 중지하고 서버 관리자로부터 현재 지문을 얻습니다. 재설치, 교체 또는 주소 재할당을 확인하세요. 문서화된 확인 필드는 확인 후에만 사용하십시오. 동일한 주소가 동일한 호스트를 보장하지는 않습니다.

## 통화 중이거나 용량이 부족함

동시성을 줄이고 세션을 재사용하며 사용하지 않는 구독 또는 터미널을 닫습니다. 활성 작업을 검사합니다. 클라이언트가 계속 재시도하므로 작업이 무기한 대기할 수 없습니다. 자신의 작업이 중지될 때까지 기다리세요. 다른 연결의 작업을 이어받지 마십시오.

## 업로드 또는 업데이트 실패

역할, 요청 전체가 전달되었는지 여부, 경로, SD 상태, 여유 용량, 대상 파티션 크기, 하드웨어·파티션 구성에 맞는 완전한 이미지를 확인하세요. 업로드 성공은 패키지 검증이나 설치 성공을 뜻하지 않습니다. SSH는 보관한 작업 접수 정보로 결과를 조회하세요. OTA는 재시도, 롤백 또는 복구 자료 삭제 전에 장치 전체 진행 정보와 파티션 상태를 확인하세요.
