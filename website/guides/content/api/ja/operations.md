# 連携システムの継続運用

## ログイン状態の管理

クライアントプロセスごとに一つのセッションを保持し、リクエストに再利用します。expires_in に基づいて更新を予定し、ポーリングのたびにログインするのではなく、認証の失敗が確認された場合に再ログインしてください。セッションの利用枠はスクリプトとブラウザーで共有され、合計 8 個です。満杯の場合、新たなログインにより同じアカウントの古いセッションが無効になることがあります。

このビルドの通常セッションは 86400 秒で期限切れになります。再起動、ログアウト、パスワードの変更、権限の取り消し後は再認証が必要です。トークンは内容を解析したり自分で生成したりせず、受け取った認証情報として扱ってください。

## ポーリングと購読の使い分け

ときどき状態を読む場合は HTTP、ダッシュボードに継続して表示する場合は WebSocket を使用します。必要なトピックだけを購読し、画面を離れるときは購読を解除してください。表示の更新間隔を変更しても、ハードウェアの測定周期やファンの制御周期は変わりません。

切断後は再接続し、認証と購読をやり直します。電源操作、SSH コマンド、更新処理を自動的に再実行しないでください。切断中に取り逃したテレメトリやログが後から再送されるとは限りません。

## 個別の操作を追跡する

ストリーミング SSH は session_id+boot_id+result_key を使用します。実行用の session_id はログイン用の session_id とは別のものです。OTA は個別の操作受付情報を使わず、機器全体の進捗を使用します。

SSH の実行結果を照会するには、操作受付情報一式と、実行を開始したログインセッションが必要です。キャンセルには、同じログインセッションから取得した実行用 session_id だけを使用できる場合があります。操作受付情報を他者と共有しないでください。再起動、実行の置き換え、保持期間の制限により結果を取得できなくなった場合は、リモート側の状態を確認します。OTA の状態は機器全体で共有され、個別の専用タスクではないため、開始、キャンセル、進捗の確認を一つの保守プロセスで調整してください。

## タイムアウトと再試行

接続と実行のタイムアウトを別々に設定します。スキャン、ネットワーク診断、リモートコマンド、更新は、通常の読み取りより時間がかかる場合があります。HTTP がタイムアウトしても、サーバー側の処理はキャンセルされません。

照会を再試行する際は同時実行数を制限し、待機時間を段階的に延ばします。書き込み結果が不明な場合は、まず状態を確認してください。処理が開始されておらず、なお必要だと確認できた場合に限って再実行します。toggle よりも、目的の状態を明示する操作を選びます。

## 設定の変更

書き込み前に active_version を読み取り、競合が起きた場合は読み直します。ルールでは expected_revision が必要な場合もあります。フィルタリングされた一覧の応答を使って、完全なオブジェクトを上書きしないでください。

連携システムが使用するアプリケーションのバージョン、ビルド日時、機能を記録します。バージョン文字列が同じでも、修正内容の異なるビルドである場合があります。アップグレード後は、メソッド、ロール、フィールド、廃止予定の機能に変更がないか確認してください。

## 運用記録

日時、対象、操作の種類、処理コード、簡潔な理由、秘密情報ではない操作識別子を記録します。結果照会用の認証情報を保存する必要がある場合は、アクセスを管理した保存先を使用してください。通常のログに Authorization、ログインのリクエスト本文、秘密鍵、設定パッケージ内の秘密情報を記録しないでください。
