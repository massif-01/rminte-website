# TianShanOS セキュリティページ操作ガイド

機器のパスワード変更、SSH 接続の管理、証明書の設定を説明します。初めて使う方は第 1・2 章からお読みください。証明書と設定パッケージは、機器のセキュリティ担当管理者が扱ってください。

対象：2026-09-07 に確認した作業ツリーのコード。基準コミットは `d6ed947` です。記述はコード調査に基づき、お使いの実機での動作確認を意味しません。各節の「結果の確認」は実際の環境で行う必要があります。以下では説明に日本語を使い、操作箇所を特定できるよう機器の中国語ラベルを併記します。

> まずネットワークの安全性を確認してください。現在の完全な管理画面は HTTP を使い、多くの API に共通のログイン・権限チェックがありません。管理された隔離ネットワークだけで操作し、機器をインターネットやゲストネットワークに直接公開しないでください。HTTPS 証明書を入れても、この管理画面は自動的に HTTPS には切り替わりません。

## 1. 始める前の確認

### 1.1 目的の機能を探す

| 目的 | 操作場所 |
| --- | --- |
| root/admin のパスワード変更 | アカウントセキュリティ。第 2 章 |
| 鍵でサーバーに接続 | 鍵管理・登録済みホスト。第 3 章 |
| 鍵のコピー、サーバーの識別情報変更への対応 | 鍵管理・既知ホストのフィンガープリント。第 4 章 |
| 機器証明書と相互証明書認証の設定 | HTTPS 証明書。第 5 章 |
| 暗号化設定パッケージの受け渡し | Config Pack。第 6 章。汎用の適用機能は未完成 |

### 1.2 アカウントと機器の識別情報は別物

- admin：セキュリティページを開き、鍵、ホスト、証明書、設定パッケージの機能を表示できます。ただしアカウントセキュリティ（「账号安全」）は表示されません。
- root：root/admin のパスワード設定と admin パスワードのリセットもできます。これらの API はバックエンドで root を確認します。
- Developer 機器：機器証明書の OU 属性で識別され、ログインアカウントとは異なります。現在、設定パッケージと SSH ホスト設定をエクスポートできるのはこの機器だけです。root でログインしても機器の識別は変わりません。

上記のパスワード管理など独自に認証を行う API を除き、画面にログインが必要であることだけでは API の直接呼び出しを防げません。ネットワーク隔離が現在の利用条件です。

### 1.3 操作の準備

1. アドレスバーの IP が対象機器であり、パソコンも信頼できる管理ネットワークにあることを確認します。
2. サーバー管理者に SSH アドレス、ポート、ユーザー名を確認します。
3. 画面から公開鍵を配備したり認可を取り消したりするには、対象アカウントのパスワードが必要で、そのアカウントでパスワードログインが許可されている必要があります。障害調査のためにサーバーの制限を緩めたままにしないでください。
4. 鍵の削除、認可の取り消し、証明書交換の前に、サーバーコンソール、別の管理者鍵、機器の HTTP 管理画面など、代替経路が使えることを確認します。

## 2. 機器のログインパスワードを変更する

ここで変えるのは TianShanOS のログインパスワードです。リモートサーバーの SSH パスワードではありません。

### 2.1 初回ログイン後の変更通知

パスワード変更済みと記録されていないアカウントでは、ログイン後に変更通知が出ます。他で使っていない長いパスワードを設定してください。「稍后修改」（後で変更）を選んで初期パスワードを使い続けないでください。

この通知は、いつでも開けるアカウント設定ではありません。変更済みの admin が再度変更する場合は、root がセキュリティページで設定できます。

### 2.2 root によるパスワード設定

1. root でログインし、セキュリティ（「安全」）を開きます。
2. アカウントセキュリティ（「账号安全」）でroot パスワードを設定（「设置 root 密码」）またはadmin パスワードを設定（「设置 admin 密码」）を選択します。
3. 同じ新規パスワードを 2 回入力して送信します。入力範囲は 4-64 文字ですが、4 文字は技術的な下限であり、推奨する強度ではありません。

結果の確認：プライベートウィンドウで新しいパスワードのログインを確認してから元のセッションを閉じます。変更しても既存セッションは自動終了しません。

ログインに失敗したら、アカウントと IP を確認します。5 回連続で失敗すると約 5 分間ロックされます。繰り返し推測しないでください。

### 2.3 admin パスワードのリセット

root はアカウントセキュリティで admin を初期パスワード `rm01` に戻し、ログインロックを解除できます。直後に新しいセッションで admin にログインし、新しいパスワードを設定してください。

リセットは一時的な復旧手段です。初期パスワードを常用しないでください。また、パスワード変更が既存セッションをすべて無効にするわけではありません。

## 3. SSH 鍵でサーバーに接続する

初回は RSA 鍵の生成 → 公開鍵の配備 → 接続テスト → サーバーの識別確認の順で進めます。廃止時はリモート側の認可を取り消し、ログインできないことを確認してからローカル鍵を削除します。

### 3.1 鍵を生成する

1. 鍵管理（「密钥管理」）で新しい鍵を生成（「生成新密钥」）を選択します。
2. 既存一覧を確認し、`backup01` など未使用の鍵 ID を入力します。現在は重複 ID を拒否しないため、既存 ID を使うと元の鍵を上書きするおそれがあります。
3. RSA 2048 または RSA 4096 を選びます。既定は RSA 2048 です。ECDSA も表示されますが、現在の SSH 公開鍵認証では使えません。
4. 必要なら備考と別名を入力します。秘密鍵のバックアップ・移行が必要な場合だけ秘密鍵のエクスポートを許可（「允许导出私钥」）を選択してください。生成後にこの属性を変える画面はありません。
5. 生成（「生成」）を選び、完了後に一覧を更新します。

結果の確認：正しい ID と RSA の種類を確認し、公開鍵（「公钥」）で全文が `ssh-rsa` から始まることを確かめます。

注意：一覧の上限は 8 個です。満杯なら生成を続けず、取り消し手順に従って古い鍵を整理してください。保存と一覧登録は一体として完了するとは限らないため、成功通知後も一覧を確認します。鍵 ID を非表示（「隐藏密钥 ID」）は、API から実際の ID が読まれることを防ぎません。

### 3.2 公開鍵を配備する

配備はリモートアカウントの `~/.ssh/authorized_keys` に公開鍵を追加し、対応する秘密鍵でのログインを可能にするための処理です。サーバーのパスワードは変更しません。

1. 新しい鍵の行で配備（「部署」）を選びます。
2. サーバーアドレス、ユーザー名、SSH ポート、そのアカウントのパスワードを入力します。
3. 確認して配備を開始（「开始部署」）を選びます。
4. 完了後、登録済みホスト（「已部署主机」）の記録を確認し、次節のテストを行います。

現在の処理はパスワードで SSH 認証した後にホストのフィンガープリントを確認し、初めてのホストを自動で信頼します。サーバーの識別を確認してからパスワードを送る保証はありません。初回接続は管理されたネットワークで行ってください。後でフィンガープリントを照合しても、すでにパスワードを送信したリスクは消えません。

成功表示後に記録がない、またはテストが失敗した場合は、すぐに再配備しないでください。公開鍵の書き込みは済み、鍵ログインの再確認やローカル保存だけが失敗した可能性があります。別の管理経路から `authorized_keys` を調べてください。繰り返すと重複行が追加される場合があります。

### 3.3 接続をテストして結果を確認する

1. 登録済みホスト（「已部署主机」）でアドレス、ポート、ユーザー名、鍵 ID を確認します。
2. テスト（「测试」）を選びます。機器は固定コマンド echo "TianshanOS SSH Test OK" の実行を試みます。
3. 初回接続後、第 4.3 節に従って保存されたホストフィンガープリントを照合します。

成功表示の意味：画面は API 要求の成否だけを見ており、リモートコマンドの終了コードと出力内容は確認しません。基本的な接続確認であり、完全な受け入れ試験でも sudo や業務コマンドの動作証明でもありません。重要な用途では実際のタスクで出力、終了コード、権限を確認してください。

失敗したらネットワーク、SSH サービス、アカウント、リモート認可を確認します。フィンガープリント変更やサーバーの身元不明が関わる場合は再試行を止め、第 4.3 節に従ってください。

### 3.4 リモート認可を取り消してからローカル鍵を削除する

1. 別のサーバー管理経路が使え、機器の元の鍵が残っていることを確認します。
2. 登録済みホスト（「已部署主机」）の対象行で認可を取り消す（「撤销」）を選び、サーバーパスワードを入力して認可を取り消して除去（「撤销并移除」）を確認します。鍵の行から対象情報を入力して開始することもできます。
3. 結果を確認し、信頼できるサーバー管理経路から `authorized_keys` を調べ、対象公開鍵と重複行が消えていることを確かめます。
4. 古い鍵でログインできないことを確認します。`authorized_keys.bak` が残るため、古い認可を復元しないようサーバーのバックアップ方針に沿って扱います。
5. ローカル一覧を更新します。画面は記録の削除を試みますが結果を確認しないため、必要なら手動で除去（「移除」）します。
6. すべての対象サーバーを処理してから、機器の古い鍵と不要な秘密鍵のコピーを削除します。

公開鍵が見つかりません（「未找到公钥」）と表示されたら、サーバー側で対象アカウントが正しく、公開鍵が本当にないことを確認してからローカル記録だけを削除します。

失敗した場合やサーバーの身元が疑わしい場合は、ローカル鍵を残し、信頼できるコンソールや別の管理経路で処理してください。疑わしいサーバーにパスワードを送り続けないでください。

## 4. 鍵・ホスト・フィンガープリントの管理

### 4.1 公開鍵のコピーと秘密鍵のエクスポート

公開鍵：公開鍵（「公钥」）で完全な 1 行をコピーし、サーバー管理者に渡します。公開鍵は秘密情報ではありません。誤送信だけで秘密鍵が漏れたことにはならず、直ちに鍵交換が必要になるわけでもありません。管理者が認可一覧に追加して初めてアクセス権が生じます。

秘密鍵：生成時にエクスポートを許可した鍵だけが秘密鍵（「私钥」）から取り出せます。信頼できるパソコンと隔離ネットワークで操作し、管理された鍵保管庫に保存して、クリップボードやダウンロード先の一時コピーを消してください。チャット、問い合わせ票、ログに貼り付けないでください。

コピーできない場合：HTTP ではブラウザーのクリップボード API が使えないことがあります。表示テキストを手動で選択してコピーし、先頭・末尾・全文を確認してください。コピーのためにブラウザーの保護を緩めないでください。

### 4.2 取り消し・除去・削除の違い

| 操作 | 変更内容 |
| --- | --- |
| 公開鍵の取り消し | サーバーの認可削除を試みます。リモートのパスワードが必要です |
| ホストの除去 | 機器内の接続記録だけを消します。サーバーの認可は残ります |
| 鍵の削除 | 機器内の鍵を消します。サーバーには接続せず、認可も取り消しません |
| 既知ホストフィンガープリントの削除 | 保存したサーバーの識別記録を消します。接続記録やサーバー認可は残ります |

登録済みホスト（「已部署主机」）はローカル一覧で、サーバーを継続照会しません。空でもリモート認可が消えた証拠にはならず、記録があっても現在ログインできるとは限りません。

### 4.3 SSH サーバーのフィンガープリントを照合する

フィンガープリントは接続先サーバーを識別するための値です。現在の画面は SHA-256 ダイジェストを 64 桁の 16 進数で保存しますが、一般的な OpenSSH は `SHA256:base64` を出力します。管理者に形式をそろえてもらってください。文字列をそのまま比較することはできません。

初回接続後：既知ホストのフィンガープリント（「已知主机指纹」）の表示（「查看」）で全文を開き、サーバーコンソール、資産管理システムなど別の信頼できる経路の値と照合します。表には先頭 32 桁しか表示されないため、それだけでは不十分です。

不一致の場合：接続を止め、隔離して調査します。SSH パスワードを入力済みなら漏えいの可能性として扱い、信頼できる経路から変更し、ログインログと不正な公開鍵を調べます。疑わしい接続で画面の取り消し処理を行わないでください。

保存済みのフィンガープリントが変わった場合：

1. 再試行を止め、旧記録をすぐに消さないでください。
2. 信頼できるコンソールで新しいフィンガープリント、IP、ポート、資産の識別情報、保守記録を照合します。
3. 再インストールや正規の鍵交換だと確認できてから旧フィンガープリントを削除します。
4. 管理されたネットワークで再接続し、新しい記録をもう一度照合します。

専用の比較ダイアログが出ず、一般的な接続エラーだけが表示される場合があります。

SD カードの管理：フィンガープリントは機器ストレージに保存され、SD カードにも平文 JSON で同期されます。起動時に SD のフィンガープリント設定があれば、それを優先して対応する NVS 記録を置き換えます。署名による保護はありません。信頼できない人に SD カードを変更させないでください。

### 4.4 SSH ホスト設定のインポート・エクスポート

これは専用の `.tscfg` 手順で、第 6 章の未完成な汎用適用とは別です。アドレス、ポート、ユーザー、認証種別、鍵 ID を保存します。SSH パスワードや秘密鍵は含まず、リモート権限も付与しません。

エクスポート：Developer 機器でホスト行のエクスポート（「导出」）を選びます。別機器向けなら対象の機器証明書を入力・照合してからダウンロードします。通常機器はボタンが見えてもバックエンドが拒否します。

インポート：

1. 本機器向けのパッケージで、SD カードが書き込み可能であることを確認し、信頼できる経路で出所を照合します。
2. 参照される正しい鍵が本機器にあることを確認します。ID の一致だけでは足りず、鍵自体がサーバーの認可と対応している必要があります。
3. ホスト設定のインポートを開き、ファイルとプレビューを確認します。同名設定を置き換える場合だけ上書きを選択します。
4. 確認後、案内に従って再起動します。インポートは SD に保存するだけで、読み込みと復号は再起動時に試みます。
5. 読み込まれたアドレス、ユーザー、ポート、鍵 ID を確認して接続テストを行います。

プレビュー成功は利用可能の証明ではありません。署名者の信頼性も受信機器のフィンガープリントも確認しておらず、対象の確認は再起動時です。誤った記録は削除し、SD の該当パッケージも除いて再読込を防いでください。機器証明書の交換前には第 5.5 節もお読みください。

## 5. HTTPS 証明書と mTLS の設定

証明書管理者向けの章です。現在の 443 サービスは健全性・識別・権限テスト API のみを提供し、完全な管理画面は提供しません。既定の起動には機器秘密鍵、機器証明書、クライアント CA チェーンがすべて必要です。

### 5.1 証明書の役割を区別する

- 機器秘密鍵・証明書：接続してくるクライアントに機器の身元を示します。
- クライアント証明書・秘密鍵：パソコンやサービスが持ち、機器にクライアントの身元を示します。
- 機器に入れる CA チェーン：クライアント証明書を検証します。パソコンやブラウザーが機器証明書を自動で信頼するようになるわけではありません。

双方が証明書を提示する方式が mTLS です。クライアント側でも機器証明書の CA を信頼する設定と、接続名・用途の検証が必要です。

### 5.2 機器秘密鍵と証明書署名要求を生成する

1. HTTPS 証明書（「HTTPS 证书」）で鍵ペアを生成（「生成密钥对」）を選びます。SSH とは別の ECDSA P-256 秘密鍵を生成します。この画面ではエクスポートできません。
2. 既存鍵がある場合は中断し、第 5.5 節で影響を確認します。続けると上書きされます。
3. CSR を生成（「生成 CSR」）で機器 ID（CN）、組織（O）、組織単位（OU）を入力するか、すべて空欄にします。
4. CSR 全文を CA 管理者に渡します。CSR は申請であり、秘密鍵は含まず、証明書の自動インストールも行いません。

発行前の名前確認：項目を指定する経路では SAN を生成しません。全空欄なら CN は `TIANSHAN-DEVICE-001` 固定で、現在の IP が取得できる場合だけその IP の SAN を追加します。DNS SAN はありません。CA 管理者が CSR を調べ、管理された発行手順で実際の IP/DNS を最終証明書の SAN に加えてください。このフォームでは SAN を編集できません。

結果の確認：更新後に秘密鍵の存在を確認します。CA 管理者が CSR を解析し、公開鍵、主体、SAN と、最終証明書に必要なサーバー認証用途（EKU）があることを確認します。

### 5.3 機器証明書をインストールする

1. 現在の機器秘密鍵に対応する PEM 証明書を用意します。
2. 証明書をインストール（「安装证书」）に開始・終了マーカーを含む全文を貼り付けて送信します。
3. 証明書を表示し、主体、発行者、有効期間を確認します。

成功通知が示すのは解析可能で、公開鍵が現在の秘密鍵と一致することだけです。信頼チェーン、SAN、EKU、現在の有効性、主体ポリシーの完全な検証は行いません。

実際のクライアントがチェーン、接続先、用途、有効期間を確認して初めて信頼性を判断できます。鍵不一致なら現在の CSR に対応する証明書を探してください。エラーを消すためだけに秘密鍵を再生成しないでください。

### 5.4 クライアント CA チェーンを入れてテストする

1. CA をインストール（「安装 CA」）に、クライアント証明書を信頼するための PEM CA 証明書を 1 つ以上貼り付けます。
2. HTTP 管理経路を残し、再起動を予定してからテストします。インストール API はストレージのみを更新し、稼働中の 443 サービスを再起動しません。
3. 信頼され、用途とロールが正しいクライアント証明書で対応するテストエンドポイントに接続します。
4. 信頼されない証明書、または証明書なしでも試し、拒否を確認します。

結果の確認：機器が意図した新証明書を使い、信頼できるクライアントも自分のロールに許可された API だけにアクセスでき、信頼されないクライアントは接続できないことを確認します。ハンドシェイクとロールの挙動は実機試験が必要で、インストール通知だけでは確認できません。

### 5.5 証明書の更新と全資格情報の削除

期限切れのみ：漏えいしていない秘密鍵を継続使用して新証明書を申請し、インストール後に再テストできます。ただし設定パッケージは受信側の証明書フィンガープリントに結び付いています。同じ秘密鍵でも新証明書のフィンガープリントが変わると、再初期化や再起動で読む古いパッケージは対象不一致で拒否されます。残す必要のあるパッケージを事前に作り直してください。

秘密鍵交換：古い証明書と CSR は新しい鍵と対応しません。古い証明書が CA によって失効したという意味ではありません。漏えい時は別途失効・事故対応が必要です。古い秘密鍵がなければ、それに依存するパッケージは復旧できない場合があります。

全 PKI 資格情報の削除：資格情報を削除（「删除凭证」）は機器秘密鍵、証明書、クライアント CA チェーンをまとめて消します。HTTP 管理経路と代替パッケージの準備を確認してから実行してください。公開証明書のバックアップでは秘密鍵は復元できません。

削除後にページを更新して未初期化と表示されること、再起動後に 443 が古い資格情報を使わないことを確認します。再有効化には秘密鍵生成、証明書発行、CA チェーンのインストールとテストが必要です。

## 6. Config Pack の利用前に制限を確認する

Config Pack は暗号化・署名された `.tscfg` 設定パッケージです。現在は生成と検査ができますが、汎用の設定適用は未完成です。本番の一括設定、災害復旧、設定反映の証明には使わないでください。

### 6.1 現在の各ボタンの動作

| 操作 | 現在の結果 |
| --- | --- |
| 機器証明書のエクスポート | 送信者が本機器向けパッケージを作るための公開証明書を表示します。秘密鍵は出しません |
| 検証 | 構造と内蔵証明書による暗号文署名を確認します。署名者の信頼性や対象一致は確認しません |
| セキュリティページで選択・貼り付けてインポート | フロントエンドとバックエンドのパラメーターが合わず、完了できません |
| パッケージ一覧からインポート | 既存ファイルを検証するだけで、コピー・復号・適用はしません |
| 適用 | 復号してモジュール名を列挙しますが、設定は書き込みません。成功と表示される場合もあります |
| Developer のエクスポート | ダウンロード可能な暗号化署名パッケージを作り、SD 保存も試みます |

### 6.2 署名有効の表示だけでなく出所を確認する

受信機器はパッケージ内の証明書で署名を確認し、署名者の信頼チェーンを検証していません。署名が保護するのは暗号文で、すべての表示項目が信頼できる認証を受けたとは言えません。公式（「官方」）も出所の証明にはなりません。

インポート・検査前に、資産管理システムや管理者が認める独立経路で署名者の証明書フィンガープリント、対象機器証明書、用途を確認してください。同じメールに添付された証明書とフィンガープリントだけで信頼を判断しないでください。プレビューの対象名もフィンガープリント照合の代わりにはなりません。

### 6.3 機器証明書の提供と受信パッケージの検査

機器証明書の提供：機器証明書をエクスポート（「导出设备证书」）で PEM 全文と表示されたフィンガープリントをコピーし、公開証明書を送信者に渡して、別の信頼できる経路でフィンガープリントを照合します。

受信パッケージの検査：設定パッケージをインポート（「导入配置包」）で `.tscfg` を選ぶか貼り付け、検証（「验证」）を選択します。署名者と出所を確認します。検証は設定を適用せず、本機器向けであることも証明しません。出所不明、対象不一致、用途不明なら中断してください。

検証に通っても現在の汎用インポート・適用に依存しないでください。各機能のページに戻り、対応済みの方法で設定し、実際の結果を確認します。

### 6.4 Developer 機器からエクスポートする

1. SD カードに有効な JSON 設定ファイルを用意し、照合済みの対象機器証明書を入手します。
2. 設定パッケージをエクスポート（「导出配置包」）でファイルを選び、名前と説明を入力し、対象証明書を貼り付けます。
3. 生成後に `.tscfg` をダウンロードします。
4. ブラウザーのファイルと `/sdcard/output_config/` の保存結果を別々に確認します。SD 保存に失敗しても、API がダウンロード用データを返す場合があります。

元の設定は変更されません。対象が誤っている、または受信側証明書が交換された場合は再生成が必要です。受信側の汎用適用は未完成なので、エクスポート成功だけで配布フロー全体が使えるとは判断できません。

## 7. 障害・セキュリティインシデントへの対応

### 7.1 よくある問題

| 症状 | 対処 |
| --- | --- |
| アカウントセキュリティがない | root でログインします。admin には表示されません |
| 鍵生成は成功したが一覧にない | 更新し、上限を確認します。ID の再利用や連続生成は避けます |
| ECDSA の配備が失敗 | 新 ID で RSA を生成します。サーバー制限を繰り返し緩めないでください |
| 配備成功後のテストが失敗 | 別経路で認可を確認し、すぐに再配備しないでください |
| ホスト除去後もログインできる | ローカル記録だけの削除です。リモート公開鍵を別途取り消します |
| フィンガープリント変更・身元不明 | 接続を止め、信頼できるコンソールで確認します。第 4.3 節 |
| 証明書導入後に 443 が使えない | 秘密鍵、機器証明書、クライアント CA を確認し、再起動後に正しいクライアント証明書で試します |
| クライアントが証明書を信頼しない | クライアントの信頼ストア、SAN、EKU、有効期間、チェーンを確認します。機器内 CA はブラウザーの信頼ストアではありません |
| パッケージ適用成功なのに変化なし | 現在はモジュール設定を書き込みません。各機能ページで操作します |

### 7.2 SSH 秘密鍵が漏えいした可能性がある場合

1. 機器とログへのアクセスを制限します。現在のログには秘密鍵の冒頭が含まれる場合があります。
2. 信頼できる経路で各サーバーの認可を取り消し、バックアップを確認して、古い鍵でログインできないことを確かめます。
3. 新 ID で RSA 鍵を生成・配備し、正常動作後に古い鍵とエクスポート済みコピーを削除します。
4. ログインログを調べます。機器の一覧が過去に認可した全サーバーを網羅するとは限りません。

HTTPS 秘密鍵なら第 5.5 節に従って資格情報を交換し、CA 管理者と旧証明書の失効・旧パッケージへの対応を進めます。

### 7.3 現バージョンで残るリスク

前述の HTTP、API 認証、初回ホスト信頼、パッケージ制限に加え、調査したビルド設定では NVS Encryption、Flash Encryption、Secure Boot が無効です。秘密鍵がこれらの保存・起動保護を受けているとは言えません。実機の書き込み設定と eFuse 状態は別途確認が必要です。

許容できない用途ではネットワーク接続を停止し、セキュリティ責任者が隔離策または製品修正を判断してください。操作ガイドの確認手順は、欠けている製品のセキュリティ制御の代わりにはなりません。

## 8. 調査根拠と用語

### 8.1 調査方法

`d6ed947` を基準とする作業ツリーを調べました。画面操作と通知は `components/ts_webui/web/js/app.js`、API は `components/ts_api/src/`、鍵・ホスト保存は `components/ts_security/src/`、証明書・443 サービス・パッケージは順に `components/ts_cert/`、`components/ts_https/`、`components/ts_config_pack/` にあります。

重複鍵 ID、テスト終了コード、取り消し後のローカル削除、証明書フィンガープリントへの結び付け、未完成のインポート・適用を重点確認しました。静的コード調査であり、この変更作業ではリモート接続、機器資格情報の変更、実機セキュリティ試験を行っていません。

### 8.2 用語

- 公開鍵・秘密鍵：公開鍵は認可する側に渡せますが、秘密鍵は秘密に保ちます。サーバーは公開鍵を認可し、機器は対応する秘密鍵でログインします。
- NVS：Flash 内の設定・鍵保存領域です。名称自体は暗号化を意味しません。
- CSR・CA：CSR は証明書署名要求、CA は証明書を発行・検証する認証局またはその証明書です。
- CN・O・OU：証明書主体のコモンネーム、組織、組織単位です。
- SAN・EKU：利用できる接続名・IP と、認証用途をそれぞれ表します。
- PEM：BEGIN/END マーカー付きのテキスト形式で、証明書、CSR、鍵に使います。
- PKI・mTLS：PKI は証明書と信頼の管理基盤、mTLS はクライアントとサーバー双方が証明書を提示する接続方式です。
