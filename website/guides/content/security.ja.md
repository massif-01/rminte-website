# TianShanOS セキュリティ ページ ガイド

対象バージョン：TianshanOS 0.6.4。確認日：2026 年 11 月 3 日。

このガイドを使用して、デバイスのパスワードの変更、SSH サーバーへの接続、サーバー ID の確認、証明書と構成パッケージの管理を行います。初めてセットアップする場合は、第 1 章、第 2 章、および第 3 章から始めてください。証明書の発行と回復については、デバイスまたはサーバーの管理者と協力してください。

> 信頼できる管理ネットワークを使用してください。完全な Web インターフェイスは HTTP を使用します。証明書をインストールしても HTTPS には切り替わりません。一部の証明書操作はサインインしなくても呼び出すことができるため、サインアウトしてもネットワークの分離は置き換えられません。デバイス管理アクセスをパブリック ネットワークに公開しないでください。

## 1. 始める前に

### 1.1 必要なタスクを見つける

1. ブラウザにターゲット デバイスの IP アドレスを入力し、デバイス アカウントでサインインします。
2. ナビゲーションバーで「セキュリティ」を選択します。パスワードを入力したりキーを扱ったりする前に、アドレスを確認してください。
3. 以下の表を使用して、適切なセクションを見つけてください。ルートにはアカウント セキュリティも表示されます。

| タスク | どこへ行くか |
|---|---|
| デバイスの root または admin パスワードを変更します | アカウントのセキュリティ;第2章 |
| SSH キーを使用してサーバーに接続します | キー管理とデプロイされたホスト。第3章 |
| キーのコピー、ホストの編集または削除、またはフィンガープリントの確認 | キー管理、デプロイされたホスト、および既知のホストのフィンガープリント。第4章 |
| デバイス証明書を要求してインストールする | HTTPS 証明書;第5章 |
| 一般的な暗号化された構成パッケージを検査または作成する | 構成パック。最初に第 6 章の制限事項をお読みください |

### 1.2 アカウントとデバイス ID

- **admin** は「セキュリティ」を開き、SSH 鍵、ホスト、画面で提供される証明書機能を管理できます。「アカウントのセキュリティ」は表示されません。
- **root** は、root と admin のパスワード設定、admin のアクセス復旧に加え、root 権限が必要な自動化設定や Web ターミナルを扱えます。ログイン済みの admin も、ホーム画面のサービス操作を使えます。
- **Developer デバイス** は、証明書に開発用の識別情報が記録されたデバイスです。ログインアカウントではありません。暗号化 Config Pack や SSH ホスト設定のエクスポートには、この識別情報が必要です。root でログインしても変更されません。

ログインが必要な操作では、デバイスがアカウントを確認します。一部の照会と証明書操作は、未ログインでも呼び出せます。ボタンが見えるだけでは、アカウントやデバイスの条件を満たしたことにはなりません。権限が拒否されたら、ログイン状態と必要条件を確認してから再試行してください。

### 1.3 操作の準備

1. コンピューターとターゲット デバイスが信頼された管理ネットワーク上にあることを確認してください。
2. SSH アドレス、ポート、アカウント、および完全なホスト フィンガープリントをサーバー管理者に確認してください。
3. ページを通じて公開キーを展開または取り消すには、リモート アカウントのパスワードとパスワード認証が必要です。サーバー管理者は、その後もパスワード認証を有効にしておくかどうかを決定します。
4. アクセスの取り消し、キーの削除、または証明書の置き換えを行う前に、サーバー コンソール、別の管理者キー、デバイスの HTTP インターフェイスなどの別の管理接続が機能していることを確認してください。

## 2. デバイスのパスワードを変更する

これらのコントロールは、TianshanOS のログイン パスワードを変更します。リモート サーバーの SSH パスワードは変更されません。

### 2.1 最初のサインイン後のプロンプト

パスワードが未変更と記録されているアカウントでログインすると、変更を促す画面が表示されます。長く、他で使っていないパスワードを設定してください。「後で変更」は、この画面を閉じるだけです。

このプロンプトは、いつでも再度開くことができるアカウント設定画面ではありません。 admin がすでにパスワードを変更しており、さらに変更する必要がある場合は、root にセキュリティからパスワードを設定するように依頼してください。

### 2.2 パスワードを root として設定します

1. root としてサインインし、「セキュリティ」を開きます。
2. [アカウント セキュリティ] で、root または管理者のパスワード コントロールを見つけます。新しいパスワードとその確認を入力します。
3. [root パスワードの設定] または [管理者パスワードの設定] を選択します。 12 文字以上の一意のパスワードを使用してください。英語の文字、数字、記号を使用すると、長さのカウントの違いを避けることができます。

画面の案内は 4～64 文字ですが、デバイスは UTF-8 のバイト数で確認します。英字、数字、一般的な ASCII 記号は 1 文字が 1 バイト、漢字は通常複数バイトです。4 は受け付ける最小値であり、推奨するパスワードの長さではありません。

**結果を確認してください:** 元のセッションからサインアウトする前に、プライベート ブラウジング ウィンドウで新しいパスワードを使用してサインインします。新しいパスワードを設定しても、既存のセッションは自動的に終了しません。

**ログインできない場合：**アカウントとデバイスのアドレスを確認してください。5 回連続で失敗すると、約 5 分間ロックされます。推測したパスワードを繰り返し入力しないでください。

### 2.3 admin パスワードのリセット

Root は、[admin をデフォルトにリセット] を選択して、パスワードを `rm01` に復元し、ログイン ロックアウトをクリアできます。新しいセッションで admin としてサインインし、直後に一意のパスワードを設定します。

> デフォルトのパスワードは、アクセスを一時的に回復する場合にのみ使用してください。すぐに変更し、不要になったセッションからサインアウトしてください。

### 2.4 root パスワードを忘れた場合

デバイスに合う復旧方法を管理者に確認してください。現在の復旧ファームウェアは新しい設定保存方式だけに対応し、root と admin の両方のパスワードをリセットします。古い復旧ファームウェアを自分で導入しないでください。復旧後は各アカウントに固有のパスワードを設定します。

## 3. SSH キーを使用してサーバーに接続します

初期セットアップでは、RSA キーを作成し、その公開キーを展開し、結果を確認して、接続をテストします。このプロセスの一環としてサーバーのフィンガープリントを確認します。キーを廃止するには、すべてのサーバーでアクセスを取り消し、古いキーが機能しなくなったことを確認してから、ローカル キーを削除します。

### 3.1 キーの作成

1. [キー管理] で、[新しいキーの生成] を選択します。
2. 未使用の鍵 ID を指定します。例は `backup01` です。カンマは使わず、10 文字以内の英字・数字にしてください。上限は UTF-8 で 10 バイトです。漢字 10 文字を入力できるという意味ではありません。
3. RSA 2048 または RSA 4096 を選択します。RSA 2048 がデフォルトです。 ECDSA オプションも表示されますが、現在の SSH ワークフローはそれらをサポートしていません。 SSH には RSA を選択します。
4. 役立つ場合は、コメントまたはエイリアスを追加します。秘密キーをバックアップまたは移行する必要がある場合にのみ、「エクスポート可能」を有効にします。作成後にこのオプションを変更するためのページ コントロールはありません。
5. 必要に応じて「非表示」を設定し、「生成」を選択します。 Hidden は表示に影響します。実際のキー ID またはキーへのアクセスは妨げられません。

**結果を確認します。** ウィンドウが閉じてリストが更新されたら、目的の ID と RSA タイプを見つけます。公開キーを開き、完全なテキストが `ssh-rsa` で始まることを確認します。

**生成を待っている間：**再度送信しないでください。ウィンドウを閉じても、デバイス上の生成処理は取り消されません。

| メッセージまたは状況 | どうすればいいですか |
|---|---|
| IDはすでに使用されています | 別の ID を選択してください。新しいキーを作成しても既存のキーを上書きすることはできません |
| キー数の制限に達しました | SSH 鍵は最大 8 個です。不要な鍵は先に接続先で許可を取り消し、その結果を確認してから削除してください。 |
| ストレージまたはメモリが不足しています | デバイスのリソースの問題を解決します。失敗を成功した作成として扱わないでください |
| キーは生成されましたが、リストを更新できませんでした | 手動で更新してキーを確認してください。再度生成しないでください |
| 鍵の生成結果が未確認 | 待ってから記録を確認してください。同じIDを再送信しないでください |
| クリーンアップが完了しませんでした | キーの作成を一時停止し、管理者にストレージを確認するように依頼します |

同じ ID を持つレコードは、この試行が完了したことを証明するものではありません。結果が不確かな場合は、記録とキーマテリアルを確認してください。

### 3.2 公開キーの展開

デプロイメントにより、公開キーがリモート アカウントの認証ファイル `~/.ssh/authorized_keys` に追加されるため、一致する秘密キーでサインインできるようになります。サーバーのパスワードは変更されません。

1. 目的のキーの行で [デプロイ] を選択します。
2. サーバー アドレス、ユーザー名、SSH ポート、および SSH ログイン パスワードを入力します。
3. アドレスとアカウントを確認し、[展開の開始] を選択します。
4. 結果を読み取り、「デプロイされたホスト」の下の対応するレコードを確認します。

> デプロイメントでは、パスワードを使用する前にホストのフィンガープリントがチェックされます。既知のホストの変更されたフィンガープリントは拒否されます。ただし、不明なホストへの最初の展開では、最初に確認を求められることなく、フィンガープリントが保存され信頼されます。制御されたネットワークを使用し、信頼できるチャネルを通じて完全なフィンガープリントを検証します。

### 3.3 導入結果の理解

| 結果からわかること | 次に何をするか |
|---|---|
| キーが展開され、ホストが登録され、公開キーのサインインが検証されました | ホストの詳細を確認し、実際のタスクをテストします |
| キーはデプロイされ、ホストは登録されましたが、サインインは未確認です | 「テスト」を選択します。失敗した場合は、別の接続を介して認証とアカウント設定を確認してください |
| キーはデプロイされましたが、登録が失敗したか、未確認です | 再度展開する前に、ローカル リストとリモート認証を確認してください |
| デプロイは完了しましたが、リストを更新できませんでした | 手動で更新します。更新に失敗しても、リモート キーがインストールされていないことを意味するわけではありません |

デプロイメントごとにキーが追加されるため、これを繰り返すと重複行が作成される可能性があります。リモート結果の確認が必要な場合は、別の管理接続を使用して認証ファイルを検査します。

### 3.4 接続をテストする

1. [展開されたホスト] で、アドレス、ポート、ユーザー名、およびキー ID を確認し、[テスト] を選択します。
2. 最初のフィンガープリントの確認が表示された場合は、「信頼して接続」を選択する前に、セクション 4.3 の説明に従って完全なフィンガープリントを比較します。
3. フィンガープリントが変わっている場合、保存済みの値と現在の値が表示されます。まず「キャンセル」で中止して理由を調べてください。承認された変更だと確認した後にだけ、「ホスト鍵を更新」を選びます。

テストでは、固定エコー コマンド `echo "TianshanOS SSH Test OK"` を試行します。成功メッセージでは、コマンドの終了ステータスや出力はチェックされません。基本的な接続チェックとしてのみ使用してください。 sudo やアプリケーションのコマンドが動作するかどうかは保証されません。

**失敗した場合:** ネットワーク、SSH サービス、アカウント、およびリモート認証を確認してください。サーバーの ID が不明な場合、またはサーバーのフィンガープリントが変更された場合は、再試行を停止します。

### 3.5 リモート アクセスを取り消し、ローカル レコードをクリーンアップする

> 取り消しは、今後のサインインに影響します。別の管理接続が機能していることを確認し、まだ停止または確認する必要があるタスクを処理します。公開キーの取り消し、ホストの削除、またはキーの削除を行っても、リモート プログラムは自動的に停止しません。

1. ホスト行の「取り消し」を選択し、サーバーのパスワードを入力して、「リモート公開キーの取り消し」を選択します。キー行から開始してターゲットの詳細を入力することもできます。
2. リモート結果を読み取ります。取り消しに成功すると、ローカル ホストの削除チェックが開始されます。ローカルでの削除には、依然として個別の決定が必要です。レコードは自動的に削除されていません。
3. 信頼された接続を介して、公開キーと重複が認証ファイルから削除されていることを確認します。古いキーが機能しなくなったことを確認します。古いアクセスが後で復元されないように、結果の `authorized_keys.bak` をサーバーのバックアップ ポリシーに基づいて処理します。
4. ローカルホスト構成を削除する場合は、確認する前に、セクション 4.2 で説明されているように、その参照と影響を確認してください。
5. すべてのターゲット サーバーと関連タスクが処理されたら、セクション 4.1 の説明に従って、古いデバイス キーと不要な秘密キーのコピーを削除します。

**一致する公開鍵が見つからない場合：**対象アカウントとサーバー側の登録を確認してください。「ホスト設定を確認して削除」で扱うのはデバイス内の登録だけです。接続先の確認に代わる操作ではありません。

**取り消しが失敗した場合、または取り消しが確認されていない場合:** 信頼された接続を介してリモート認証を検査します。結果が明らかになるまでローカルキーを保管してください。リモート失効とローカル削除を個別に評価します。一方が失敗しても、もう一方が起こらなかったことは証明されません。

## 4. キー、ホスト、指紋の管理

### 4.1 キーのコピー、エクスポート、および削除

SSH キーの行については、以下の手順に従ってください。 `https` という名前の行には、デバイス証明書キーが保持されます。その行を削除すると、すべての証明書資格情報がクリアされます。まずセクション 5.6 をお読みください。

**公開鍵をコピー：**「公開鍵」を選び、1 行の完全な値をサーバー管理者に渡します。公開鍵は共有できます。管理者がアカウントの許可一覧に追加すると、その鍵で接続できます。

**秘密鍵をエクスポート：**作成時に「エクスポート可能」を有効にした鍵だけが対象です。信頼できるパソコンと隔離された管理ネットワークで「秘密鍵」を選び、承認された保管先へ保存します。クリップボードとダウンロード先に残った一時コピーは削除してください。チャット、問い合わせ票、ログには貼り付けないでください。

**コピーしても反応しない場合：**HTTP のページでは、ブラウザーがクリップボードへのアクセスを制限することがあります。文字を選択して手動でコピーし、全文がそろっているか確認してください。コピーのためにブラウザーのセキュリティ設定を弱めないでください。

**鍵を削除する前に：**サーバー側の接続許可を取り消し、確認画面に表示されるホストと実行記録を調べてください。削除後は、このデバイスからその鍵を使った接続や関連タスクの確認・停止ができなくなります。タスク自体は接続先で動き続けることがあります。先に別の接続手段で対処してください。影響一覧が不完全でも、利用先がないとは限りません。

削除を確認したら、更新して結果を確認してください。ストレージの削除が完了していない場合は、現在の状態を検査し、管理者に問題の解決を依頼してください。欠落リストのエントリだけでは完了の証明にはなりません。

### 4.2 ホストの削除とその参照の処理

| アクション | 何が変わるのか |
|---|---|
| 公開鍵を取り消す | 一致するリモート認証を削除します。リモートパスワードが必要です |
| ホストを削除します | デバイス構成を削除し、選択に従って関連するコマンドとルールを処理します。 |
| キーを削除します | デバイス上のキーマテリアルを削除します |
| 既知のホストのフィンガープリントを削除する | デバイスに保存されているサーバー ID レコードを削除します |

最後の 3 つのアクションは、リモート公開キーを取り消したり、リモート プログラムを停止したりしません。デプロイされたホストはローカルのリストにすぎません。リストが空であっても、リモート アクセスが削除されたことは証明されません。

1. ホスト行で [削除] を選択し、参照チェックを待ちます。
2. 影響を受けるコマンド、テンプレート、またはルールを確認します。代替ホストを選択するか、参照のリンクを解除して、影響を受ける構成を無効にします。代替には、必要なアカウント、キー、およびタスク環境が必要です。
3. [削除] を選択し、結果を読み、関連するコマンドとルールを確認します。リンクされていないコマンドを再度有効にする前に、ホストを選択する必要があります。

強制削除は、影響を理解した上で設定を削除するための操作です。接続先のサービスが停止済みであることや、状態が判明していることは前提条件になっていません。影響を確定できない場合、「自動化を一時停止して削除を続けることに同意」を選ぶ必要があります。その後は root が設定を確認して有効にするまで、自動化は停止したままです。

> エラーを解消するためだけに強制的に削除しないでください。まず、誰がリモート タスクを管理するのか、どの自動ルールが影響を受けるのかを確立します。

設定が変更されていた場合は、「削除の影響を再確認」を選び、新しい結果を見て判断します。保存先でエラーが起きた場合や結果が未確認の場合は、再読み込みして現在の設定を調べてから、再度の削除を判断してください。

### 4.3 SSH サーバーのフィンガープリントを確認する

フィンガープリントは、接続先のサーバーを識別するための値です。このページは SHA-256 の値を 64 桁の 16 進数で表示します。OpenSSH は通常 `SHA256:base64` で表示します。同じ形式の値を管理者に確認してください。異なる形式の文字列は、そのまま比較できません。

**完全な値を比較します:** [既知のホスト フィンガープリント] で [表示] を選択し、サーバー コンソール、資産レコード、または別の信頼できるチャネルの値と比較します。この表には最初の 32 文字のみが表示されており、完全なチェックには不十分です。

**テストが確認を求める場合:** 最初のダイアログに現在のフィンガープリントが表示されます。変更警告には保存された値と現在の値の両方が表示され、デフォルトでキャンセルが可能です。サーバー、アドレス、ポート、保守記録を確認してから決定してください。確認は表示された指紋にのみ適用されます。別の変更には別のチェックが必要です。

**内容が異なる場合、またはソースが不明な場合:** キャンセルして調査してください。不審な接続でパスワードが使用された場合は、信頼できる接続でパスワードを変更し、サインイン ログと承認を確認してください。キーを取り消すために、不審な接続を介してパスワードを送信しないでください。

**承認された再構築やホスト鍵の変更後：**新しいフィンガープリントと変更記録を確認してから、テスト画面で「ホスト鍵を更新」を選びます。確認を省くために古い登録を削除しないでください。削除しても、次の接続が信頼できるとは限りません。

フィンガープリントはデバイス内部に保存され、SD カード上のフィンガープリントファイルとは同期されません。設定のバックアップや SSH ホストのインポートにも含まれません。復旧や移行後は、サーバーの身元を再確認してください。

### 4.4 ホストの編集

1. 「デプロイされたホスト」で、「編集」を選択します。
2. [SSH ホストの編集] で、アドレス、ポート、またはログイン アカウントを変更します。キー認証の場合、ログインキーIDを変更することもできます。ポートは 1 ～ 65535 である必要があります。
3. [保存] を選択し、詳細を更新して確認し、接続をテストします。ターゲットサーバーを変更するときは、完全なフィンガープリントを確認してください。

変更は今後の接続に適用されます。すでに開始されているタスクの実行記録には、引き続き元のホストの詳細が使用されます。アドレスを変更しても、古いタスクは移動したり停止したりしません。

### 4.5 SSH ホスト構成のインポートとエクスポート

ホストのインポートは、第 6 章の一般的な Config Pack コントロールとは別の専用のワークフローです。パッケージには、アドレス、ポート、アカウント、認証方法、およびキー ID が含まれています。これには SSH パスワード、秘密キー、保存されたホストの指紋は含まれず、サーバーへのアクセスは許可されません。

**エクスポート：**Developer デバイスで、ホスト行の「エクスポート」を選びます。別のデバイス向けなら、その証明書を貼り付けて確認し、パッケージを生成して「ダウンロード」を選びます。ファイルが保存されたことを確認してください。通常のデバイスは、root でログインしてもエクスポート可能にはなりません。

**インポート前に：**提供元と、このデバイス向けのパッケージであることを確認してください。必要な鍵が登録済みかも確認します。同じ ID があるだけでは足りず、実際の鍵が接続先の登録と一致する必要があります。現在使っている設定の保存先には書き込みが必要ですが、SD カードが必須とは限りません。

1. [ホストのインポート] を選択し、 `.tscfg` ファイルを選択して、チェックが完了するまで待ちます。
2. プレビューでホスト、アドレス、アカウント、および変更を確認します。既存の構成を同じ ID で置き換える場合にのみ、上書きを有効にします。
3. 「インポートの確認」を選択します。デバイスは、古いプレビューに依存するのではなく、パッケージ、認証情報、および現在の構成を再チェックします。
4. 保存が成功したら、ホスト リストを更新して確認し、接続をテストします。保存された構成は、再起動しなくてもすぐに有効になります。既存の有効化または一時停止されたオートメーション設定は保持されます。

このワークフローは、プレビュー中に受信者のデバイス、署名、信頼できる発行者、および署名者の適格性をチェックし、コンテンツを復号化してチェックします。また、信頼できるチャネルを通じてソースを確認してください。名前や公式ラベルだけでは十分ではありません。

**チェックが失敗した場合:** メッセージに従って、デバイスの時間、デバイス証明書、クライアント CA チェーン、および信頼できる発行者の設定を確認します。 HTTPS で受け入れられた証明書は、必ずしも構成パックに署名できるわけではありません。デバイス管理者にこれを解決するよう依頼してください。馴染みのないパッケージをインポートするためだけに、馴染みのない CA をインストールしないでください。

**プレビューの期限が切れた場合：**「パッケージを再確認」を選び、変更内容を確認します。画面を開き直す必要がある場合は、必要な入力を安全な場所へ控えてから、第 7.2 節の手順に従ってください。

### 4.6 バックアップと復元で取り戻せるもの

SSH ホストは、オートメーション ルール、テンプレート、コマンド、および関連する構成とともに保存されます。通常の動作では SD 構成が使用されます。内部緊急モードでは、編集内容はデバイス内に保存されます。ホストのインポート、編集、削除はすべて、現在使用されている構成に書き込みます。

ルートは、[自動化] ページの [構成とバックアップ] で現在の場所を表示できます。緊急バックアップを保存すると、完全な内部コピーが手動で更新されます。編集するたびに同期は行われません。緊急バックアップを復元すると、再起動せずに、現在の構成を置き換える前の差異が表示されます。

古いコピーでは、古いホスト、コマンド、ルールが復元され、自動化が有効かどうかが変更される場合があります。復元する前に相違点を確認してください。復元では、リモート サービスの停止や再起動、秘密キーや既知のホストのフィンガープリントの回復は行われません。

現在の構成を削除しても、他の手動コピーはクリーンアップされません。ホストを廃止した後に緊急コピーを更新するように手配します。 SD カードを再度挿入しても、構成は自動的に切り替わりません。 root は、[設定とバックアップ] でどれを使用するかを選択する必要があります。ファイル マネージャーを使用して、内部管理されているオートメーション ファイルを削除したり上書きしたりしないでください。

## 5. HTTPS 証明書と mTLS を構成する

このガイドで確認したビルド設定では、HTTPS サービスは有効ではありません。画面で認証情報を用意できても、ポート 443 が開いているとは限りません。HTTPS が必要な場合は、導入済みファームウェアで有効になっているか、先に管理者へ確認してください。

有効にすると、現在の HTTPS サービスは、完全な Web インターフェイスではなく、ヘルス、アイデンティティ、および権限テストのエンドポイントを提供します。以下の接続テストは、HTTPS が有効になっている展開に適用されます。

### 5.1 どの証明書が何を行うかを知る

- **デバイス証明書と秘密キー**により、デバイスはクライアントにその身元を証明できます。
- コンピューターまたはサービスが保持する **クライアント証明書と秘密キー** を使用すると、クライアントはデバイスに対して身元を証明できます。
- **デバイス上のクライアント検証 CA** がクライアント証明書を検証します。ブラウザがデバイス証明書を自動的に信頼するようにはなりません。

この双方向認証は mTLS と呼ばれます。クライアントは引き続きデバイス証明書の発行者を信頼し、そのアクセス名、許可された使用法、および有効性を確認する必要があります。 CA は認証局、またはその証明書です。

### 5.2 ステータスの読み取りとデバイスの時刻の設定

「保存済み」「有効期間内」「HTTPS：動作中」は、それぞれ保存状態、期限、サービスの動作を示します。どれか一つだけで、他も満たしているとは判断できません。

| ステータスまたは状況 | どうすればいいですか |
|---|---|
| デバイス証明書、秘密キー、またはクライアント検証 CA がありません | 不足しているマテリアルをインストールする |
| デバイス時間の待機中 | コンピューターの時計を確認し、[このコンピューターからデバイスの時刻を設定する (ブラウザー ソース)] を選択します。 |
| まだ有効ではないか期限切れです | デバイスの時刻と証明書の日付を確認します。必要に応じて更新を手配する |
| 有効期限は正しいが、HTTPS が停止している | まずファームウェアで HTTPS が有効になっていることを確認し、表示された資格情報、照合、または起動の問題を解決します。 |
| 実行中のサービスはまだ以前のマテリアルを使用しています | 他の作業を保存し、指示に従って再起動し、実際に使用されている証明書を確認します |
| 保存や読み込みは未確認 | 再度インストールまたは削除する前に、更新して確認してください |

ファームウェアで HTTPS が有効になっている場合、認証情報と時間が準備できると、停止したサービスが起動を試みます。時刻を設定したら、デバイスの時計、同期状態、HTTPS の状態を確認します。インストールが成功しただけでは、準備が整っていることは証明されません。

### 5.3 デバイスキーと証明書リクエストの生成

> 鍵がすでにある場合は、先に第 5.6 節を読んでください。再生成するとその鍵が上書きされ、古い証明書やパッケージを使い続けられなくなることがあります。

1. [キー ペアの生成] を選択します。これにより、SSH キーとは関係のない、別の ECDSA P-256 秘密キーが作成されます。このインターフェイスを介してエクスポートすることはできません。
2. [CSR の生成] を選択します。デバイス ID (CN)、組織、部門を入力するか、すべてのフィールドを空白のままにします。部門は、証明書の組織単位 (OU) に対応します。
3. [証明書署名要求の生成] を選択し、完全な CSR を CA 管理者に送信します。

英語の文字と数字で構成される短くて安定したデバイス ID を使用してください。フォームフィールドでは最大 63 UTF-8 バイトが許可されます。中国語の文字は複数のバイトを使用します。長さエラーが表示される場合はフィールドを短くしてください。

**発行前に接続先名を確認：**項目を指定した場合、このフォームは SAN（証明書が対象とする名前やアドレス）の一覧を生成しません。すべて空欄の場合、デバイス ID は `TIANSHAN-DEVICE-001` に固定されます。現在の IP を取得できれば追加されますが、DNS 名は追加されません。CA 管理者に実際の接続先 IP または DNS 名を含めてもらい、管理された発行手順で認証用途も確認してください。このフォームから SAN は編集できません。

CSR は単なるリクエストです。秘密キーは含まれておらず、証明書もインストールされません。発行前に公開キー、サブジェクト、アクセス名を確認してください。

### 5.4 デバイス証明書のインストール

1. 現在のデバイスの秘密キーと一致する PEM 証明書を取得します。 PEM は、BEGIN/END 境界マーカーが付いたテキストです。
2. [証明書のインストール] を選択し、完全なテキストを貼り付けて、 [インストール] を選択します。
3. 保存された結果、件名、発行者、有効性を確認し、実際の HTTPS ステータスを確認します。

インストールでは、形式とキーの一致がチェックされます。クライアントは、信頼性、アクセス アドレス、および許可された使用を個別に確認する必要があります。

証明書のテキストを表示するには、キー管理の `https` 行で [証明書] を選択します。完全な PEM を確認またはコピーします。パブリック証明書を Config Pack 送信者と共有できます。秘密鍵を秘密にしておきます。

**鍵が一致しない場合：**現在の CSR に対して発行された証明書を探してください。エラーを消すためだけに秘密鍵を作り直さないでください。結果が未確認なら、再読み込みして保存内容を調べてから再試行を判断します。

### 5.5 クライアント CA チェーンをインストールしてテストする

1. 「CA のインストール」を選択し、クライアントの検証に必要な 1 つ以上の PEM CA 証明書を貼り付けて、「インストール」を選択します。管理者によって承認された CA のみをインストールします。
2. ステータスを確認してください。 HTTPS が有効になっている場合、資格情報と時間が準備できると、停止したサービスが起動を試みます。実行中のサービスに新しいマテリアルを適用する必要がある場合は、指示に従って再起動します。
3. 管理者に、目的と役割が正しい信頼されたクライアント証明書を使用して、適切なテスト エンドポイントにアクセスしてもらいます。
4. 信頼できない証明書を使用するか、証明書を使用せずに繰り返し、拒否を確認します。

**結果の確認：**意図した証明書で HTTPS が動作していることを確認します。「使用中の証明書 SHA-256」が表示される場合は照合してください。信頼するクライアントにも、役割に応じた接続先だけを許可します。実機で、許可すべき接続と拒否すべき接続をそれぞれ確認してください。

### 5.6 認証情報の更新、置換、または削除

**証明書の期限更新：**漏洩していない鍵を使って新しい証明書を申請し、インストールと適用を行って接続を確認します。Config Pack は受信先の証明書のフィンガープリントに結び付いています。秘密鍵が同じでも、証明書の変更後に古いパッケージを読み込むと拒否されることがあります。先に代わりのパッケージを手配してください。

**秘密鍵を交換：**古い CSR と証明書は新しい鍵に一致しなくなります。古い鍵に依存するパッケージは復元できないことがあります。鍵が漏洩した場合は、CA 管理者に証明書の失効も依頼してください。新しい鍵を作るだけでは失効されません。

**認証情報をすべて削除：**先に HTTP の管理画面へ接続できることを確認し、今後も必要なパッケージを手配します。「認証情報を削除」は、デバイスの鍵、デバイス証明書、クライアント検証用 CA チェーンをまとめて削除します。公開証明書のバックアップだけでは秘密鍵を復元できません。

削除後は再読み込みし、認証情報がなくなったことを確認します。動作中の HTTPS サービスが古い認証情報を保持していることがあります。保存データを削除しても、直ちに利用が止まるとは限りません。指示に従って再起動し、古い認証情報が使われていないことを確認します。復旧時は鍵、デバイス証明書、CA チェーンを用意し直し、接続を確認してください。

## 6. Config Pack の一般的な制限事項を理解する

Config Pack は、暗号化と署名が施された `.tscfg` ファイルです。「Config Pack」の汎用操作は、第 4.5 節の「ホストのインポート」とは別の機能です。ホスト、コマンド、データソース、テンプレート、ルールの専用インポートの動作を、汎用操作から判断しないでください。

### 6.1 コントロールの機能

| アクション | 現在の結果 |
|---|---|
| デバイス証明書のエクスポート | 公開証明書を共有して、送信者がこのデバイス用のパッケージを作成できるようにします。秘密鍵をエクスポートしません |
| 検証のみ | 構造と署名を、含まれている証明書と照合してチェックします。署名者の信頼や受信者の照合を確立しません |
| 一般ダイアログで選択または貼り付けた後にインポートします | 現在、このエントリ ポイントはインポートを完了できません |
| パッケージリストからインポート | 設定のコピー、復号化、適用を行わずに、既存のデバイス ファイルをチェックします。 |
| 適用 | 設定を書き込むことなく、構成カテゴリを復号化してリストします。まだ成功を報告する可能性があります |
| Developer デバイス上で Config Pack をエクスポート | パッケージを作成して SD カードに保存し、成功後にダウンロードを提供します |

> 汎用の「適用」を、一括設定、災害復旧、設定の反映確認に使わないでください。成功と表示されても、対象機能のページで設定し、結果を確認してください。

### 6.2 送信元と受信者を確認してください

汎用の「検証のみ」は、パッケージ内の署名者証明書を使い、信頼する認証局からの発行かどうかは確認しません。署名が保護するのは暗号化された内容です。表示されたすべての項目が信頼できるとは限りません。「Official」の表示、パッケージ名、宛先名だけで提供元を判断しないでください。

資産レコードまたは独立した信頼できるチャネルを使用して、署名者証明書のフィンガープリント、受信者のデバイス証明書、および目的を確認します。同じメッセージで受信した証明書とフィンガープリントは、独立したチェックではありません。ソース、ターゲット、目的が不明瞭な場合は中止してください。

### 6.3 デバイス証明書の共有とパッケージの検査

**このデバイスの証明書を提供します:** [デバイス証明書のエクスポート] を選択し、完全な PEM と表示されたフィンガープリントをコピーします。公開証明書を送信者に送信し、別の信頼できるチャネルを通じてフィンガープリントを確認します。

**受信したパッケージを検査します:** [構成パックのインポート] を開き、ファイルを選択または貼り付けて、[検証のみ] を選択します。署名情報を確認し、ソースを確認します。これは設定を適用したり、このデバイスが受信者であることを証明したりするものではありません。

検証に合格した後でも、一般的なインポートと適用を利用してデバイスを構成することはできません。 SSH ホスト パッケージには [ホストのインポート] を使用し、その他の設定には関連ページでサポートされているコントロールを使用します。

### 6.4 開発者デバイスから一般的な構成パックをエクスポートする

1. SD カード上に有効な JSON 構成ファイルを準備し、検証済みのターゲット デバイス証明書を取得します。
2. [構成パックのエクスポート] を選択し、ファイルを選択します。必要なファイルがすべてロードされていることを確認してください。必要なコンテンツを省略するのではなく、読み取りエラーを解決します。
3. 名前と説明を入力し、受信者の証明書を貼り付けて、パッケージを生成します。
4. 成功メッセージとデバイスの保存パスを確認し、[ダウンロード] を選択します。ブラウザが `.tscfg` ファイルを保存したことを確認します。

保存先は `/sdcard/output_config/` です。デバイスへの保存に失敗するとエラーになり、新しく生成したパッケージはダウンロードできません。前回の結果を今回の成功と取り違えないでください。SD カードと保存結果を確認してから、作り直すか判断します。

エクスポートしても、元の設定は変わりません。宛先が違う場合や受信先の証明書を交換した場合は、パッケージを作り直します。エクスポートの成功は、受信先の汎用「適用」が使えることを保証しません。

## 7。トラブルシューティングとインシデント対応

### 7.1 よくある問題

| の症状 | どうすればいいですか |
|---|---|
| アカウントのセキュリティがありません | root にのみ表示されます |
| 認証または許可が拒否されました | アカウントと必要なデバイス ID を確認してください。繰り返しクリックしても要件を回避することはできません |
| 生成や展開は未確認 | 再送信する前にローカルレコードとリモート結果を確認してください |
| リストが読めない | 接続を復元して更新します。読み取り失敗はリストが空であることを意味するわけではありません |
| ホストのフィンガープリントが変更される | キャンセルし、信頼できるチャネルを通じて確認します。セクション 4.3 を参照 |
| 取り消し後もローカルホストが残る | リモート失効とローカル削除を個別に確認してください。セクション 3.5 を参照 |
| ホストを削除した後もアクセスは引き続き機能します | リモート公開キーを個別に取り消します。ローカルで削除してもアクセスは取り消されません |
| 削除チェックまたはパッケージ プレビューの有効期限が切れる | 古いプレビューではなく、新しい結果から再確認して決定します |
| 証明書は保存されていますが、HTTPS は停止しています | まずファームウェアで HTTPS が有効になっていることを確認し、次に時刻、認証情報、起動メッセージを確認します。 |
| クライアントが証明書を拒否しました | クライアントの信頼性、アクセス名、許可された使用法、有効性を確認します。 |
| 一般適用は成功しますが、設定は変更されません | この入口では、まだ設定を書き込めません。対象機能のページを使ってください。 |

### 7.2 設定変更または不確実な結果

**設定が変更されたと表示された場合：**入力は画面に残っていても、下書きとして保存されていません。必要な内容を安全な場所へ控え、編集画面を開き直して現在の設定を読み込んでから編集してください。パスワードや秘密鍵を普通のメモへ書き込まないでください。

**パッケージのプレビュー期限が切れた場合：**「パッケージを再確認」を選び、変更内容を確認してください。認証情報や設定が変わると、古いプレビューは使えません。

**削除確認の期限が切れた場合：**「削除の影響を確認」を選び、現在どの設定が使っているかを確認してください。別のウィンドウでの操作により、結果が変わっていることがあります。

**タイムアウト、切断、応答の欠落が起きた場合：**まず現在の設定、鍵、証明書、接続先の公開鍵登録を確認してください。確認の応答がなくても、操作は実行されている可能性があります。結果を調べてから再試行を判断してください。

### 7.3 キーまたはパスワードの漏洩の疑い

1. デバイスおよび影響を受けるマテリアルへのアクセスを制限します。調査に必要な記録を保管してください。
2. 公開された SSH 秘密キーの場合は、信頼できる接続を通じて、影響を受けるすべてのサーバーでその公開キーを取り消します。バックアップをチェックし、古いキーが機能しなくなっていることを確認します。
3. 新しい ID で新しい RSA キーを作成して展開します。それを確認してから、古いキーとエクスポートされたコピーを削除します。
4. 公開された SSH パスワードの場合は、信頼できる管理接続を通じてパスワードを変更し、サインイン レコードを確認します。
5. 公開されたデバイス証明書キーの場合は、セクション 5.6 の説明に従って資格情報を置き換えます。失効および古いパッケージについては CA 管理者と協力してください。

ローカル ホスト リストには、アクセスを許可したすべてのサーバーが含まれているわけではありません。サーバーと資産の記録も確認してください。ログを共有する前に、パスワード、キー、その他の機密情報がないか確認してください。

### 7.4 現在の動作限界

HTTP とアクセスの制限については第 1 章で、初期展開の信頼については第 3 章で、一般的な Config Pack の制限については第 6 章で説明します。Hidden はアクセス制御メカニズムではありません。

レビューされたビルド構成では、NVS 暗号化、フラッシュ暗号化、またはセキュア ブートが有効になっていません。暗号化と安全な起動が保存されたキーを保護することを確立できません。実際のファームウェアとハードウェアのセキュリティ設定は個別に検証する必要があります。これらの制限が受け入れられない場合は、セキュリティ所有者に隔離または修正を手配するよう依頼してください。

## 8. 範囲と用語集

### 8.1 この版の基礎

このガイドでは、TianshanOS 0.6.4 について説明します。その手順は、2026 年 11 月 3 日にレビューされたアップストリーム コードとその中国語と英語のインターフェイスに従っています。レビューされた実装を使用して機能を判断します。バージョン番号だけでは不十分です。

後の更新でも、このガイドを使える部分はあります。画面、手順、結果が違う場合は、実際の画面と更新内容を確認してください。文書の確認だけでは、実機の SSH 接続、サーバー側の公開鍵登録、HTTPS 接続、再起動、復旧の検証に代えられません。

### 8.2 このガイドで使用される用語

- **公開鍵／秘密鍵：**公開鍵は接続を許可する相手へ渡し、秘密鍵は秘密に保ちます。接続時には、この組み合わせを使って本人であることを確認します。
- **フィンガープリント:** サーバーまたは証明書の ID を比較するために使用されるダイジェスト。比較する前に、異なる表示形式を変換します。
- **CSR / CA:** 証明書署名リクエスト、および認証局またはその証明書。
- **CN / OU:** 証明書内の名前と組織単位。フォーム内の部門は OU に対応します。
- **SAN:** 証明書がカバーする DNS 名または IP アドレス。
- **PEM:** BEGIN/END マーカーを含む証明書、リクエスト、またはキー テキスト。
- **mTLS:** 双方が証明書を提示する認証。
- **NVS:** デバイス設定とキー用の内部ストレージ領域。その名前は暗号化を意味するものではありません。
