重要提示

先确认网络安全：当前完整管理页面使用 HTTP，且多数接口没有统一执行登录和权限检查。请只在受控、隔离的管理网络中操作，不要将设备直接暴露到公网或访客网络。安装 HTTPS 证书不会把完整管理页面自动切换到 HTTPS。

1.2 账号与设备身份不是一回事

  • admin：能进入安全页，看到密钥、主机、证书和配置包功能，但看不到“账号安全”。
  • root：还可以设置 root/admin 密码，或重置 admin 密码。这些密码管理接口会在后端校验root 身份。
  • Developer 设备：由设备证书的 OU 属性识别，不是登录账号。当前只有这类设备能导出配置包和 SSH 主机配置；以 root 登录不会改变设备身份。

除上述密码管理等自行校验身份的接口外，不能依靠“页面需要登录”阻止直接调用接口。网络隔离仍是当前使用前提。

1.3 操作前的准备

  1. 确认地址栏 IP 对应目标设备，电脑也在可信管理网络中。
  2. 向服务器管理员确认 SSH 地址、端口和用户名。
  3. 使用页面部署或撤销公钥时，需要目标账户的密码，且该账户允许密码登录。不要为排障长期放宽服务器策略。
  4. 删除密钥、撤销授权或更换证书前，确认还有服务器控制台、另一管理员密钥或设备 HTTP 管理入口可用。

2. 修改设备登录密码

这里修改的是 TianShanOS 的登录密码，不是远端服务器的 SSH 密码。

2.1 首次登录后的密码提醒

账号尚未标记为已修改密码时，登录后会出现改密提醒。请设置独有的长密码，不要选择“稍后修改”后长期保留默认密码。

这个提醒并不是随时可打开的账号设置入口。已经改过密码的 admin 用户如需再次改密，可由root 在安全页设置。

2.2 由 root 设置密码

  1. 以 root 登录，打开“安全”。
  2. 在“账号安全”中点击“设置 root 密码”或“设置 admin 密码”。
  3. 两次输入相同的新密码并提交。界面接受 4-64 个字符；4 个字符只是技术下限，不是强度建议。

确认结果：用无痕窗口重新登录，确认新密码可用，再关闭原会话。修改密码不会自动结束已有会话。

登录失败时：先核对账号和设备 IP。连续 5 次失败会锁定约 5 分钟，不要反复猜测。

2.3 重置 admin 密码

root 可在账号安全区将 admin 重置为默认密码 rm01，并清除 admin 的登录锁定。重置后，立即用新会话登录 admin 并设置新密码。

重置是临时恢复手段。不要把默认密码留作日常使用，也不要把“修改密码”理解为已踢出所有旧会话。

3. 用 SSH 密钥连接服务器

首次设置按以下顺序进行：生成 RSA 密钥 → 部署公钥 → 测试连接 → 核对服务器身份。退役时，先撤销远端授权，确认不能再登录，最后删除本地密钥。

3.1 生成密钥

  1. 在“密钥管理”中点击“生成新密钥”。
  2. 先查看已有列表，再输入未使用的密钥 ID，例如 backup01。不要复用旧 ID：当前生成接口没有重复 ID 拦截，可能覆盖原密钥。
  3. 选择 RSA 2048 或 RSA 4096。页面默认选 RSA 2048；虽然也列出 ECDSA，但当前 SSH 公钥认证不支持它。
  4. 按需填写备注和别名。只有确实需要备份或迁移私钥时，才勾选“允许导出私钥”；生成后没有修改此属性的页面入口。
  5. 点击“生成”，完成后刷新列表。

确认结果：找到正确的 ID 和 RSA 类型，点击“公钥”，确认完整文本以 ssh-rsa 开头。

注意：密钥列表容量为 8 个。满额时不要继续生成；先按撤销流程清理旧密钥。当前保存与列表登记并非完整的原子操作，成功提示后也要检查列表。“隐藏密钥 ID”不能保护真实 ID 不被接口读取。

3.2 部署公钥

部署会将公钥追加到远端账户的 ~/.ssh/authorized_keys，使设备有机会用对应私钥登录。它不会修改服务器密码。

  1. 在新密钥所在行点击“部署”。
  2. 填写服务器地址、用户名、SSH 端口和该账户的密码。
  3. 核对信息，点击“开始部署”。
  4. 完成后，在“已部署主机”检查对应记录，并按下一节测试。

当前流程先用密码完成 SSH 认证，再检查主机指纹；首次遇到的主机会被自动信任。它不能保证“确认服务器身份后才发送密码”。首次连接必须在受控网络中进行，事后比对指纹不能消除密码已经发出的风险。

提示成功但列表没有记录，或测试失败时：不要马上重复部署。远端公钥可能已经写入，只是密钥登录复验或本地保存失败。请从另一管理入口检查 authorized_keys；反复部署可能追加重复行。

3.3 测试连接并确认结果

  1. 在“已部署主机”核对地址、端口、用户名和密钥 ID。
  2. 点击“测试”。设备会尝试执行固定命令 echo "TianshanOS SSH Test OK"。
  3. 首次连接后，按第 4.3 节核对保存的主机指纹。

如何理解成功提示：页面只检查 API 请求是否成功，没有检查远端命令的退出码和回显内容。因此它是基础连接检查，不是完整验收，更不能证明 sudo 或业务命令可用。重要用途还需在实际任务中确认命令输出、退出码和权限。

测试失败时：先检查网络、SSH 服务、账户与远端授权。涉及指纹变化或服务器身份不明时，停止重试，按第 4.3 节处理。

3.4 撤销远端授权，再删除本地密钥

  1. 确认另一条服务器管理入口可用，且设备上的原密钥尚未删除。
  2. 在“已部署主机”对应行点击“撤销”，输入服务器密码，确认“撤销并移除”。也可从密钥行发起撤销并填写目标信息。
  3. 查看撤销结果，再从可信的服务器管理入口检查 authorized_keys，确认对应公钥及重复行已移除。
  4. 确认旧密钥不能再登录。撤销会留下 authorized_keys.bak 备份；按服务器备份策略处理，避免以后恢复旧授权。
  5. 刷新本地主机列表。页面会尝试移除记录，但没有核对该移除请求的结果，必要时再手动“移除”。
  6. 所有目标服务器都处理完后，才删除设备中的旧密钥及不再需要的私钥副本。

提示“未找到公钥”：先从服务器侧确认选对账户且公钥确实不存在，再选择仅移除本地记录。

撤销失败或服务器身份可疑：保留本地密钥，改用可信控制台或另一管理员入口处理。不要继续向可疑服务器发送密码。

4. 管理密钥、主机与指纹

4.1 复制公钥和导出私钥

公钥：点击密钥行的“公钥”，复制完整的一行给服务器管理员。公钥不是秘密；发错对象本身不等于私钥泄露，也不要求立即换钥。管理员必须另行把它加入授权列表，才会产生访问权限。

私钥：只有生成时允许导出的密钥才能点击“私钥”导出。请在可信电脑和隔离网络中操作，保存到受控密钥库，并清理剪贴板、下载目录等临时副本。不要粘贴到聊天、工单或日志里。

复制按钮无响应：HTTP 页面可能无法使用浏览器剪贴板接口。可手动选中并复制可见文本，随后检查开头、结尾和内容是否完整。不要为方便复制而放宽浏览器安全设置。

4.2 分清“撤销”“移除”和“删除”

操作改变什么
撤销公钥尝试删除服务器上的授权，需要远端密码
移除主机删除设备本地的连接记录，不撤销服务器授权
删除密钥删除设备本地密钥，不访问服务器，也不撤销授权
删除已知主机指纹删除设备保存的服务器身份记录，不删除连接记录或服务器授权

“已部署主机”是本地清单，不会持续查询服务器。列表为空不代表远端授权已清理；列表中有记录也不代表现在仍能登录。

4.3 核对 SSH 服务器指纹

指纹用于确认你连接的是哪台服务器。当前页面保存 SHA-256 摘要的 64 位十六进制值；常见OpenSSH 输出则是 SHA256:base64。先请管理员统一格式，不能直接比较这两种字符串。

首次连接后：在“已知主机指纹”点击“查看”，与服务器控制台、资产系统或另一条可信渠道提供的完整值比较。表格只显示前 32 位，不足以完成核对。

不一致时：停止连接并隔离调查。若已输入 SSH 密码，按可能泄露处理，通过可信入口修改密码、检查登录日志和清理不应存在的公钥。不要通过可疑连接执行页面撤销。

已保存的指纹发生变化时：

  1. 暂停重试，不要直接删除旧记录。
  2. 通过可信控制台核对新指纹、IP、端口、资产身份和维护记录。
  3. 只有确认是服务器重装或正常换钥后，才删除旧指纹。
  4. 在受控网络重新连接，再次查看并核对新记录。

页面当前可能只显示通用连接错误，不一定出现专门的指纹对比弹窗。

保管 SD 卡：指纹会保存到设备存储，并同步为 SD 卡明文 JSON。启动时有 SD 指纹配置就会以它为准替换对应 NVS 记录；文件没有签名保护。不要让不可信人员修改 SD 卡。

4.4 导入和导出 SSH 主机配置

这是一条专用的 .tscfg 流程，与第 6 章尚未完成的通用配置应用不同。包中保存主机地址、端口、用户、认证类型和密钥 ID，不包含 SSH 密码或私钥，也不授予远端权限。

导出：在 Developer 设备上点击主机行“导出”，给另一设备使用时提供并核对目标设备证书，然后下载包。普通设备即使能看到按钮，后端也会拒绝导出。

导入：

  1. 确认包是为本设备制作的，SD 卡可写，并通过可信渠道核对来源。
  2. 确认本设备已有包所引用的正确密钥。只有相同 ID 不够，密钥本身也必须与服务器授权对应。
  3. 点击主机配置导入入口，选择文件并检查预览。只有确实要替换同名配置时才勾选覆盖。
  4. 确认后按提示重启。导入只把包保存到 SD 卡，重启时才尝试加载和解密。
  5. 检查加载后的地址、用户、端口和密钥 ID，再测试连接。

预览通过不等于可用：它既没有确认签名者可信，也没有核对接收设备指纹；目标检查要到重启加载时才执行。错误记录需要移除，并清理 SD 卡中对应包，避免重启后重新加载。更换设备证书前请同时阅读第 5.5 节。

5. 配置 HTTPS 证书与 mTLS

这部分面向证书管理员。当前 443 服务只提供健康、身份和权限测试接口，不提供完整管理页面。默认启动还需要设备私钥、设备证书和客户端 CA 链齐备。

5.1 先分清证书方向

  • 设备私钥和设备证书：让设备向连接它的客户端证明身份。
  • 客户端证书和私钥：由电脑或服务持有，让客户端向设备证明身份。
  • 安装在设备上的 CA 链：用于验证客户端证书，不会自动让电脑或浏览器信任设备证书。

双方都出示证书的方式叫 mTLS。客户端侧仍需配置信任设备证书的 CA，并校验访问名称和证书用途。

5.2 生成设备私钥和证书申请

  1. 在“HTTPS 证书”点击“生成密钥对”。这会生成独立的 ECDSA P-256 私钥，与 SSH 密钥无关；本界面不能导出它。
  2. 已有私钥时先停止，按第 5.5 节确认替换影响；继续生成会覆盖旧私钥。
  3. 点击“生成 CSR”，填写设备 ID（CN）、组织（O）和组织单位（OU），或全部留空。
  4. 复制完整的 CSR 文本给 CA 管理员。CSR 是证书申请，不含私钥，也不会自动安装证书。

签发前必须检查名称：自定义字段路径不会生成 SAN；全部留空时，CN 固定为TIANSHAN-DEVICE-001，仅在能取得当前 IP 时加入该 IP 的 SAN，不含 DNS SAN。请让 CA 管理员核对 CSR，并通过受控签发流程把实际访问的 IP/DNS 加入最终证书 SAN；此表单不能编辑SAN。

确认结果：刷新后确认私钥存在；让 CA 管理员解析 CSR，核对公钥、主体和 SAN，并确认最终证书包含所需的服务器认证用途（EKU）。

5.3 安装设备证书

  1. 取得与当前设备私钥匹配的 PEM 证书。
  2. 点击“安装证书”，粘贴包含首尾标记的完整文本并提交。
  3. 查看证书，核对主体、签发者和有效期。

成功提示只表示：证书可以解析，且公钥与当前私钥匹配。安装过程没有完整验证信任链、SAN、EKU、当前有效期或主体策略。

最终是否可信，要由实际客户端检查证书链、访问地址、用途和有效期。若提示密钥不匹配，先找回当前 CSR 对应的证书，不要为了消除错误而重新生成私钥。

5.4 安装客户端 CA 链并测试

  1. 点击“安装 CA”，粘贴用于信任客户端证书的一个或多个 PEM CA 证书。
  2. 保留 HTTP 管理入口，安排重启设备后再测试。安装接口只更新存储，不会主动重启正在运行的443 服务。
  3. 使用受信任、用途及角色正确的客户端证书访问相应测试端点。
  4. 再使用不受信任的证书或不提供证书测试，确认连接被拒绝。

确认结果：设备使用预期的新证书；可信客户端只能访问其角色允许的接口，不可信客户端无法接入。具体握手和角色行为需要真机验收，不能仅凭安装提示确认。

5.5 更新证书或删除全部凭证

仅证书到期：可以沿用未泄露的私钥申请新证书，安装后重新测试。但配置包绑定的是接收方证书指纹；即使沿用同一私钥，新证书指纹改变后，重新初始化或重启加载的旧包也会因目标不匹配而被拒绝。更换前请重新制作需要保留的包。

替换私钥：旧证书和旧 CSR 不再对应新私钥。这不等于旧证书已被 CA 吊销；若旧私钥泄露，应另行执行吊销和事件处理。没有旧私钥时，依赖它的旧包可能无法恢复。

删除全部 PKI 凭证：证书区的“删除凭证”会一起清除设备私钥、设备证书和客户端 CA 链。先确认 HTTP 管理入口可用，完成配置包替代安排，再确认删除。公开证书备份不能恢复私钥。

删除后刷新应显示未初始化；重启后检查 443 不再使用旧凭证。重新启用时需重新生成私钥、签发设备证书、安装 CA 链并完成测试。

6. 使用 Config Pack 前先看限制

Config Pack 是加密、签名的 .tscfg 配置包。当前可以生成和检查包，但通用配置应用尚未完成，不要将它用于生产批量配置、灾难恢复或证明配置已经生效。

6.1 各按钮目前实际做什么

操作当前结果
导出设备证书显示公开证书，供发送方为本设备制作包；不导出私钥
验证检查包结构和自带证书对应的密文签名，不确认签名者可信或目标匹配
安全页选择/粘贴包后导入前后端参数不匹配，当前不能完成导入
配置包列表中的导入验证设备上已有文件，不复制、不解密、不应用
应用解密并列出模块名，但没有写入模块配置；仍可能提示成功
Developer 导出配置包生成可下载的加密签名包，并尝试保存到 SD 卡

6.2 核对来源，不要只看“签名有效”

接收设备目前用包内自带的证书检查签名，没有完成签名者证书链信任验证。签名保护的是包内密文，不应由此推断所有展示字段都已得到可信认证。“官方”字段也不能作为来源证明。

导入或检查前，通过资产系统或管理员认可的独立渠道核对签名者证书指纹、目标设备证书和包的用途。不要只凭同一封邮件同时收到的证书和指纹判断可信；预览里的目标名称也不能替代证书指纹核对。

6.3 导出设备证书、检查收到的包

提供本设备证书：点击“导出设备证书”，复制完整 PEM 和显示的指纹，将公开证书交给发送方，再通过独立可信渠道核对指纹。

检查收到的包：打开“导入配置包”，选择或粘贴 .tscfg，点击“验证”。检查签名者信息并核对来源；验证不会应用配置，也不会证明包属于本设备。来源不明、目标不符或用途不清时停止。

即使验证通过，也不要继续依赖当前通用“导入”和“应用”完成配置。请回到对应功能页面使用已支持的设置方式，并检查实际结果。

6.4 Developer 设备导出配置包

  1. 准备 SD 卡中的有效 JSON 配置文件，并取得已核对的目标设备证书。
  2. 点击“导出配置包”，选择文件，填写名称和说明，粘贴目标证书。
  3. 生成后下载 .tscfg。
  4. 分别检查浏览器下载文件和设备上的 /sdcard/output_config/ 保存结果。SD 保存失败时，接口仍可能返回包内容供下载。

导出不会修改源配置。发送给错误目标或接收方证书已更换时，需要重新生成包。当前接收端的通用应用功能仍未完成，不能因为导出成功就认为整个分发流程可用。

7.2 SSH 私钥可能泄露

  1. 限制设备和日志访问；当前日志可能包含私钥开头片段。
  2. 通过可信入口逐台撤销远端公钥，核对备份副本，确认旧密钥不能登录。
  3. 用新 ID 生成 RSA 密钥并重新部署，确认正常后删除旧密钥和导出副本。
  4. 检查相关登录日志。设备本地列表不一定覆盖所有曾授权的服务器。

如果泄露的是 HTTPS 私钥，按第 5.5 节替换设备凭证，并与 CA 管理员处理旧证书吊销及旧配置包。

7.3 当前版本还需承担的风险

除前述 HTTP、接口鉴权、首次主机信任及配置包限制外，当前检查的构建配置未启用 NVS Encryption、Flash Encryption 和 Secure Boot。不能宣称设备私钥已得到这些存储和启动保护；实际设备的烧录配置与 eFuse 状态还需另行核验。

如使用场景无法接受这些限制，应暂停接入相应网络，由安全负责人决定隔离措施或产品修复。不要用操作手册中的验证步骤替代缺失的产品安全控制。

1.3 Prepare for the operation

  1. Check that the IP address in your browser belongs to the intended device and that your computer is on a trusted management network.
  2. Confirm the SSH server address, port, and username with its administrator.
  3. To deploy or revoke a public key through this page, you need the remote account's password, and that account must accept password authentication. Do not leave server restrictions relaxed just to troubleshoot.
  4. Before deleting keys, revoking access, or replacing certificates, make sure you have another way in: a server console, a separate administrator key, or the device's HTTP management interface.

2. Change device passwords

These controls change TianShanOS login passwords, not the SSH password on a remote server.

2.1 The password prompt after sign-in

If an account is still marked as having an unchanged password, a password-change prompt appears after sign-in. Set a long, unique password. Choosing to change it later dismisses the prompt; it does not make the default password safe to keep.

This prompt is not an account-settings screen that you can reopen at any time. If admin has already changed its password and needs another change, root can set it from the Security page.

2.2 Set a password as root

  1. Sign in as root and open Security.
  2. Under Account Security, select Set root password or Set admin password.
  3. Enter the same new password twice and submit. The interface accepts 4-64 characters; four characters is a technical minimum, not a security recommendation.

Check the result: sign in with the new password in a private browsing window before closing your original session. Changing a password does not automatically end existing sessions.

If sign-in fails: check the account and device address first. Five consecutive failed attempts trigger a lockout of about five minutes. Avoid repeated guesses.

2.3 Reset the admin password

root can reset admin to the default password, rm01, and clear its login lockout. After resetting, sign in as admin in a new session and set a new password immediately. A reset is a temporary recovery measure. Do not keep the default password, and do not assume a password change signs out every existing session.

3. Connect to a server with an SSH key

For initial setup: create an RSA key, deploy its public key, test the connection, then check the server fingerprint. When retiring a key, revoke access on the servers first, confirm that the old key no longer works, and only then delete the local key.

3.1 Create a key

  1. In Key Management, select Generate New Key.
  2. Check the existing list and choose an unused key ID, such as backup01. Do not reuse an ID: the generation API does not reject duplicates and may overwrite the existing key.
  3. Choose RSA 2048 or RSA 4096. RSA 2048 is the interface default. ECDSA options are shown, but the current SSH public-key authentication path does not support them.
  4. Add a comment or alias if useful. Allow private-key export only if you need it for backup or migration; there is no interface for changing this setting later.
  5. Select Generate, wait for completion, and refresh the list.

Check the result: find the intended ID and RSA type. Open Public Key and check that the complete text starts with ssh-rsa.

Keep in mind: the key list holds eight entries. Do not keep generating keys when it is full; retire an unused key first. Key storage and list registration can succeed or fail separately, so check the list even after a success message. Hide Key ID does not prevent the API from exposing the real ID.

3.2 Deploy the public key

Deployment appends the public key to the remote account's ~/.ssh/authorized_keys, allowing that account to accept the matching private key. It does not change the server password.

  1. Select Deploy on the new key's row.
  2. Enter the server address, username, SSH port, and that account's password.
  3. Review the details and select Start Deploy.
  4. Check for the server under Deployed Hosts, then test it as described below.

The current implementation authenticates with the password before checking the host fingerprint, and automatically trusts previously unknown hosts. It does not guarantee that the server's identity is verified before the password is sent. Make the first connection on a controlled network; checking the fingerprint afterward cannot undo password exposure. If deployment reports success but the record is missing or the test fails: do not immediately deploy again. The public key may already be installed even though the follow-up key test or local record save failed. Check authorized_keys through another management connection. Repeated deployment can append duplicate entries.

3.3 Test the connection

  1. Under Deployed Hosts, check the address, port, username, and key ID.
  2. Select Test. The device attempts to run echo "TianshanOS SSH Test OK".
  3. After the first connection, check the saved host fingerprint using Section 4.3.

What success means: the page checks whether the API operation succeeded, but does not check the remote command's exit status or output. Treat this as a basic connection check, not a complete acceptance test. It does not establish that sudo or your application commands will work. For an important workload, verify the actual command's output, exit status, and permissions.

If the test fails: check connectivity, the SSH service, the account, and remote authorization. Stop retrying if the fingerprint has changed or the server's identity is uncertain; follow Section 4.3.

3.4 Revoke access before deleting the local key

  1. Confirm that another server-management connection works and that the original key still exists on the device.
  2. Select Revoke on the host row, enter the server password, and confirm Revoke & Remove. You can also start from the key row and enter the target details.
  3. Review the result, then use a trusted server-management connection to check that the public key and any duplicate entries are gone from authorized_keys.
  4. Confirm that the old key can no longer sign in. Revocation leaves an authorized_keys.bak backup; handle it under the server's backup policy so an old authorization is not restored later.
  5. Refresh the local host list. The page attempts to remove the record but does not check that request's result. Remove the record manually if it remains.
  6. Only after every target server is handled should you delete the old key from the device and remove unneeded private-key copies.

If no matching public key is found: confirm on the server that you selected the correct account and that the key is absent before choosing to remove only the local record.

If revocation fails or the server looks suspicious: keep the local key and use a trusted console or another administrator connection. Do not keep sending a password to a server whose identity is in doubt.

4. Manage keys, hosts, and fingerprints

4.1 Copy a public key or export a private key

Public key: select Public Key and copy the complete, single-line value for the server administrator. A public key is not secret. Sending it to the wrong person does not by itself expose the private key or require key replacement. Access is granted only when an administrator adds it to an account's authorization list.

Private key: export is available only if you enabled it when the key was created. Use a trusted computer on an isolated network, store the key in an approved secret store, and clear temporary copies from the clipboard and download folder. Never paste it into chat, tickets, or logs.

If Copy does nothing: browsers may block clipboard access on an HTTP page. Select and copy the visible text manually, then check that the beginning, end, and full contents are intact. Do not weaken browser security settings just to enable copying.

4.2 Revoke, Remove, and Delete are different

ActionEffect
Revoke a public keyAttempts to remove authorization on the server; requires the remote password
Remove a hostDeletes the device's local connection record, not remote authorization
Delete a keyDeletes local key material; does not contact the server or revoke access
Delete a host fingerprintDeletes a saved server-identity record, not the connection record or remote authorization

Deployed Hosts is a local list, not a live view of server authorization. An empty list does not prove that remote access has been removed, and a listed host is not guaranteed to be reachable.

4.3 Check the SSH server fingerprint

A fingerprint identifies the server you are connecting to. This page stores the SHA-256 digest as 64 hexadecimal characters. OpenSSH tools commonly show SHA256:base64 instead. Ask the administrator to provide the same format before comparing; the strings are not directly interchangeable.

After the first connection: open the full fingerprint with View in the host-fingerprint section. Compare it with a value obtained from a server console, asset inventory, or another trusted channel. The table shows only the first 32 characters, which is not enough for the full check. If they differ: stop connecting and investigate in isolation. If you entered an SSH password, treat it as potentially exposed. Use a trusted connection to change it, review sign-in logs, and remove any unwanted public-key authorization. Do not use the suspicious connection to revoke access through this page.

If a previously saved fingerprint changes:

  1. Stop retrying. Do not simply delete the old entry.
  2. Use a trusted console to verify the new fingerprint, IP address, port, asset identity, and maintenance record.
  3. Delete the old fingerprint only after confirming an authorized server rebuild or host-key change.
  4. Reconnect on a controlled network, then view and check the new saved fingerprint.

The current page may show a generic connection error rather than a dedicated fingerprint-comparison dialog.

Protect the SD card: fingerprints are stored locally and synchronized to plaintext JSON on the card. At startup, available SD fingerprint configurations replace the corresponding NVS records. These files are not signed; do not allow untrusted changes to them.

4.4 Import and export SSH host configurations

This dedicated .tscfg workflow is separate from the unfinished general configuration application in Chapter 6. A host package contains the address, port, username, authentication type, and key ID. It contains neither the SSH password nor the private key, and it does not grant access on the server.

To export: on a Developer device, select Export on the host row. Supply and verify the target device's certificate when exporting for another device, then download the package. An ordinary device may show the button, but the backend rejects its export request.

To import:

  1. Confirm that the package was made for this device, the SD card is writable, and the source has been verified through a trusted channel.
  2. Make sure this device already has the correct key referenced by the package. A matching ID alone is not enough; the key material must match the server's authorization.
  3. Select Import Host, choose the file, and review the preview. Enable overwrite only when you intend to replace an existing configuration with the same name.
  4. Confirm and restart as prompted. Import saves the package to the SD card; loading and decryption are attempted at restart.
  5. Check the loaded address, username, port, and key ID, then test the connection. A successful preview is not proof that the package will work. It neither establishes trust in the signer nor checks the recipient fingerprint. The target check happens during loading after restart. Remove an incorrect record and its corresponding SD package to prevent it from loading again. Before replacing the device certificate, also read Section 5.5.

5. Configure HTTPS certificates and mTLS

This chapter is for certificate administrators. The current service on port 443 offers only health, identity, and permission-test endpoints, not the full web interface. With its default settings, startup requires a device private key, a device certificate, and a client CA chain.

5.1 Know which certificate does what

  • The device certificate and private key let the device prove its identity to a connecting client.
  • A client certificate and private key, held by a computer or service, let that client prove its identity to the device.
  • The CA chain installed on the device is used to verify client certificates. It does not automatically make a computer or browser trust the device certificate.

This two-way certificate exchange is called mutual TLS, or mTLS. The client must still trust the CA that issued the device certificate and check its name and permitted uses.

5.2 Generate a device key and certificate request

  1. Under HTTPS Certificate, select Generate Key Pair. This creates a separate ECDSA P-256 private key, unrelated to SSH keys. It cannot be exported through this interface.
  2. If a key already exists, stop and review Section 5.5 before proceeding. Generating another key overwrites the old one.
  3. Select Generate CSR. Enter the device ID (CN), organization (O), and organizational unit (OU), or leave all fields blank.
  4. Send the complete CSR text to your CA administrator. A CSR requests a certificate; it contains no private key and does not install a certificate.

Check names before issuance: the custom-field path does not generate a SAN. With all fields blank, the CN is fixed at TIANSHAN-DEVICE-001; the current IP is included as an IP SAN only if it can be obtained. No DNS SAN is added. Have your CA administrator inspect the CSR and use a controlled issuance process to put the required IP addresses or DNS names in the final certificate's SAN. This form cannot edit SANs. Check the result: refresh the page to confirm that the private key exists. Have the CA administrator inspect the CSR's public key, subject, and SAN, and ensure that the issued certificate has the required server-authentication purpose (EKU).

5.3 Install the device certificate

  1. Obtain a PEM certificate that matches the device's current private key.
  2. Select Install Cert, paste the full text including its boundary markers, and submit.
  3. View the certificate and check its subject, issuer, and validity dates.

The success message means only that the certificate can be parsed and its public key matches the current private key. Installation does not fully validate the trust chain, SAN, EKU, current validity, or subject policy.

The actual client must check the chain, access name, purposes, and validity. If installation reports a key mismatch, locate the certificate issued for the current CSR. Do not generate a new private key simply to clear the error.

5.4 Install the client CA chain and test

  1. Select Install CA and paste one or more PEM CA certificates used to trust your clients.
  2. Keep the HTTP management interface available and schedule a device restart before testing. Installation updates storage but does not actively restart the running service on port 443.
  3. Access the relevant test endpoints using a trusted client certificate with the correct purpose and role.
  4. Repeat with an untrusted certificate or no certificate, and confirm that the connection is rejected.

Check the result: the device presents the intended new certificate; trusted clients can access only the endpoints allowed for their roles, and untrusted clients cannot connect. Handshake and role behavior must be tested on the device, not inferred from an installation message.

5.5 Renew certificates or delete all credentials

Operational note

For certificate expiry alone: you can reuse an uncompromised private key to request a new certificate, install it, and test again. However, Config Packs are tied to the recipient certificate's fingerprint. Even with the same private key, a changed certificate fingerprint causes old packages to be rejected as belonging to another recipient after reinitialization or restart. Arrange replacement packages before changing the certificate.

When replacing the private key: the old CSR and certificate no longer match the new key. This does not revoke the old certificate at the CA. If the old key was exposed, handle revocation and incident response separately. Packages that depend on a lost private key may be unrecoverable. To delete all PKI credentials: Delete Credentials in the certificate section clears the device private key, device certificate, and client CA chain together. Verify your HTTP recovery access and arrange replacement packages before confirming. A backup of the public certificate cannot restore a private key.

After deletion, refresh the page and check for an uninitialized state. Restart and verify that port 443 no longer uses the old credentials. To restore the service, generate a new key, obtain and install a device certificate, install the CA chain, and repeat the tests.

6. Understand Config Pack limitations

A Config Pack is an encrypted, signed .tscfg package. The current implementation can create and inspect packages, but general configuration application is unfinished. Do not rely on it for production fleet configuration, disaster recovery, or proof that settings have changed.

6.1 What the controls currently do

ActionCurrent result

6.2 Verify the source, not just the signature

The recipient currently checks the signature using the certificate included in the package. Signer certificate-chain trust validation is not implemented. The signature covers the ciphertext; do not assume that every displayed metadata field is therefore authenticated. An Official label is not proof of a trusted source either.

Before importing or inspecting a package, use an asset system or an independent, approved channel to confirm the signer certificate fingerprint, target certificate, and intended change. Receiving a certificate and its fingerprint together in one email is not an independent check. The target name shown in the preview is not a substitute for checking the certificate fingerprint.

6.3 Share the device certificate and inspect a package

To provide this device's certificate: select Export Device Certificate, copy the full PEM and displayed fingerprint, and send the public certificate to the sender. Confirm the fingerprint through a separate trusted channel.

To inspect a received package: open Import Config Pack, select or paste the .tscfg file, and select Verify. Review the signer details and check the source. Verification does not apply settings or prove that this device is the recipient. Stop if the source, target, or purpose is unclear.

Even if verification passes, do not rely on the current general Import and Apply controls to configure the device. Use the supported controls on the relevant feature pages and check the actual settings afterward.

6.4 Export a package from a Developer device

  1. Prepare valid JSON configuration files on the SD card and obtain a verified target-device certificate.
  2. Select Export Config Pack, choose the files, enter a name and description, and paste the target certificate.
  3. Generate and download the .tscfg file.
  4. Check the browser download and the saved file under /sdcard/output_config/ separately. If the SD write fails, the API may still return the package for download.

Export does not modify the source settings. Regenerate a package made for the wrong target or an obsolete recipient certificate. Successful export does not establish that the full distribution workflow works: general application on the receiving device is still unfinished.

  1. Restrict device and log access. Current logs may contain the beginning of a private key.

  3. Create and deploy a new RSA key under a new ID. Once it works, delete the old key and exported copies.

In addition to the HTTP, authorization, first-connection trust, and package limitations already described, the inspected build configuration does not enable NVS Encryption, Flash Encryption, or Secure Boot. Do not claim that these mechanisms protect stored private keys or startup integrity. The firmware actually flashed to a device and its eFuse settings require separate checks.

If your use case cannot tolerate these limitations, keep the device out of that network or trust environment until the security owner approves isolation measures or a product fix. Checks in a user guide cannot replace missing product security controls.

上記のパスワード管理など独自に認証を行う API を除き、画面にログインが必要であることだけでは API の直接呼び出しを防げません。ネットワーク隔離が現在の利用条件です。

1.3 操作の準備

  1. アドレスバーの IP が対象機器であり、パソコンも信頼できる管理ネットワークにあることを確認します。
  2. サーバー管理者に SSH アドレス、ポート、ユーザー名を確認します。
  3. 画面から公開鍵を配備したり認可を取り消したりするには、対象アカウントのパスワードが必要で、そのアカウントでパスワードログインが許可されている必要があります。障害調査のためにサーバーの制限を緩めたままにしないでください。
  4. 鍵の削除、認可の取り消し、証明書交換の前に、サーバーコンソール、別の管理者鍵、機器の HTTP 管理画面など、代替経路が使えることを確認します。

2. 機器のログインパスワードを変更する

ここで変えるのは TianShanOS のログインパスワードです。リモートサーバーの SSH パスワードではありません。

2.1 初回ログイン後の変更通知

パスワード変更済みと記録されていないアカウントでは、ログイン後に変更通知が出ます。他で使っていない長いパスワードを設定してください。「稍后修改」（後で変更）を選んで初期パスワードを使い続けないでください。

この通知は、いつでも開けるアカウント設定ではありません。変更済みの admin が再度変更する場合は、root がセキュリティページで設定できます。

2.2 root によるパスワード設定

  1. root でログインし、セキュリティ（「安全」）を開きます。
  2. アカウントセキュリティ（「账号安全」）でroot パスワードを設定（「设置 root 密码」）またはadmin パスワードを設定（「设置 admin 密码」）を選択します。
  3. 同じ新規パスワードを 2 回入力して送信します。入力範囲は 4-64 文字ですが、4 文字は技術的な下限であり、推奨する強度ではありません。

結果の確認：プライベートウィンドウで新しいパスワードのログインを確認してから元のセッションを閉じます。変更しても既存セッションは自動終了しません。

ログインに失敗したら、アカウントと IP を確認します。5 回連続で失敗すると約 5 分間ロックされます。繰り返し推測しないでください。

2.3 admin パスワードのリセット

root はアカウントセキュリティで admin を初期パスワード rm01 に戻し、ログインロックを解除できます。直後に新しいセッションで admin にログインし、新しいパスワードを設定してください。

リセットは一時的な復旧手段です。初期パスワードを常用しないでください。また、パスワード変更が既存セッションをすべて無効にするわけではありません。

3. SSH 鍵でサーバーに接続する

初回は RSA 鍵の生成 → 公開鍵の配備 → 接続テスト → サーバーの識別確認の順で進めます。廃止時はリモート側の認可を取り消し、ログインできないことを確認してからローカル鍵を削除します。

3.1 鍵を生成する

  1. 鍵管理（「密钥管理」）で新しい鍵を生成（「生成新密钥」）を選択します。
  2. 既存一覧を確認し、backup01 など未使用の鍵 ID を入力します。現在は重複 ID を拒否しないため、既存 ID を使うと元の鍵を上書きするおそれがあります。
  3. RSA 2048 または RSA 4096 を選びます。既定は RSA 2048 です。ECDSA も表示されますが、現在の SSH 公開鍵認証では使えません。
  4. 必要なら備考と別名を入力します。秘密鍵のバックアップ・移行が必要な場合だけ秘密鍵のエクスポートを許可（「允许导出私钥」）を選択してください。生成後にこの属性を変える画面はありません。
  5. 生成（「生成」）を選び、完了後に一覧を更新します。

結果の確認：正しい ID と RSA の種類を確認し、公開鍵（「公钥」）で全文が ssh-rsa から始まることを確かめます。

注意：一覧の上限は 8 個です。満杯なら生成を続けず、取り消し手順に従って古い鍵を整理してください。保存と一覧登録は一体として完了するとは限らないため、成功通知後も一覧を確認します。鍵 ID を非表示（「隐藏密钥 ID」）は、API から実際の ID が読まれることを防ぎません。

3.2 公開鍵を配備する

配備はリモートアカウントの ~/.ssh/authorized_keys に公開鍵を追加し、対応する秘密鍵でのログインを可能にするための処理です。サーバーのパスワードは変更しません。

  1. 新しい鍵の行で配備（「部署」）を選びます。
  2. サーバーアドレス、ユーザー名、SSH ポート、そのアカウントのパスワードを入力します。
  3. 確認して配備を開始（「开始部署」）を選びます。
  4. 完了後、登録済みホスト（「已部署主机」）の記録を確認し、次節のテストを行います。

現在の処理はパスワードで SSH 認証した後にホストのフィンガープリントを確認し、初めてのホストを自動で信頼します。サーバーの識別を確認してからパスワードを送る保証はありません。初回接続は管理されたネットワークで行ってください。後でフィンガープリントを照合しても、すでにパスワードを送信したリスクは消えません。

成功表示後に記録がない、またはテストが失敗した場合は、すぐに再配備しないでください。公開鍵の書き込みは済み、鍵ログインの再確認やローカル保存だけが失敗した可能性があります。別の管理経路から authorized_keys を調べてください。繰り返すと重複行が追加される場合があります。

3.3 接続をテストして結果を確認する

  1. 登録済みホスト（「已部署主机」）でアドレス、ポート、ユーザー名、鍵 ID を確認します。
  2. テスト（「测试」）を選びます。機器は固定コマンド echo "TianshanOS SSH Test OK" の実行を試みます。
  3. 初回接続後、第 4.3 節に従って保存されたホストフィンガープリントを照合します。

成功表示の意味：画面は API 要求の成否だけを見ており、リモートコマンドの終了コードと出力内容は確認しません。基本的な接続確認であり、完全な受け入れ試験でも sudo や業務コマンドの動作証明でもありません。重要な用途では実際のタスクで出力、終了コード、権限を確認してください。

失敗したらネットワーク、SSH サービス、アカウント、リモート認可を確認します。フィンガープリント変更やサーバーの身元不明が関わる場合は再試行を止め、第 4.3 節に従ってください。

3.4 リモート認可を取り消してからローカル鍵を削除する

  1. 別のサーバー管理経路が使え、機器の元の鍵が残っていることを確認します。
  2. 登録済みホスト（「已部署主机」）の対象行で認可を取り消す（「撤销」）を選び、サーバーパスワードを入力して認可を取り消して除去（「撤销并移除」）を確認します。鍵の行から対象情報を入力して開始することもできます。
  3. 結果を確認し、信頼できるサーバー管理経路から authorized_keys を調べ、対象公開鍵と重複行が消えていることを確かめます。
  4. 古い鍵でログインできないことを確認します。authorized_keys.bak が残るため、古い認可を復元しないようサーバーのバックアップ方針に沿って扱います。
  5. ローカル一覧を更新します。画面は記録の削除を試みますが結果を確認しないため、必要なら手動で除去（「移除」）します。
  6. すべての対象サーバーを処理してから、機器の古い鍵と不要な秘密鍵のコピーを削除します。

公開鍵が見つかりません（「未找到公钥」）と表示されたら、サーバー側で対象アカウントが正しく、公開鍵が本当にないことを確認してからローカル記録だけを削除します。

失敗した場合やサーバーの身元が疑わしい場合は、ローカル鍵を残し、信頼できるコンソールや別の管理経路で処理してください。疑わしいサーバーにパスワードを送り続けないでください。

4. 鍵・ホスト・フィンガープリントの管理

4.1 公開鍵のコピーと秘密鍵のエクスポート

公開鍵：公開鍵（「公钥」）で完全な 1 行をコピーし、サーバー管理者に渡します。公開鍵は秘密情報ではありません。誤送信だけで秘密鍵が漏れたことにはならず、直ちに鍵交換が必要になるわけでもありません。管理者が認可一覧に追加して初めてアクセス権が生じます。

秘密鍵：生成時にエクスポートを許可した鍵だけが秘密鍵（「私钥」）から取り出せます。信頼できるパソコンと隔離ネットワークで操作し、管理された鍵保管庫に保存して、クリップボードやダウンロード先の一時コピーを消してください。チャット、問い合わせ票、ログに貼り付けないでください。

コピーできない場合：HTTP ではブラウザーのクリップボード API が使えないことがあります。表示テキストを手動で選択してコピーし、先頭・末尾・全文を確認してください。コピーのためにブラウザーの保護を緩めないでください。

4.2 取り消し・除去・削除の違い

操作変更内容
公開鍵の取り消しサーバーの認可削除を試みます。リモートのパスワードが必要です
ホストの除去機器内の接続記録だけを消します。サーバーの認可は残ります
鍵の削除機器内の鍵を消します。サーバーには接続せず、認可も取り消しません
既知ホストフィンガープリントの削除保存したサーバーの識別記録を消します。接続記録やサーバー認可は残ります

登録済みホスト（「已部署主机」）はローカル一覧で、サーバーを継続照会しません。空でもリモート認可が消えた証拠にはならず、記録があっても現在ログインできるとは限りません。

4.3 SSH サーバーのフィンガープリントを照合する

フィンガープリントは接続先サーバーを識別するための値です。現在の画面は SHA-256 ダイジェストを 64 桁の 16 進数で保存しますが、一般的な OpenSSH は SHA256:base64 を出力します。管理者に形式をそろえてもらってください。文字列をそのまま比較することはできません。

初回接続後：既知ホストのフィンガープリント（「已知主机指纹」）の表示（「查看」）で全文を開き、サーバーコンソール、資産管理システムなど別の信頼できる経路の値と照合します。表には先頭 32 桁しか表示されないため、それだけでは不十分です。

不一致の場合：接続を止め、隔離して調査します。SSH パスワードを入力済みなら漏えいの可能性として扱い、信頼できる経路から変更し、ログインログと不正な公開鍵を調べます。疑わしい接続で画面の取り消し処理を行わないでください。

保存済みのフィンガープリントが変わった場合：

  1. 再試行を止め、旧記録をすぐに消さないでください。
  2. 信頼できるコンソールで新しいフィンガープリント、IP、ポート、資産の識別情報、保守記録を照合します。
  3. 再インストールや正規の鍵交換だと確認できてから旧フィンガープリントを削除します。
  4. 管理されたネットワークで再接続し、新しい記録をもう一度照合します。

専用の比較ダイアログが出ず、一般的な接続エラーだけが表示される場合があります。

SD カードの管理：フィンガープリントは機器ストレージに保存され、SD カードにも平文 JSON で同期されます。起動時に SD のフィンガープリント設定があれば、それを優先して対応する NVS 記録を置き換えます。署名による保護はありません。信頼できない人に SD カードを変更させないでください。

4.4 SSH ホスト設定のインポート・エクスポート

これは専用の .tscfg 手順で、第 6 章の未完成な汎用適用とは別です。アドレス、ポート、ユーザー、認証種別、鍵 ID を保存します。SSH パスワードや秘密鍵は含まず、リモート権限も付与しません。

エクスポート：Developer 機器でホスト行のエクスポート（「导出」）を選びます。別機器向けなら対象の機器証明書を入力・照合してからダウンロードします。通常機器はボタンが見えてもバックエンドが拒否します。

インポート：

  1. 本機器向けのパッケージで、SD カードが書き込み可能であることを確認し、信頼できる経路で出所を照合します。
  2. 参照される正しい鍵が本機器にあることを確認します。ID の一致だけでは足りず、鍵自体がサーバーの認可と対応している必要があります。
  3. ホスト設定のインポートを開き、ファイルとプレビューを確認します。同名設定を置き換える場合だけ上書きを選択します。
  4. 確認後、案内に従って再起動します。インポートは SD に保存するだけで、読み込みと復号は再起動時に試みます。
  5. 読み込まれたアドレス、ユーザー、ポート、鍵 ID を確認して接続テストを行います。

プレビュー成功は利用可能の証明ではありません。署名者の信頼性も受信機器のフィンガープリントも確認しておらず、対象の確認は再起動時です。誤った記録は削除し、SD の該当パッケージも除いて再読込を防いでください。機器証明書の交換前には第 5.5 節もお読みください。

5. HTTPS 証明書と mTLS の設定

証明書管理者向けの章です。現在の 443 サービスは健全性・識別・権限テスト API のみを提供し、完全な管理画面は提供しません。既定の起動には機器秘密鍵、機器証明書、クライアント CA チェーンがすべて必要です。

5.1 証明書の役割を区別する

  • 機器秘密鍵・証明書：接続してくるクライアントに機器の身元を示します。
  • クライアント証明書・秘密鍵：パソコンやサービスが持ち、機器にクライアントの身元を示します。
  • 機器に入れる CA チェーン：クライアント証明書を検証します。パソコンやブラウザーが機器証明書を自動で信頼するようになるわけではありません。

双方が証明書を提示する方式が mTLS です。クライアント側でも機器証明書の CA を信頼する設定と、接続名・用途の検証が必要です。

5.2 機器秘密鍵と証明書署名要求を生成する

  1. HTTPS 証明書（「HTTPS 证书」）で鍵ペアを生成（「生成密钥对」）を選びます。SSH とは別の ECDSA P-256 秘密鍵を生成します。この画面ではエクスポートできません。
  2. 既存鍵がある場合は中断し、第 5.5 節で影響を確認します。続けると上書きされます。
  3. CSR を生成（「生成 CSR」）で機器 ID（CN）、組織（O）、組織単位（OU）を入力するか、すべて空欄にします。
  4. CSR 全文を CA 管理者に渡します。CSR は申請であり、秘密鍵は含まず、証明書の自動インストールも行いません。

発行前の名前確認：項目を指定する経路では SAN を生成しません。全空欄なら CN は TIANSHAN-DEVICE-001 固定で、現在の IP が取得できる場合だけその IP の SAN を追加します。DNS SAN はありません。CA 管理者が CSR を調べ、管理された発行手順で実際の IP/DNS を最終証明書の SAN に加えてください。このフォームでは SAN を編集できません。

結果の確認：更新後に秘密鍵の存在を確認します。CA 管理者が CSR を解析し、公開鍵、主体、SAN と、最終証明書に必要なサーバー認証用途（EKU）があることを確認します。

5.3 機器証明書をインストールする

  1. 現在の機器秘密鍵に対応する PEM 証明書を用意します。
  2. 証明書をインストール（「安装证书」）に開始・終了マーカーを含む全文を貼り付けて送信します。
  3. 証明書を表示し、主体、発行者、有効期間を確認します。

成功通知が示すのは解析可能で、公開鍵が現在の秘密鍵と一致することだけです。信頼チェーン、SAN、EKU、現在の有効性、主体ポリシーの完全な検証は行いません。

実際のクライアントがチェーン、接続先、用途、有効期間を確認して初めて信頼性を判断できます。鍵不一致なら現在の CSR に対応する証明書を探してください。エラーを消すためだけに秘密鍵を再生成しないでください。

5.4 クライアント CA チェーンを入れてテストする

  1. CA をインストール（「安装 CA」）に、クライアント証明書を信頼するための PEM CA 証明書を 1 つ以上貼り付けます。
  2. HTTP 管理経路を残し、再起動を予定してからテストします。インストール API はストレージのみを更新し、稼働中の 443 サービスを再起動しません。
  3. 信頼され、用途とロールが正しいクライアント証明書で対応するテストエンドポイントに接続します。
  4. 信頼されない証明書、または証明書なしでも試し、拒否を確認します。

結果の確認：機器が意図した新証明書を使い、信頼できるクライアントも自分のロールに許可された API だけにアクセスでき、信頼されないクライアントは接続できないことを確認します。ハンドシェイクとロールの挙動は実機試験が必要で、インストール通知だけでは確認できません。

5.5 証明書の更新と全資格情報の削除

期限切れのみ：漏えいしていない秘密鍵を継続使用して新証明書を申請し、インストール後に再テストできます。ただし設定パッケージは受信側の証明書フィンガープリントに結び付いています。同じ秘密鍵でも新証明書のフィンガープリントが変わると、再初期化や再起動で読む古いパッケージは対象不一致で拒否されます。残す必要のあるパッケージを事前に作り直してください。

秘密鍵交換：古い証明書と CSR は新しい鍵と対応しません。古い証明書が CA によって失効したという意味ではありません。漏えい時は別途失効・事故対応が必要です。古い秘密鍵がなければ、それに依存するパッケージは復旧できない場合があります。

全 PKI 資格情報の削除：資格情報を削除（「删除凭证」）は機器秘密鍵、証明書、クライアント CA チェーンをまとめて消します。HTTP 管理経路と代替パッケージの準備を確認してから実行してください。公開証明書のバックアップでは秘密鍵は復元できません。

削除後にページを更新して未初期化と表示されること、再起動後に 443 が古い資格情報を使わないことを確認します。再有効化には秘密鍵生成、証明書発行、CA チェーンのインストールとテストが必要です。

6. Config Pack の利用前に制限を確認する

Config Pack は暗号化・署名された .tscfg 設定パッケージです。現在は生成と検査ができますが、汎用の設定適用は未完成です。本番の一括設定、災害復旧、設定反映の証明には使わないでください。

6.2 署名有効の表示だけでなく出所を確認する

受信機器はパッケージ内の証明書で署名を確認し、署名者の信頼チェーンを検証していません。署名が保護するのは暗号文で、すべての表示項目が信頼できる認証を受けたとは言えません。公式（「官方」）も出所の証明にはなりません。

インポート・検査前に、資産管理システムや管理者が認める独立経路で署名者の証明書フィンガープリント、対象機器証明書、用途を確認してください。同じメールに添付された証明書とフィンガープリントだけで信頼を判断しないでください。プレビューの対象名もフィンガープリント照合の代わりにはなりません。

6.3 機器証明書の提供と受信パッケージの検査

機器証明書の提供：機器証明書をエクスポート（「导出设备证书」）で PEM 全文と表示されたフィンガープリントをコピーし、公開証明書を送信者に渡して、別の信頼できる経路でフィンガープリントを照合します。

受信パッケージの検査：設定パッケージをインポート（「导入配置包」）で .tscfg を選ぶか貼り付け、検証（「验证」）を選択します。署名者と出所を確認します。検証は設定を適用せず、本機器向けであることも証明しません。出所不明、対象不一致、用途不明なら中断してください。

検証に通っても現在の汎用インポート・適用に依存しないでください。各機能のページに戻り、対応済みの方法で設定し、実際の結果を確認します。

6.4 Developer 機器からエクスポートする

  1. SD カードに有効な JSON 設定ファイルを用意し、照合済みの対象機器証明書を入手します。
  2. 設定パッケージをエクスポート（「导出配置包」）でファイルを選び、名前と説明を入力し、対象証明書を貼り付けます。
  3. 生成後に .tscfg をダウンロードします。
  4. ブラウザーのファイルと /sdcard/output_config/ の保存結果を別々に確認します。SD 保存に失敗しても、API がダウンロード用データを返す場合があります。

元の設定は変更されません。対象が誤っている、または受信側証明書が交換された場合は再生成が必要です。受信側の汎用適用は未完成なので、エクスポート成功だけで配布フロー全体が使えるとは判断できません。

7.3 現バージョンで残るリスク

許容できない用途ではネットワーク接続を停止し、セキュリティ責任者が隔離策または製品修正を判断してください。操作ガイドの確認手順は、欠けている製品のセキュリティ制御の代わりにはなりません。

8.2 用語

  • 公開鍵・秘密鍵：公開鍵は認可する側に渡せますが、秘密鍵は秘密に保ちます。サーバーは公開鍵を認可し、機器は対応する秘密鍵でログインします。
  • NVS：Flash 内の設定・鍵保存領域です。名称自体は暗号化を意味しません。
  • CSR・CA：CSR は証明書署名要求、CA は証明書を発行・検証する認証局またはその証明書です。
  • CN・O・OU：証明書主体のコモンネーム、組織、組織単位です。
  • SAN・EKU：利用できる接続名・IP と、認証用途をそれぞれ表します。
  • PEM：BEGIN/END マーカー付きのテキスト形式で、証明書、CSR、鍵に使います。
  • PKI・mTLS：PKI は証明書と信頼の管理基盤、mTLS はクライアントとサーバー双方が証明書を提示する接続方式です。

2. 장치 로그인 비밀번호 변경

여기서 바꾸는 것은 TianShanOS 로그인 비밀번호이며 원격 서버의 SSH 비밀번호가 아닙니다.

2.1 첫 로그인 후 비밀번호 알림

비밀번호 변경 완료로 표시되지 않은 계정은 로그인 후 알림이 나타납니다. 다른 곳에서 사용하지 않는 긴 비밀번호를 설정하세요. ‘稍后修改’(나중에 변경)를 선택한 뒤 초기 비밀번호를 계속 사용하지 마세요.

이 알림은 언제든 열 수 있는 계정 설정 화면이 아닙니다. 이미 변경한 admin이 다시 바꾸려면 root가 보안 페이지에서 설정할 수 있습니다.

2.2 root가 비밀번호 설정

  1. root로 로그인하고 보안(‘安全’)을 엽니다.
  2. 계정 보안(‘账号安全’)에서 root 비밀번호 설정(‘设置 root 密码’) 또는 admin 비밀번호 설정(‘设置 admin 密码’)를 선택합니다.
  3. 동일한 새 비밀번호를 두 번 입력하고 제출합니다. 4-64자를 허용하지만 4자는 기술적 최솟값일 뿐 보안 권장 길이가 아닙니다.

결과 확인: 시크릿 창에서 새 비밀번호로 로그인한 뒤 기존 세션을 닫습니다. 비밀번호를 변경해도 기존 세션은 자동 종료되지 않습니다.

로그인 실패 시 계정과 IP를 먼저 확인하세요. 5회 연속 실패하면 약 5분간 잠깁니다. 반복해서 추측하지 마세요.

2.3 admin 비밀번호 초기화

root는 계정 보안에서 admin을 기본 비밀번호 rm01로 되돌리고 로그인 잠금을 해제할 수 있습니다. 초기화 직후 새 세션에서 admin으로 로그인하여 새 비밀번호를 설정하세요.

초기화는 임시 복구 수단입니다. 기본 비밀번호를 일상적으로 사용하지 마세요. 비밀번호 변경이 모든 기존 세션을 강제 종료한다는 뜻도 아닙니다.

3. SSH 키로 서버 연결

처음에는 RSA 키 생성 → 공개키 배포 → 연결 시험 → 서버 신원 확인 순서로 진행합니다. 폐기할 때는 원격 권한을 철회하고 로그인이 불가능한지 확인한 뒤 로컬 키를 삭제합니다.

3.1 키 생성

  1. 키 관리(‘密钥管理’)에서 새 키 생성(‘生成新密钥’)를 선택합니다.
  2. 기존 목록을 확인한 뒤 backup01처럼 사용하지 않은 키 ID를 입력합니다. 현재 중복 ID를 차단하지 않으므로 재사용하면 기존 키를 덮어쓸 수 있습니다.
  3. RSA 2048 또는 RSA 4096을 선택합니다. 기본값은 RSA 2048입니다. ECDSA도 표시되지만 현재 SSH 공개키 인증에서는 지원하지 않습니다.
  4. 필요하면 메모와 별칭을 입력합니다. 개인키 백업·이전이 꼭 필요할 때만 개인키 내보내기 허용(‘允许导出私钥’)를 선택하세요. 생성 후 이 속성을 바꾸는 화면은 없습니다.
  5. 생성(‘生成’)을 선택하고 완료 후 목록을 새로고침합니다.

결과 확인: 올바른 ID와 RSA 유형을 찾고 공개키(‘公钥’)에서 전체 텍스트가 ssh-rsa로 시작하는지 확인합니다.

주의: 키 목록은 최대 8개입니다. 가득 차면 계속 생성하지 말고 철회 절차로 이전 키를 정리하세요. 저장과 목록 등록은 완전한 원자적 작업이 아니므로 성공 메시지 후에도 목록을 확인해야 합니다. 키 ID 숨기기(‘隐藏密钥 ID’)는 API에서 실제 ID를 읽는 것을 막지 않습니다.

3.2 공개키 배포

배포는 원격 계정의 ~/.ssh/authorized_keys에 공개키를 추가하여 대응하는 개인키로 로그인할 수 있도록 하는 작업입니다. 서버 비밀번호는 바꾸지 않습니다.

  1. 새 키 행에서 배포(‘部署’)를 선택합니다.
  2. 서버 주소, 사용자 이름, SSH 포트, 해당 계정 비밀번호를 입력합니다.
  3. 확인한 뒤 배포 시작(‘开始部署’)를 선택합니다.
  4. 완료 후 배포된 호스트(‘已部署主机’)에서 기록을 확인하고 다음 절의 시험을 진행합니다.

현재 절차는 비밀번호로 SSH 인증을 마친 뒤 호스트 지문을 검사하며 처음 만나는 호스트는 자동으로 신뢰합니다. 서버 신원을 확인한 후 비밀번호를 전송한다는 보장은 없습니다. 첫 연결은 통제된 네트워크에서 해야 합니다. 사후 지문 확인으로 이미 비밀번호가 전송된 위험을 없앨 수는 없습니다.

성공했지만 기록이 없거나 시험에 실패해도 바로 다시 배포하지 마세요. 공개키는 이미 기록되었고 키 로그인 재검증이나 로컬 저장만 실패했을 수 있습니다. 다른 관리 경로에서 authorized_keys를 확인하세요. 반복 배포하면 중복 행이 생길 수 있습니다.

3.3 연결 시험 및 결과 확인

  1. 배포된 호스트(‘已部署主机’)에서 주소, 포트, 사용자 이름, 키 ID를 확인합니다.
  2. 테스트(‘测试’)를 선택합니다. 장치는 고정 명령 echo "TianshanOS SSH Test OK" 실행을 시도합니다.
  3. 첫 연결 후 4.3절에 따라 저장된 호스트 지문을 확인합니다.

성공 메시지의 의미: 화면은 API 요청 성공 여부만 확인하며 원격 명령의 종료 코드와 출력은 검사하지 않습니다. 기본 연결 시험일 뿐 완전한 검증이 아니며 sudo나 업무 명령의 사용 가능 여부를 증명하지도 않습니다. 중요한 용도라면 실제 작업에서 출력, 종료 코드, 권한을 확인하세요.

실패하면 네트워크, SSH 서비스, 계정, 원격 권한을 확인합니다. 지문이 바뀌었거나 서버 신원이 불명확하면 재시도를 멈추고 4.3절에 따르세요.

3.4 원격 권한 철회 후 로컬 키 삭제

  1. 다른 서버 관리 경로가 있고 장치에 기존 키가 남아 있는지 확인합니다.
  2. 배포된 호스트(‘已部署主机’)의 대상 행에서 권한 철회(‘撤销’)를 선택하고 서버 비밀번호를 입력한 뒤 권한 철회 및 제거(‘撤销并移除’)를 확인합니다. 키 행에서 시작하여 대상 정보를 입력할 수도 있습니다.
  3. 결과를 확인한 뒤 신뢰할 수 있는 서버 관리 경로로 authorized_keys에서 해당 공개키와 중복 행이 제거되었는지 확인합니다.
  4. 이전 키로 로그인할 수 없는지 확인합니다. authorized_keys.bak가 남으므로 이전 권한이 복구되지 않도록 서버 백업 정책에 따라 처리합니다.
  5. 로컬 목록을 새로고침합니다. 화면은 기록 제거를 시도하지만 결과는 확인하지 않으므로 필요하면 제거(‘移除’)를 직접 실행합니다.
  6. 모든 대상 서버를 처리한 뒤 장치의 이전 키와 불필요한 개인키 사본을 삭제합니다.

공개키를 찾을 수 없음(‘未找到公钥’)가 표시되면 서버에서 올바른 계정인지, 공개키가 정말 없는지 확인한 뒤 로컬 기록만 제거합니다.

철회에 실패하거나 서버 신원이 의심스러우면 로컬 키를 보존하고 신뢰할 수 있는 콘솔이나 다른 관리자 경로로 처리하세요. 의심스러운 서버에 비밀번호를 계속 보내지 마세요.

4. 키·호스트·지문 관리

4.1 공개키 복사 및 개인키 내보내기

공개키: 공개키(‘公钥’)에서 한 줄 전체를 복사해 서버 관리자에게 전달합니다. 공개키는 비밀이 아닙니다. 잘못 전달했다고 개인키가 유출된 것은 아니며 즉시 교체해야 하는 것도 아닙니다. 관리자가 별도로 허용 목록에 추가해야 접근 권한이 생깁니다.

개인키: 생성 시 내보내기를 허용한 키만 개인키(‘私钥’)에서 내보낼 수 있습니다. 신뢰할 수 있는 컴퓨터와 격리 네트워크에서 작업하고 통제된 키 저장소에 보관하세요. 클립보드와 다운로드 폴더의 임시 사본을 지우고 채팅, 지원 티켓, 로그에 붙여 넣지 마세요.

복사가 되지 않을 때: HTTP 페이지에서는 브라우저 클립보드 API가 동작하지 않을 수 있습니다. 보이는 텍스트를 직접 선택해 복사한 뒤 시작, 끝, 전체 내용이 온전한지 확인하세요. 복사를 위해 브라우저 보안 설정을 완화하지 마세요.

4.2 철회·제거·삭제 구분

작업변경 사항
공개키 철회서버의 권한 제거를 시도합니다. 원격 비밀번호가 필요합니다
호스트 제거장치의 로컬 연결 기록만 지우고 서버 권한은 유지합니다
키 삭제장치의 로컬 키만 지웁니다. 서버에 접속하거나 권한을 철회하지 않습니다
알려진 호스트 지문 삭제저장한 서버 신원 기록만 지웁니다. 연결 기록과 서버 권한은 유지합니다

배포된 호스트(‘已部署主机’)는 로컬 목록이며 서버를 지속해서 조회하지 않습니다. 비어 있다고 원격 권한이 제거된 것은 아니며 기록이 있다고 현재 로그인할 수 있다는 뜻도 아닙니다.

4.3 SSH 서버 지문 확인

지문은 접속 서버를 식별하는 값입니다. 현재 화면은 SHA-256 요약을 64자리 16진수로 저장하며 일반적인 OpenSSH 출력은 SHA256:base64입니다. 관리자에게 형식을 통일해 달라고 요청하세요. 두 문자열을 그대로 비교할 수는 없습니다.

첫 연결 후 알려진 호스트 지문(‘已知主机指纹’)의 보기(‘查看’)에서 전체 값을 열고 서버 콘솔, 자산 관리 시스템 등 별도의 신뢰할 수 있는 경로에서 받은 값과 비교합니다. 표에는 앞 32자리만 표시되어 충분하지 않습니다.

불일치하면 연결을 중단하고 격리하여 조사합니다. SSH 비밀번호를 입력했다면 유출 가능성으로 취급하고 신뢰할 수 있는 경로에서 비밀번호를 바꾸며 로그인 로그와 불필요한 공개키를 점검합니다. 의심스러운 연결로 페이지의 철회를 실행하지 마세요.

저장된 지문이 변경되었을 때:

  1. 재시도를 멈추고 기존 기록을 바로 지우지 않습니다.
  2. 신뢰할 수 있는 콘솔로 새 지문, IP, 포트, 자산 신원, 유지보수 기록을 확인합니다.
  3. 서버 재설치나 정상적인 키 교체임을 확인한 뒤에만 기존 지문을 지웁니다.
  4. 통제된 네트워크에서 다시 연결하고 새 기록을 재확인합니다.

현재 화면에는 전용 지문 비교 창 대신 일반 연결 오류만 나타날 수 있습니다.

SD 카드 관리: 지문은 장치 저장소에 저장되고 SD 카드에도 평문 JSON으로 동기화됩니다. 부팅 시 SD 지문 설정이 있으면 이를 우선하여 해당 NVS 기록을 대체합니다. 파일에는 서명 보호가 없습니다. 신뢰할 수 없는 사람이 SD 카드를 수정하지 못하게 하세요.

4.4 SSH 호스트 설정 가져오기 및 내보내기

이것은 전용 .tscfg 절차이며 6장의 미완성 범용 적용과 다릅니다. 주소, 포트, 사용자, 인증 유형, 키 ID를 저장하지만 SSH 비밀번호나 개인키를 포함하지 않고 원격 권한도 부여하지 않습니다.

내보내기: Developer 장치의 호스트 행에서 내보내기(‘导出’)를 선택합니다. 다른 장치용이면 대상 장치 인증서를 제공하고 확인한 뒤 다운로드합니다. 일반 장치는 버튼이 보여도 백엔드가 거부합니다.

가져오기:

  1. 현재 장치용 패키지인지, SD 카드에 쓸 수 있는지 확인하고 신뢰할 수 있는 경로로 출처를 확인합니다.
  2. 패키지가 참조하는 올바른 키가 현재 장치에 있는지 확인합니다. ID만 같아서는 안 되며 키 자체가 서버 권한과 맞아야 합니다.
  3. 호스트 설정 가져오기를 열어 파일과 미리보기를 확인합니다. 같은 이름의 설정을 바꿀 때만 덮어쓰기를 선택합니다.
  4. 확인 후 안내에 따라 재시작합니다. 가져오기는 SD에 저장만 하며 로드와 복호화는 재시작할 때 시도합니다.
  5. 로드된 주소, 사용자, 포트, 키 ID를 확인한 뒤 연결을 시험합니다.

미리보기 통과는 사용 가능하다는 뜻이 아닙니다. 서명자 신뢰성과 수신 장치 지문을 확인하지 않으며 대상 검사는 재시작 시에 합니다. 잘못된 기록과 SD의 해당 패키지를 함께 지워 재로드를 막으세요. 장치 인증서 교체 전에는 5.5절도 읽으세요.

5. HTTPS 인증서 및 mTLS 설정

인증서 관리자용 내용입니다. 현재 443 서비스는 상태·신원·권한 시험 API만 제공하고 전체 관리 페이지는 제공하지 않습니다. 기본 시작에는 장치 개인키, 장치 인증서, 클라이언트 CA 체인이 모두 필요합니다.

5.1 인증서의 방향 구분

  • 장치 개인키와 인증서: 접속하는 클라이언트에 장치 신원을 증명합니다.
  • 클라이언트 인증서와 개인키: 컴퓨터나 서비스가 보유하여 장치에 클라이언트 신원을 증명합니다.
  • 장치에 설치하는 CA 체인: 클라이언트 인증서를 검증합니다. 컴퓨터나 브라우저가 장치 인증서를 자동으로 신뢰하게 하지는 않습니다.

양쪽 모두 인증서를 제시하는 방식이 mTLS입니다. 클라이언트도 장치 인증서의 CA를 신뢰하도록 설정하고 접속 이름과 인증서 용도를 검증해야 합니다.

5.2 장치 개인키와 인증서 요청 생성

  1. HTTPS 인증서(‘HTTPS 证书’)에서 키 쌍 생성(‘生成密钥对’)를 선택합니다. SSH와 별개인 ECDSA P-256 개인키를 생성하며 이 화면에서는 내보낼 수 없습니다.
  2. 기존 개인키가 있으면 중단하고 5.5절에서 교체 영향을 확인합니다. 계속하면 기존 키를 덮어씁니다.
  3. CSR 생성(‘生成 CSR’)에서 장치 ID(CN), 조직(O), 조직 단위(OU)를 입력하거나 모두 비워 둡니다.
  4. CSR 전체를 CA 관리자에게 전달합니다. CSR은 인증서 요청이며 개인키를 포함하거나 인증서를 자동 설치하지 않습니다.

발급 전 이름 확인: 필드를 직접 지정하는 경로에서는 SAN이 생성되지 않습니다. 모두 비우면 CN은 TIANSHAN-DEVICE-001로 고정되고 현재 IP를 얻을 수 있을 때만 해당 IP SAN을 추가합니다. DNS SAN은 없습니다. CA 관리자가 CSR을 확인하고 통제된 발급 절차로 실제 접속 IP/DNS를 최종 인증서 SAN에 추가해야 합니다. 이 양식에서는 SAN을 편집할 수 없습니다.

결과 확인: 새로고침 후 개인키가 있는지 확인합니다. CA 관리자가 CSR의 공개키, 주체, SAN을 확인하고 최종 인증서에 필요한 서버 인증 용도(EKU)가 있는지 검증합니다.

5.3 장치 인증서 설치

  1. 현재 장치 개인키와 일치하는 PEM 인증서를 준비합니다.
  2. 인증서 설치(‘安装证书’)에 시작·끝 표시를 포함한 전체 텍스트를 붙여 넣고 제출합니다.
  3. 인증서의 주체, 발급자, 유효 기간을 확인합니다.

성공 메시지는 인증서를 파싱할 수 있고 공개키가 현재 개인키와 일치한다는 뜻일 뿐입니다. 신뢰 체인, SAN, EKU, 현재 유효성, 주체 정책을 완전히 검증하지는 않습니다.

실제 클라이언트가 체인, 접속 주소, 용도, 유효 기간을 확인해야 신뢰 여부를 판단할 수 있습니다. 키 불일치 오류가 나면 현재 CSR에 맞는 인증서를 찾으세요. 오류를 없애기 위해 개인키를 다시 생성하지 마세요.

5.4 클라이언트 CA 체인 설치 및 시험

  1. CA 설치(‘安装 CA’)에 클라이언트 인증서를 신뢰하기 위한 PEM CA 인증서를 하나 이상 붙여 넣습니다.
  2. HTTP 관리 경로를 유지하고 장치 재시작을 계획한 뒤 시험합니다. 설치 API는 저장소만 갱신하고 실행 중인 443 서비스를 재시작하지 않습니다.
  3. 신뢰할 수 있고 용도와 역할이 올바른 클라이언트 인증서로 해당 시험 엔드포인트에 접속합니다.
  4. 신뢰하지 않는 인증서 또는 인증서 없이도 시험하여 연결이 거부되는지 확인합니다.

결과 확인: 장치가 의도한 새 인증서를 사용하고, 신뢰하는 클라이언트도 역할에 허용된 API만 사용하며, 신뢰하지 않는 클라이언트는 접속할 수 없어야 합니다. 핸드셰이크와 역할 동작은 실제 장치에서 검증해야 하며 설치 알림만으로 확인할 수 없습니다.

5.5 인증서 갱신 및 모든 자격 증명 삭제

인증서만 만료된 경우: 유출되지 않은 개인키를 유지하여 새 인증서를 신청하고 설치 후 다시 시험할 수 있습니다. 다만 패키지는 수신 인증서 지문에 묶입니다. 같은 개인키라도 새 인증서 지문이 달라지면 재초기화나 재시작 시 로드하는 이전 패키지는 대상 불일치로 거부됩니다. 필요한 패키지를 교체 전에 다시 만드세요.

개인키 교체: 이전 인증서와 CSR은 새 키에 맞지 않습니다. 그렇다고 CA가 이전 인증서를 폐기한 것은 아닙니다. 유출되었다면 별도의 인증서 폐기와 사고 대응이 필요합니다. 이전 개인키가 없으면 이에 의존하는 패키지를 복구하지 못할 수 있습니다.

모든 PKI 자격 증명 삭제: 자격 증명 삭제(‘删除凭证’)는 장치 개인키, 인증서, 클라이언트 CA 체인을 함께 지웁니다. HTTP 관리 경로와 패키지 대체 준비를 확인한 뒤 삭제하세요. 공개 인증서 백업으로 개인키를 복원할 수는 없습니다.

삭제 후 새로고침하면 미초기화 상태여야 합니다. 재시작 후 443이 이전 자격 증명을 쓰지 않는지 확인합니다. 다시 켜려면 개인키 생성, 인증서 발급, CA 체인 설치와 시험을 다시 해야 합니다.

6. Config Pack 사용 전 제한 확인

8.2 주요 용어

  • 공개키·개인키: 공개키는 권한을 부여할 상대에게 전달할 수 있지만 개인키는 비밀로 유지해야 합니다. 서버는 공개키를 허용하고 장치는 대응 개인키로 로그인합니다.
  • NVS: Flash의 설정·키 저장 영역입니다. 이름 자체가 암호화를 의미하지는 않습니다.
  • CSR·CA: CSR은 인증서 서명 요청, CA는 인증서를 발급·검증하는 기관 또는 해당 인증서입니다.
  • CN·O·OU: 인증서 주체의 일반 이름, 조직, 조직 단위입니다.
  • SAN·EKU: 각각 허용되는 접속 이름·IP와 인증 용도를 나타냅니다.
  • PEM: BEGIN/END 표시가 있는 텍스트 형식으로 인증서, CSR, 키에 사용합니다.
  • PKI·mTLS: PKI는 인증서·신뢰 관리 체계이며 mTLS는 클라이언트와 서버 모두 인증서를 제시하는 연결 방식입니다.

2. Cambiar las contraseñas del dispositivo

Estos controles modifican las contraseñas de inicio de sesión de TianShanOS, no la contraseña SSH de un servidor remoto.

2.1 El aviso de contraseña tras iniciar sesión

Si una cuenta sigue marcada como contraseña sin cambiar, aparece un aviso después de iniciar sesión. Establece una contraseña larga y única. Elegir cambiarla más tarde cierra el aviso; no hace seguro conservar la predeterminada.

Este aviso no es una pantalla de ajustes de cuenta que puedas reabrir en cualquier momento. Si admin ya cambió su contraseña y necesita volver a hacerlo, root puede establecerla desde Security.

2.2 Establecer una contraseña como root

  1. Inicia sesión como root y abre Security.
  2. En Account Security, selecciona Set root password o Set admin password.
  3. Introduce dos veces la misma contraseña nueva y envíala. La interfaz admite 4-64 caracteres; cuatro caracteres son un mínimo técnico, no una recomendación de seguridad.

Comprueba el resultado: inicia sesión con la contraseña nueva en una ventana de navegación privada antes de cerrar la sesión original. Cambiar una contraseña no cierra automáticamente las sesiones existentes.

Si no puedes iniciar sesión, comprueba primero la cuenta y la dirección del dispositivo. Cinco intentos fallidos consecutivos provocan un bloqueo de unos cinco minutos. Evita probar contraseñas repetidamente.

2.3 Restablecer la contraseña de admin

root puede restablecer la contraseña predeterminada de admin, rm01, y quitar su bloqueo de inicio de sesión. Después, inicia una sesión nueva como admin y establece una contraseña nueva de inmediato. El restablecimiento es una medida temporal de recuperación. No conserves la contraseña predeterminada ni supongas que cambiarla cierra todas las sesiones existentes.

3. Conectarse a un servidor con una clave SSH

En la primera configuración, crea una clave RSA, instala su clave pública, prueba la conexión y comprueba la huella del servidor. Para retirar una clave, revoca primero el acceso en los servidores, confirma que ya no funciona y solo entonces elimina la clave local.

3.1 Crear una clave

  1. En Key Management, selecciona Generate New Key.
  2. Revisa la lista y elige un ID de clave sin utilizar, como backup01. No reutilices un ID: la API de generación no rechaza duplicados y puede sobrescribir la clave existente.
  3. Elige RSA 2048 o RSA 4096. RSA 2048 es la opción predeterminada de la interfaz. Se muestran opciones ECDSA, pero la vía actual de autenticación SSH por clave pública no las admite.
  4. Añade un comentario o alias si resulta útil. Permite exportar la clave privada solo si lo necesitas para copias de seguridad o migración; no hay una interfaz para cambiar este ajuste más adelante.
  5. Selecciona Generate, espera a que termine y actualiza la lista.

Comprueba el resultado: localiza el ID previsto y el tipo RSA. Abre Public Key y comprueba que el texto completo empieza por ssh-rsa.

Ten en cuenta que la lista admite ocho entradas. Si está llena, retira una clave que ya no utilices antes de generar otra. El almacenamiento de la clave y su registro en la lista pueden completarse o fallar por separado; comprueba la lista incluso tras un mensaje de éxito. Hide Key ID no impide que la API exponga el ID real.

3.2 Instalar la clave pública

La instalación añade la clave pública a ~/.ssh/authorized_keys de la cuenta remota y permite que esa cuenta acepte la clave privada correspondiente. No cambia la contraseña del servidor.

  1. Selecciona Deploy en la fila de la nueva clave.
  2. Introduce la dirección del servidor, el usuario, el puerto SSH y la contraseña de esa cuenta.
  3. Revisa los datos y selecciona Start Deploy.
  4. Comprueba que el servidor aparece en Deployed Hosts y pruébalo como se describe a continuación.

La implementación actual se autentica con la contraseña antes de comprobar la huella del host y confía automáticamente en los hosts desconocidos. No garantiza que la identidad del servidor se verifique antes de enviar la contraseña. Realiza la primera conexión en una red controlada; comprobar la huella después no revierte la exposición de la contraseña. Si la instalación indica éxito, pero falta el registro o falla la prueba, no vuelvas a instalarla de inmediato. La clave pública puede estar instalada aunque haya fallado la prueba posterior con la clave o el guardado del registro local. Comprueba authorized_keys mediante otra conexión de gestión. Repetir la instalación puede añadir entradas duplicadas.

3.3 Probar la conexión

  1. En Deployed Hosts, comprueba la dirección, el puerto, el usuario y el ID de clave.
  2. Selecciona Test. El dispositivo intenta ejecutar echo "TianshanOS SSH Test OK".
  3. Tras la primera conexión, comprueba la huella guardada del host siguiendo el apartado 4.3.

Qué significa el éxito: la página comprueba si la operación de API se completó, pero no verifica el código de salida ni la salida del comando remoto. Es una comprobación básica de conexión, no una prueba de aceptación completa. No demuestra que sudo ni los comandos de tu aplicación funcionen. Para una tarea importante, verifica la salida, el código de salida y los permisos del comando real.

Si falla, comprueba la conectividad, el servicio SSH, la cuenta y la autorización remota. Deja de reintentar si la huella ha cambiado o la identidad del servidor es incierta; sigue el apartado 4.3.

3.4 Revocar el acceso antes de eliminar la clave local

  1. Confirma que funciona otra conexión de gestión al servidor y que la clave original sigue en el dispositivo.
  2. Selecciona Revoke en la fila del host, introduce la contraseña del servidor y confirma Revoke & Remove. También puedes empezar desde la fila de la clave e introducir los datos del destino.
  3. Revisa el resultado y utiliza una conexión de gestión de confianza para comprobar que la clave pública y sus posibles duplicados han desaparecido de authorized_keys.
  4. Confirma que la clave antigua ya no permite iniciar sesión. La revocación deja una copia authorized_keys.bak; gestiónala conforme a la política de copias de seguridad del servidor para no restaurar después una autorización antigua.
  5. Actualiza la lista local de hosts. La página intenta eliminar el registro, pero no comprueba el resultado de esa solicitud. Si sigue presente, elimínalo manualmente.
  6. Solo después de atender todos los servidores de destino, elimina la clave antigua del dispositivo y las copias de la clave privada que ya no necesites.

Si no se encuentra una clave pública coincidente, confirma en el servidor que has elegido la cuenta correcta y que la clave no está presente antes de optar por eliminar solo el registro local.

Si la revocación falla o el servidor parece sospechoso, conserva la clave local y utiliza una consola de confianza u otra conexión de administrador. No sigas enviando una contraseña a un servidor de identidad dudosa.

4. Gestionar claves, hosts y huellas

4.1 Copiar una clave pública o exportar una privada

Clave pública: selecciona Public Key y copia el valor completo en una sola línea para el administrador del servidor. Una clave pública no es secreta. Enviarla a la persona equivocada no expone por sí solo la clave privada ni exige sustituir el par. El acceso solo se concede cuando un administrador la añade a la lista de autorizaciones de una cuenta.

Clave privada: solo puede exportarse si se permitió al crearla. Utiliza un ordenador de confianza en una red aislada, guárdala en un almacén de secretos aprobado y elimina las copias temporales del portapapeles y de la carpeta de descargas. No la pegues en chats, incidencias ni registros.

Si Copy no hace nada, puede que el navegador bloquee el portapapeles en una página HTTP. Selecciona y copia el texto visible manualmente; comprueba que el principio, el final y todo el contenido estén intactos. No reduzcas la seguridad del navegador solo para habilitar la copia.

4.2 Revocar, quitar y eliminar son operaciones distintas

AcciónEfecto
Revocar una clave públicaIntenta quitar la autorización del servidor; requiere la contraseña remota
Quitar un hostElimina el registro local de conexión del dispositivo, no la autorización remota
Eliminar una claveElimina el material de clave local; no contacta con el servidor ni revoca accesos
Eliminar una huella de hostElimina el registro de identidad guardado del servidor, no el registro de conexión ni la autorización remota

Deployed Hosts es una lista local, no una vista en tiempo real de las autorizaciones del servidor. Una lista vacía no demuestra que se haya retirado el acceso remoto, ni la presencia de un host garantiza que sea accesible.

4.3 Comprobar la huella del servidor SSH

Una huella identifica el servidor al que te conectas. Esta página guarda el resumen SHA-256 como 64 caracteres hexadecimales. Las herramientas OpenSSH suelen mostrar SHA256:base64. Pide al administrador el mismo formato antes de comparar; las cadenas no son directamente intercambiables.

Tras la primera conexión, abre la huella completa con View en la sección de huellas de host. Compárala con un valor obtenido desde una consola del servidor, un inventario de activos u otro canal de confianza. La tabla solo muestra los primeros 32 caracteres, insuficientes para una comprobación completa. Si difieren, deja de conectarte e investiga en un entorno aislado. Si introdujiste una contraseña SSH, trátala como posiblemente expuesta. Utiliza una conexión de confianza para cambiarla, revisar los registros de acceso y quitar autorizaciones de clave pública no deseadas. No uses la conexión sospechosa para revocar el acceso desde esta página.

Si cambia una huella guardada:

  1. Deja de reintentar. No te limites a eliminar la entrada antigua.
  2. Utiliza una consola de confianza para verificar la nueva huella, la dirección IP, el puerto, la identidad del activo y el registro de mantenimiento.
  3. Elimina la huella antigua solo después de confirmar una reinstalación autorizada del servidor o un cambio autorizado de su clave de host.
  4. Vuelve a conectarte en una red controlada y consulta y comprueba la nueva huella guardada.

La página actual puede mostrar un error genérico de conexión en lugar de un cuadro específico de comparación de huellas.

Protege la tarjeta SD: las huellas se almacenan localmente y se sincronizan en archivos JSON en texto claro en la tarjeta. Al arrancar, las configuraciones de huellas disponibles en SD sustituyen los registros NVS correspondientes. Estos archivos no están firmados; impide su modificación por fuentes no fiables.

4.4 Importar y exportar configuraciones de hosts SSH

Este flujo específico de .tscfg es independiente de la aplicación general de configuraciones aún incompleta del capítulo 6. Un paquete de host contiene dirección, puerto, usuario, tipo de autenticación e ID de clave. No contiene la contraseña SSH ni la clave privada y no concede acceso en el servidor.

Para exportar, selecciona Export en la fila del host desde un dispositivo Developer. Si el destino es otro dispositivo, facilita y verifica su certificado y descarga el paquete. Un dispositivo normal puede mostrar el botón, pero el backend rechaza su solicitud de exportación.

Para importar:

  1. Confirma que el paquete se creó para este dispositivo, que la tarjeta SD admite escritura y que el origen se ha verificado por un canal de confianza.
  2. Asegúrate de que este dispositivo ya dispone de la clave correcta referenciada por el paquete. Un ID coincidente no basta; el material de clave debe corresponder a la autorización del servidor.
  3. Selecciona Import Host, elige el archivo y revisa la vista previa. Activa la sobrescritura solo si pretendes sustituir una configuración existente con el mismo nombre.
  4. Confirma y reinicia cuando se indique. La importación guarda el paquete en SD; la carga y el descifrado se intentan al reiniciar.
  5. Comprueba la dirección, el usuario, el puerto y el ID de clave cargados y prueba la conexión. Una vista previa correcta no demuestra que el paquete vaya a funcionar. No establece confianza en el firmante ni comprueba la huella del destinatario. La comprobación del destino se realiza al cargar tras el reinicio. Elimina un registro incorrecto y su paquete SD correspondiente para impedir que vuelva a cargarse. Antes de sustituir el certificado del dispositivo, lee también el apartado 5.5.

5. Configurar certificados HTTPS y mTLS

Este capítulo se dirige a los administradores de certificados. El servicio actual del puerto 443 solo ofrece endpoints de salud, identidad y pruebas de permisos, no la interfaz web completa. Con sus ajustes predeterminados, el arranque requiere una clave privada de dispositivo, un certificado de dispositivo y una cadena de CA de clientes.

5.1 Función de cada certificado

  • El certificado y la clave privada del dispositivo le permiten demostrar su identidad al cliente que se conecta.
  • El certificado y la clave privada del cliente, en poder de un ordenador o servicio, permiten que ese cliente demuestre su identidad al dispositivo.
  • La cadena de CA instalada en el dispositivo verifica los certificados de los clientes. No hace que un ordenador o navegador confíe automáticamente en el certificado del dispositivo.

Este intercambio de certificados en ambos sentidos se denomina TLS mutuo o mTLS. El cliente debe además confiar en la CA que emitió el certificado del dispositivo y comprobar su nombre y usos permitidos.

5.2 Generar una clave de dispositivo y una solicitud de certificado

  1. En HTTPS Certificate, selecciona Generate Key Pair. Se crea una clave privada ECDSA P-256 independiente de las claves SSH. No puede exportarse mediante esta interfaz.
  2. Si ya existe una clave, detente y revisa el apartado 5.5 antes de continuar. Generar otra sobrescribe la anterior.
  3. Selecciona Generate CSR. Introduce el ID del dispositivo (CN), la organización (O) y la unidad organizativa (OU), o deja todos los campos vacíos.
  4. Envía el texto completo de la CSR al administrador de tu CA. Una CSR solicita un certificado; no contiene la clave privada ni instala un certificado.

Comprueba los nombres antes de la emisión: el flujo con campos personalizados no genera un SAN. Con todos los campos vacíos, el CN queda fijado en TIANSHAN-DEVICE-001; la IP actual solo se incluye como SAN de tipo IP si puede obtenerse. No se añade ningún SAN DNS. Pide al administrador de la CA que inspeccione la CSR y utilice un proceso de emisión controlado para incluir en el SAN del certificado final las IP o los nombres DNS necesarios. Este formulario no permite editar los SAN. Comprueba el resultado: actualiza la página para confirmar que existe la clave privada. El administrador de la CA debe inspeccionar la clave pública, el sujeto y el SAN de la CSR, y comprobar que el certificado emitido tiene el uso requerido de autenticación de servidor (EKU).

5.3 Instalar el certificado del dispositivo

  1. Obtén un certificado PEM que corresponda a la clave privada actual del dispositivo.
  2. Selecciona Install Cert, pega el texto completo con sus delimitadores y envíalo.
  3. Consulta el certificado y comprueba su sujeto, emisor y fechas de validez.

El mensaje de éxito solo indica que el certificado puede analizarse y que su clave pública corresponde a la clave privada actual. La instalación no valida por completo la cadena de confianza, SAN, EKU, la vigencia actual ni la política del sujeto.

El cliente real debe comprobar la cadena, el nombre de acceso, los usos y la validez. Si la instalación indica que la clave no coincide, localiza el certificado emitido para la CSR actual. No generes otra clave privada solo para eliminar el error.

5.4 Instalar la cadena de CA de clientes y probar

  1. Selecciona Install CA y pega uno o varios certificados CA PEM utilizados para confiar en tus clientes.
  2. Mantén disponible la interfaz HTTP de gestión y programa un reinicio antes de probar. La instalación actualiza el almacenamiento, pero no reinicia activamente el servicio del puerto 443.
  3. Accede a los endpoints de prueba pertinentes con un certificado de cliente de confianza, con el uso y rol correctos.
  4. Repite con un certificado no fiable o sin certificado y confirma que se rechaza la conexión.

Comprueba que el dispositivo presenta el nuevo certificado previsto, que los clientes de confianza solo acceden a los endpoints permitidos por su rol y que los demás no pueden conectarse. La negociación y los roles deben probarse en el dispositivo, no deducirse de un mensaje de instalación.

5.5 Renovar certificados o eliminar todas las credenciales

Nota de operación

Si solo caduca el certificado, puedes reutilizar una clave privada no comprometida para solicitar uno nuevo, instalarlo y repetir las pruebas. Sin embargo, los Config Packs están vinculados a la huella del certificado del destinatario. Aunque se conserve la clave privada, una huella distinta hace que, tras reinicializar o reiniciar, los paquetes antiguos se rechacen por pertenecer a otro destinatario. Prepara paquetes de sustitución antes de cambiar el certificado.

Al sustituir la clave privada, la CSR y el certificado anteriores dejan de corresponder a la nueva clave. Eso no revoca el certificado antiguo en la CA. Si la clave anterior estuvo expuesta, gestiona por separado la revocación y la respuesta al incidente. Los paquetes que dependan de una clave privada perdida pueden ser irrecuperables. Para eliminar todas las credenciales PKI, Delete Credentials en la sección de certificados borra conjuntamente la clave privada, el certificado del dispositivo y la cadena de CA de clientes. Verifica tu acceso de recuperación HTTP y prepara paquetes de sustitución antes de confirmar. Una copia del certificado público no puede restaurar una clave privada.

Después de eliminar, actualiza la página y comprueba que aparece un estado sin inicializar. Reinicia y verifica que el puerto 443 ya no utiliza las credenciales antiguas. Para restablecer el servicio, genera una clave nueva, obtén e instala el certificado del dispositivo, instala la cadena de CA y repite las pruebas.

6. Comprender las limitaciones de Config Pack

Un Config Pack es un paquete .tscfg cifrado y firmado. La implementación actual permite crear e inspeccionar paquetes, pero la aplicación general de configuraciones está incompleta. No dependas de ella para configurar flotas en producción, recuperar el sistema ante desastres ni demostrar que los ajustes han cambiado.

6.1 Qué hacen actualmente los controles

AcciónResultado actual
Export Device CertificateMuestra el certificado público para que un remitente cree un paquete destinado a este dispositivo; no exporta la clave privada
VerifyComprueba la estructura y la firma del texto cifrado con el certificado incluido; no establece confianza en el firmante ni la identidad del destinatario
Import tras seleccionar o pegar un paqueteLos parámetros del frontend y del backend no coinciden; este flujo no puede completarse
Import desde la lista de paquetesValida un archivo existente en el dispositivo; no lo copia, descifra ni aplica
ApplyDescifra y enumera los nombres de módulos sin escribir sus ajustes; aun así puede indicar éxito
Export Config Pack en un dispositivo DeveloperCrea un paquete cifrado y firmado descargable e intenta guardarlo en la tarjeta SD

6.2 Verificar el origen, no solo la firma

Actualmente, el destinatario comprueba la firma con el certificado incluido en el paquete. No está implementada la validación de confianza de la cadena del certificado firmante. La firma cubre el texto cifrado; no supongas que por ello todos los metadatos mostrados están autenticados. La etiqueta Official tampoco demuestra un origen de confianza.

Antes de importar o inspeccionar un paquete, utiliza un sistema de activos o un canal independiente y aprobado para confirmar la huella del certificado firmante, el certificado de destino y el cambio previsto. Recibir un certificado y su huella en el mismo correo no es una comprobación independiente. El nombre de destino de la vista previa no sustituye la verificación de la huella del certificado.

6.3 Compartir el certificado del dispositivo e inspeccionar un paquete

Para facilitar el certificado de este dispositivo, selecciona Export Device Certificate, copia el PEM completo y la huella mostrada, y envía el certificado público al remitente. Confirma la huella por otro canal de confianza.

Para inspeccionar un paquete recibido, abre Import Config Pack, selecciona o pega el archivo .tscfg y selecciona Verify. Revisa los datos del firmante y comprueba el origen. La verificación no aplica ajustes ni demuestra que este dispositivo sea el destinatario. Detente si el origen, el destino o la finalidad no están claros.

Aunque la verificación sea correcta, no dependas de los controles generales Import y Apply actuales para configurar el dispositivo. Utiliza los controles admitidos de las páginas de cada función y comprueba después los ajustes reales.

6.4 Exportar un paquete desde un dispositivo Developer

  1. Prepara archivos de configuración JSON válidos en la tarjeta SD y obtén un certificado verificado del dispositivo de destino.
  2. Selecciona Export Config Pack, elige los archivos, introduce un nombre y una descripción y pega el certificado de destino.
  3. Genera y descarga el archivo .tscfg.
  4. Comprueba por separado la descarga del navegador y el archivo guardado en /sdcard/output_config/. Si falla la escritura en SD, la API puede devolver aun así el paquete para descargarlo.

La exportación no modifica los ajustes de origen. Vuelve a generar un paquete creado para un destino incorrecto o un certificado de destinatario obsoleto. Exportar correctamente no demuestra que funcione toda la distribución: la aplicación general en el dispositivo receptor sigue incompleta.

7.2 Posible exposición de una clave privada SSH

  1. Restringe el acceso al dispositivo y a sus registros. Los registros actuales pueden contener el principio de una clave privada.
  2. Revoca la clave pública en todos los servidores afectados mediante conexiones de confianza. Comprueba las copias de seguridad y confirma que la clave antigua ya no funciona.
  3. Crea e instala una nueva clave RSA con otro ID. Cuando funcione, elimina la clave antigua y sus copias exportadas.
  4. Revisa los registros de acceso. La lista local del dispositivo puede no incluir todos los servidores donde se autorizó la clave.

Si la expuesta es la clave privada HTTPS, sustituye las credenciales del dispositivo según el apartado 5.5 y coordina con el administrador de la CA la revocación del certificado y el tratamiento de los paquetes antiguos.

7.3 Otros riesgos de seguridad actuales

Además de las limitaciones de HTTP, autorización, confianza en la primera conexión y paquetes ya descritas, la configuración de compilación inspeccionada no activa NVS Encryption, Flash Encryption ni Secure Boot. No afirmes que estos mecanismos protegen las claves privadas almacenadas o la integridad del arranque. El firmware realmente grabado y los ajustes eFuse de cada dispositivo requieren comprobaciones aparte.

Si tu uso no admite estas limitaciones, mantén el dispositivo fuera de esa red o entorno de confianza hasta que el responsable de seguridad apruebe medidas de aislamiento o una corrección del producto. Las comprobaciones de una guía no sustituyen controles de seguridad ausentes en el producto.

8.2 Términos utilizados

  • Clave pública / privada: comparte la pública con un administrador que conceda acceso; mantén la privada en secreto. La autenticación utiliza el par correspondiente.
  • NVS: área de almacenamiento Flash para ajustes y claves del dispositivo. El nombre no implica cifrado.
  • CSR / CA: solicitud de firma de certificado y autoridad de certificación o su certificado.
  • CN / O / OU: campos de nombre común, organización y unidad organizativa del sujeto de un certificado.
  • SAN / EKU: nombres o direcciones IP cubiertos por el certificado y usos de autenticación que permite.
  • PEM: formato de texto con delimitadores BEGIN/END, utilizado para certificados, CSR y claves.
  • PKI / mTLS: sistema de gestión de certificados y confianza, y TLS mutuo, en el que cliente y servidor presentan certificados.

2. Changer les mots de passe de l’appareil

Ces commandes modifient les mots de passe de connexion à TianShanOS, pas le mot de passe SSH d’un serveur distant.

2.1 L’invite de changement après connexion

Si un compte est encore marqué comme utilisant un mot de passe inchangé, une invite apparaît après la connexion. Définissez un mot de passe long et unique. Choisir de le changer plus tard ferme l’invite ; cela ne rend pas le mot de passe par défaut sûr à conserver.

Cette invite n’est pas un écran de réglages du compte que vous pouvez rouvrir à tout moment. Si admin a déjà changé son mot de passe et doit le modifier à nouveau, root peut le définir depuis Security.

2.2 Définir un mot de passe en tant que root

  1. Connectez-vous en tant que root et ouvrez Security.
  2. Dans Account Security, sélectionnez Set root password ou Set admin password.
  3. Saisissez deux fois le même nouveau mot de passe et validez. L’interface accepte 4-64 caractères ; quatre caractères constituent un minimum technique, pas une recommandation de sécurité.

Vérifiez le résultat : connectez-vous avec le nouveau mot de passe dans une fenêtre de navigation privée avant de fermer votre session d’origine. Changer un mot de passe ne ferme pas automatiquement les sessions existantes.

Si la connexion échoue, vérifiez d’abord le compte et l’adresse de l’appareil. Cinq échecs consécutifs déclenchent un verrouillage d’environ cinq minutes. Évitez les essais répétés.

2.3 Réinitialiser le mot de passe admin

root peut rétablir le mot de passe admin par défaut, rm01, et lever son verrouillage de connexion. Après la réinitialisation, ouvrez une nouvelle session admin et définissez immédiatement un nouveau mot de passe. La réinitialisation est une mesure de récupération temporaire. Ne conservez pas le mot de passe par défaut et ne supposez pas que le changement ferme toutes les sessions existantes.

3. Se connecter à un serveur avec une clé SSH

Pour une première configuration, créez une clé RSA, déployez sa clé publique, testez la connexion, puis vérifiez l’empreinte du serveur. Pour retirer une clé, révoquez d’abord l’accès sur les serveurs, confirmez que l’ancienne clé ne fonctionne plus, puis supprimez la clé locale.

3.1 Créer une clé

  1. Dans Key Management, sélectionnez Generate New Key.
  2. Vérifiez la liste et choisissez un ID de clé inutilisé, par exemple backup01. Ne réutilisez pas un ID : l’API de génération ne rejette pas les doublons et peut écraser la clé existante.
  3. Choisissez RSA 2048 ou RSA 4096. RSA 2048 est le choix par défaut de l’interface. Des options ECDSA sont affichées, mais le chemin actuel d’authentification SSH par clé publique ne les prend pas en charge.
  4. Ajoutez un commentaire ou un alias si utile. N’autorisez l’exportation de la clé privée que pour un besoin de sauvegarde ou de migration ; aucune interface ne permet de modifier ce réglage ultérieurement.
  5. Sélectionnez Generate, attendez la fin et actualisez la liste.

Vérifiez le résultat : retrouvez l’ID prévu et le type RSA. Ouvrez Public Key et vérifiez que le texte complet commence par ssh-rsa.

La liste contient au maximum huit entrées. Lorsqu’elle est pleine, retirez une clé inutilisée avant d’en générer une autre. Le stockage de la clé et son inscription dans la liste peuvent réussir ou échouer séparément ; vérifiez donc la liste même après un message de réussite. Hide Key ID n’empêche pas l’API d’exposer le véritable ID.

3.2 Déployer la clé publique

Le déploiement ajoute la clé publique à ~/.ssh/authorized_keys du compte distant, ce qui permet à ce compte d’accepter la clé privée correspondante. Il ne change pas le mot de passe du serveur.

  1. Sélectionnez Deploy sur la ligne de la nouvelle clé.
  2. Saisissez l’adresse du serveur, le nom d’utilisateur, le port SSH et le mot de passe de ce compte.
  3. Vérifiez les informations et sélectionnez Start Deploy.
  4. Recherchez le serveur dans Deployed Hosts, puis testez-le comme indiqué ci-dessous.

L’implémentation actuelle s’authentifie avec le mot de passe avant de vérifier l’empreinte de l’hôte et fait automatiquement confiance aux hôtes inconnus. Elle ne garantit pas que l’identité du serveur soit vérifiée avant l’envoi du mot de passe. Effectuez la première connexion sur un réseau contrôlé ; vérifier ensuite l’empreinte ne peut pas annuler l’exposition du mot de passe. Si le déploiement annonce une réussite mais que l’entrée manque ou que le test échoue, ne recommencez pas immédiatement. La clé publique peut déjà être installée malgré l’échec du test par clé ou de l’enregistrement local qui suit. Vérifiez authorized_keys par une autre connexion d’administration. Des déploiements répétés peuvent ajouter des doublons.

3.3 Tester la connexion

  1. Dans Deployed Hosts, vérifiez l’adresse, le port, le nom d’utilisateur et l’ID de clé.
  2. Sélectionnez Test. L’appareil tente d’exécuter echo "TianshanOS SSH Test OK".
  3. Après la première connexion, vérifiez l’empreinte enregistrée de l’hôte selon la section 4.3.

Ce que signifie la réussite : la page vérifie si l’opération d’API a réussi, mais pas le code de sortie ni la sortie de la commande distante. Il s’agit d’un contrôle élémentaire de connexion, pas d’un test d’acceptation complet. Il ne prouve pas que sudo ni les commandes de votre application fonctionneront. Pour une tâche importante, vérifiez la sortie, le code de sortie et les permissions de la commande réelle.

En cas d’échec, vérifiez la connectivité, le service SSH, le compte et l’autorisation distante. Cessez les essais si l’empreinte a changé ou si l’identité du serveur est incertaine ; suivez la section 4.3.

3.4 Révoquer l’accès avant de supprimer la clé locale

  1. Confirmez qu’une autre connexion d’administration au serveur fonctionne et que la clé d’origine existe toujours sur l’appareil.
  2. Sélectionnez Revoke sur la ligne de l’hôte, saisissez le mot de passe du serveur et confirmez Revoke & Remove. Vous pouvez aussi partir de la ligne de la clé et saisir les informations de la cible.
  3. Examinez le résultat, puis vérifiez par une connexion d’administration de confiance que la clé publique et ses éventuels doublons ont disparu de authorized_keys.
  4. Confirmez que l’ancienne clé ne permet plus de se connecter. La révocation laisse une sauvegarde authorized_keys.bak ; traitez-la selon la politique de sauvegarde du serveur pour éviter de rétablir ultérieurement une ancienne autorisation.
  5. Actualisez la liste locale des hôtes. La page tente de retirer l’entrée sans vérifier le résultat de cette requête. Supprimez-la manuellement si elle subsiste.
  6. Une fois tous les serveurs cibles traités, supprimez l’ancienne clé de l’appareil et les copies privées devenues inutiles.

Si aucune clé publique correspondante n’est trouvée, confirmez sur le serveur que le compte choisi est correct et que la clé est absente avant de supprimer uniquement l’entrée locale.

Si la révocation échoue ou si le serveur semble suspect, conservez la clé locale et utilisez une console de confiance ou une autre connexion d’administrateur. Ne continuez pas à envoyer un mot de passe à un serveur dont l’identité est douteuse.

4. Gérer les clés, les hôtes et les empreintes

4.1 Copier une clé publique ou exporter une clé privée

Clé publique : sélectionnez Public Key et copiez la valeur complète, sur une seule ligne, pour l’administrateur du serveur. Une clé publique n’est pas secrète. L’envoyer à la mauvaise personne n’expose pas en soi la clé privée et n’impose pas de remplacer la paire. L’accès n’est accordé que lorsqu’un administrateur l’ajoute à la liste d’autorisation d’un compte.

Clé privée : l’exportation n’est disponible que si elle a été autorisée à la création. Utilisez un ordinateur de confiance sur un réseau isolé, conservez la clé dans un coffre de secrets approuvé et effacez les copies temporaires du presse-papiers et du dossier de téléchargement. Ne la collez jamais dans une conversation, un ticket ou un journal.

Si Copy ne fait rien, le navigateur peut bloquer le presse-papiers sur une page HTTP. Sélectionnez et copiez manuellement le texte visible, puis vérifiez son début, sa fin et l’intégralité de son contenu. N’affaiblissez pas les réglages de sécurité du navigateur pour permettre la copie.

4.2 Révoquer, retirer et supprimer sont des opérations distinctes

ActionEffet
Révoquer une clé publiqueTente de retirer l’autorisation sur le serveur ; exige le mot de passe distant
Retirer un hôteSupprime l’entrée locale de connexion de l’appareil, pas l’autorisation distante
Supprimer une cléSupprime les données de clé locales ; ne contacte pas le serveur et ne révoque pas l’accès
Supprimer une empreinte d’hôteSupprime une identité de serveur enregistrée, pas l’entrée de connexion ni l’autorisation distante

Deployed Hosts est une liste locale, pas une vue en temps réel des autorisations du serveur. Une liste vide ne prouve pas le retrait de l’accès distant, et la présence d’un hôte ne garantit pas qu’il soit joignable.

4.3 Vérifier l’empreinte du serveur SSH

Une empreinte identifie le serveur auquel vous vous connectez. Cette page conserve le condensat SHA-256 sous forme de 64 caractères hexadécimaux. Les outils OpenSSH affichent souvent SHA256:base64. Demandez à l’administrateur le même format avant toute comparaison ; les chaînes ne sont pas directement interchangeables.

Après la première connexion, ouvrez l’empreinte complète avec View dans la section des empreintes d’hôtes. Comparez-la à une valeur obtenue depuis une console du serveur, un inventaire d’actifs ou un autre canal de confiance. Le tableau n’affiche que les 32 premiers caractères, ce qui ne suffit pas à une vérification complète. En cas de différence, cessez les connexions et enquêtez dans un environnement isolé. Si vous avez saisi un mot de passe SSH, considérez-le comme potentiellement exposé. Changez-le par une connexion de confiance, examinez les journaux de connexion et retirez les autorisations de clé publique indésirables. N’utilisez pas la connexion suspecte pour révoquer l’accès depuis cette page.

Si une empreinte enregistrée change :

  1. Cessez les essais. Ne supprimez pas simplement l’ancienne entrée.
  2. Utilisez une console de confiance pour vérifier la nouvelle empreinte, l’adresse IP, le port, l’identité de l’actif et son historique de maintenance.
  3. Ne supprimez l’ancienne empreinte qu’après avoir confirmé une réinstallation autorisée du serveur ou un changement autorisé de sa clé d’hôte.
  4. Reconnectez-vous sur un réseau contrôlé, puis consultez et vérifiez la nouvelle empreinte enregistrée.

La page actuelle peut afficher une erreur de connexion générique plutôt qu’un dialogue dédié à la comparaison des empreintes.

Protégez la carte SD : les empreintes sont stockées localement et synchronisées dans des fichiers JSON en clair sur la carte. Au démarrage, les configurations d’empreintes disponibles sur SD remplacent les entrées NVS correspondantes. Ces fichiers ne sont pas signés ; empêchez leur modification par des sources non fiables.

4.4 Importer et exporter des configurations d’hôtes SSH

Ce processus .tscfg dédié est distinct de l’application générale des configurations, encore inachevée, décrite au chapitre 6. Un paquet d’hôte contient l’adresse, le port, le nom d’utilisateur, le type d’authentification et l’ID de clé. Il ne contient ni le mot de passe SSH ni la clé privée, et n’accorde aucun accès sur le serveur.

Pour exporter, sélectionnez Export sur la ligne de l’hôte depuis un appareil Developer. Pour un autre appareil, fournissez et vérifiez le certificat de la cible, puis téléchargez le paquet. Un appareil ordinaire peut afficher le bouton, mais le backend rejette sa demande d’exportation.

Pour importer :

  1. Confirmez que le paquet a été créé pour cet appareil, que la carte SD est accessible en écriture et que l’origine a été vérifiée par un canal de confiance.
  2. Assurez-vous que l’appareil possède déjà la bonne clé référencée par le paquet. Un ID identique ne suffit pas ; les données de clé doivent correspondre à l’autorisation du serveur.
  3. Sélectionnez Import Host, choisissez le fichier et examinez l’aperçu. N’activez l’écrasement que pour remplacer volontairement une configuration portant le même nom.
  4. Confirmez et redémarrez lorsque cela est demandé. L’importation enregistre le paquet sur SD ; le chargement et le déchiffrement sont tentés au redémarrage.
  5. Vérifiez l’adresse, le nom d’utilisateur, le port et l’ID de clé chargés, puis testez la connexion. Un aperçu réussi ne prouve pas que le paquet fonctionnera. Il n’établit ni la confiance dans le signataire ni l’empreinte du destinataire. Le contrôle de la cible a lieu au chargement après redémarrage. Supprimez une entrée incorrecte et son paquet SD pour empêcher un nouveau chargement. Avant de remplacer le certificat de l’appareil, lisez aussi la section 5.5.

5. Configurer les certificats HTTPS et mTLS

Ce chapitre s’adresse aux administrateurs de certificats. Le service actuel sur le port 443 ne propose que des points d’accès de santé, d’identité et de test des permissions, pas l’interface web complète. Avec ses réglages par défaut, son démarrage exige une clé privée d’appareil, un certificat d’appareil et une chaîne de CA de confiance pour les clients.

5.1 Comprendre le rôle de chaque certificat

  • Le certificat et la clé privée de l’appareil lui permettent de prouver son identité au client qui se connecte.
  • Le certificat et la clé privée du client, détenus par un ordinateur ou un service, permettent à ce client de prouver son identité à l’appareil.
  • La chaîne de CA installée sur l’appareil sert à vérifier les certificats clients. Elle ne fait pas automatiquement reconnaître le certificat de l’appareil comme fiable par un ordinateur ou un navigateur.

Cet échange de certificats dans les deux sens est appelé TLS mutuel, ou mTLS. Le client doit aussi faire confiance à la CA ayant émis le certificat de l’appareil et vérifier son nom et ses usages autorisés.

5.2 Générer une clé d’appareil et une demande de certificat

  1. Dans HTTPS Certificate, sélectionnez Generate Key Pair. Cela crée une clé privée ECDSA P-256 distincte des clés SSH. Elle ne peut pas être exportée par cette interface.
  2. Si une clé existe déjà, arrêtez-vous et consultez la section 5.5. En générer une nouvelle écrase l’ancienne.
  3. Sélectionnez Generate CSR. Saisissez l’ID d’appareil (CN), l’organisation (O) et l’unité d’organisation (OU), ou laissez tous les champs vides.
  4. Envoyez le texte complet de la CSR à l’administrateur de votre CA. Une CSR demande un certificat ; elle ne contient pas de clé privée et n’installe aucun certificat.

Vérifiez les noms avant l’émission : le chemin utilisant des champs personnalisés ne génère pas de SAN. Avec tous les champs vides, le CN est fixé à TIANSHAN-DEVICE-001 ; l’IP actuelle n’est incluse comme SAN de type IP que si elle peut être obtenue. Aucun SAN DNS n’est ajouté. Demandez à l’administrateur de la CA d’examiner la CSR et d’utiliser un processus d’émission contrôlé pour inclure les adresses IP ou noms DNS requis dans le SAN du certificat final. Ce formulaire ne permet pas de modifier les SAN. Vérifiez le résultat : actualisez la page pour confirmer la présence de la clé privée. L’administrateur de la CA doit examiner la clé publique, le sujet et le SAN de la CSR, et vérifier que le certificat émis autorise l’authentification de serveur requise (EKU).

5.3 Installer le certificat de l’appareil

  1. Obtenez un certificat PEM correspondant à la clé privée actuelle de l’appareil.
  2. Sélectionnez Install Cert, collez le texte complet avec ses délimiteurs et validez.
  3. Consultez le certificat et vérifiez son sujet, son émetteur et ses dates de validité.

Le message de réussite signifie seulement que le certificat peut être analysé et que sa clé publique correspond à la clé privée actuelle. L’installation ne valide pas complètement la chaîne de confiance, le SAN, l’EKU, la validité actuelle ni la politique du sujet.

Le client réel doit vérifier la chaîne, le nom d’accès, les usages et la validité. Si l’installation signale une incompatibilité de clé, retrouvez le certificat émis pour la CSR actuelle. Ne générez pas une nouvelle clé privée simplement pour faire disparaître l’erreur.

5.4 Installer la chaîne de CA de confiance pour les clients et tester

  1. Sélectionnez Install CA et collez un ou plusieurs certificats CA PEM utilisés pour faire confiance à vos clients.
  2. Gardez l’interface HTTP d’administration disponible et prévoyez un redémarrage avant les tests. L’installation met à jour le stockage, mais ne redémarre pas activement le service du port 443.
  3. Accédez aux points de test concernés avec un certificat client de confiance ayant l’usage et le rôle appropriés.
  4. Répétez avec un certificat non fiable ou sans certificat et confirmez le rejet de la connexion.

Vérifiez que l’appareil présente le nouveau certificat prévu, que les clients de confiance n’accèdent qu’aux points autorisés par leur rôle et que les clients non fiables ne peuvent pas se connecter. La négociation et les rôles doivent être testés sur l’appareil, et non déduits d’un message d’installation.

5.5 Renouveler les certificats ou supprimer tous les éléments d’authentification

Note d’utilisation

Si seul le certificat arrive à expiration, vous pouvez réutiliser une clé privée non compromise pour demander un nouveau certificat, l’installer et refaire les tests. Toutefois, les Config Packs sont liés à l’empreinte du certificat du destinataire. Même avec la même clé privée, un changement d’empreinte entraîne le rejet des anciens paquets comme destinés à un autre appareil après réinitialisation ou redémarrage. Préparez des paquets de remplacement avant de changer le certificat.

Lorsque vous remplacez la clé privée, l’ancienne CSR et l’ancien certificat ne correspondent plus à la nouvelle clé. Cela ne révoque pas l’ancien certificat auprès de la CA. Si l’ancienne clé a été exposée, traitez séparément la révocation et la réponse à l’incident. Les paquets dépendant d’une clé privée perdue peuvent être irrécupérables. Pour supprimer tous les éléments PKI, Delete Credentials dans la section des certificats efface ensemble la clé privée, le certificat de l’appareil et la chaîne de CA de confiance pour les clients. Vérifiez votre accès de récupération HTTP et préparez des paquets de remplacement avant de confirmer. Une sauvegarde du certificat public ne peut pas restaurer une clé privée.

Après la suppression, actualisez la page et vérifiez l’état non initialisé. Redémarrez et vérifiez que le port 443 n’utilise plus les anciens éléments d’authentification. Pour rétablir le service, générez une nouvelle clé, obtenez et installez un certificat d’appareil, installez la chaîne de CA et répétez les tests.

6. Comprendre les limites de Config Pack

Un Config Pack est un paquet .tscfg chiffré et signé. L’implémentation actuelle permet de créer et d’inspecter des paquets, mais l’application générale des configurations est inachevée. Ne vous y fiez pas pour configurer un parc en production, assurer une reprise après sinistre ou prouver que des réglages ont changé.

6.1 Ce que font actuellement les commandes

ActionRésultat actuel
Export Device CertificateAffiche le certificat public pour qu’un expéditeur crée un paquet destiné à cet appareil ; n’exporte pas la clé privée
VerifyVérifie la structure et la signature du contenu chiffré avec le certificat inclus ; n’établit ni la confiance dans le signataire ni l’identité du destinataire
Import après sélection ou collage d’un paquetLes paramètres du frontend et du backend ne correspondent pas ; ce processus ne peut pas aboutir
Import depuis la liste des paquetsValide un fichier existant sur l’appareil ; ne le copie, ne le déchiffre et ne l’applique pas
ApplyDéchiffre et énumère les noms de modules sans écrire leurs réglages ; peut malgré tout annoncer une réussite
Export Config Pack sur un appareil DeveloperCrée un paquet chiffré et signé téléchargeable et tente de l’enregistrer sur la carte SD

6.2 Vérifier l’origine, pas seulement la signature

Le destinataire vérifie actuellement la signature avec le certificat inclus dans le paquet. La validation de confiance de la chaîne du certificat signataire n’est pas implémentée. La signature couvre le contenu chiffré ; n’en déduisez pas que toutes les métadonnées affichées sont authentifiées. Le libellé Official ne prouve pas non plus une origine fiable.

Avant d’importer ou d’inspecter un paquet, utilisez un système de gestion des actifs ou un canal indépendant approuvé pour confirmer l’empreinte du certificat signataire, le certificat cible et le changement prévu. Recevoir un certificat et son empreinte dans le même courriel ne constitue pas une vérification indépendante. Le nom de cible affiché dans l’aperçu ne remplace pas la vérification de l’empreinte du certificat.

6.3 Partager le certificat de l’appareil et inspecter un paquet

Pour fournir le certificat de cet appareil, sélectionnez Export Device Certificate, copiez le PEM complet et l’empreinte affichée, puis transmettez le certificat public à l’expéditeur. Confirmez l’empreinte par un autre canal de confiance.

Pour inspecter un paquet reçu, ouvrez Import Config Pack, sélectionnez ou collez le fichier .tscfg, puis sélectionnez Verify. Examinez les informations du signataire et vérifiez l’origine. La vérification n’applique aucun réglage et ne prouve pas que cet appareil est le destinataire. Arrêtez-vous si l’origine, la cible ou l’objectif n’est pas clair.

Même si la vérification réussit, ne comptez pas sur les commandes générales Import et Apply actuelles pour configurer l’appareil. Utilisez les commandes prises en charge sur les pages des fonctions concernées, puis contrôlez les réglages réels.

6.4 Exporter un paquet depuis un appareil Developer

  1. Préparez des fichiers de configuration JSON valides sur la carte SD et obtenez un certificat vérifié de l’appareil cible.
  2. Sélectionnez Export Config Pack, choisissez les fichiers, saisissez un nom et une description, puis collez le certificat cible.
  3. Générez et téléchargez le fichier .tscfg.
  4. Vérifiez séparément le téléchargement du navigateur et le fichier enregistré dans /sdcard/output_config/. Si l’écriture SD échoue, l’API peut tout de même renvoyer le paquet à télécharger.

L’exportation ne modifie pas les réglages sources. Régénérez un paquet créé pour la mauvaise cible ou pour un certificat destinataire obsolète. Une exportation réussie ne prouve pas le fonctionnement de toute la distribution : l’application générale sur l’appareil récepteur reste inachevée.

7.2 Exposition présumée d’une clé privée SSH

  1. Restreignez l’accès à l’appareil et aux journaux. Les journaux actuels peuvent contenir le début d’une clé privée.
  2. Révoquez la clé publique sur tous les serveurs concernés par des connexions de confiance. Vérifiez les sauvegardes et confirmez que l’ancienne clé ne fonctionne plus.
  3. Créez et déployez une nouvelle clé RSA avec un nouvel ID. Une fois son fonctionnement confirmé, supprimez l’ancienne clé et ses copies exportées.
  4. Examinez les journaux de connexion. La liste locale de l’appareil peut ne pas contenir tous les serveurs ayant autorisé cette clé.

Si c’est la clé privée HTTPS qui a été exposée, remplacez les éléments d’authentification selon la section 5.5 et coordonnez avec l’administrateur de la CA la révocation du certificat et le traitement des anciens paquets.

7.3 Autres risques de sécurité actuels

Outre les limites déjà décrites concernant HTTP, les autorisations, la confiance à la première connexion et les paquets, la configuration de compilation examinée n’active ni NVS Encryption, ni Flash Encryption, ni Secure Boot. N’affirmez pas que ces mécanismes protègent les clés privées stockées ou l’intégrité du démarrage. Le firmware réellement installé et les réglages eFuse de l’appareil exigent des contrôles distincts.

Si votre usage ne peut pas accepter ces limites, maintenez l’appareil hors de ce réseau ou de cet environnement de confiance jusqu’à l’approbation de mesures d’isolation ou d’une correction du produit par le responsable de la sécurité. Les vérifications d’un guide utilisateur ne remplacent pas les contrôles de sécurité absents du produit.

8. Périmètre de la revue et glossaire

8.1 Base de ce guide

La revue a utilisé la copie de travail actuelle fondée sur d6ed947. Le comportement et les messages de la page se trouvent dans components/ts_webui/web/js/app.js ; celui des API, dans components/ts_api/src/ ; le stockage des clés et des hôtes, dans components/ts_security/src/. Les certificats, le service du port 443 et les paquets sont implémentés dans components/ts_cert/, components/ts_https/ et components/ts_config_pack/.

Les contrôles ont notamment porté sur les ID de clé en double, le traitement du code de sortie du test SSH, le nettoyage local après révocation, les empreintes du certificat destinataire et la logique inachevée d’importation et d’application des paquets. Il s’agissait d’une revue statique : aucune connexion à un serveur distant, aucune modification des éléments d’authentification d’un appareil ni aucun test d’acceptation de sécurité sur matériel n’a été effectué.

8.2 Termes employés

  • Clé publique / clé privée : partagez la clé publique avec l’administrateur qui accorde l’accès ; gardez la clé privée secrète. L’authentification utilise la paire correspondante.
  • NVS : zone de stockage Flash des réglages et des clés de l’appareil. Ce nom n’implique aucun chiffrement.
  • CSR / CA : demande de signature de certificat, et autorité de certification ou son certificat.
  • CN / O / OU : champs de nom commun, d’organisation et d’unité d’organisation du sujet d’un certificat.
  • SAN / EKU : noms ou adresses IP couverts par un certificat, et usages d’authentification autorisés.
  • PEM : format texte avec des délimiteurs BEGIN/END, utilisé pour les certificats, CSR et clés.
  • PKI / mTLS : système de gestion des certificats et de la confiance, et TLS mutuel où client et serveur présentent des certificats.
